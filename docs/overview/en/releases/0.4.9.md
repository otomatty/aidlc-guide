## [0.4.9] - 2026-05-28

Closes the per-Bolt fork/merge triad with its third leg. v0.4.0 shipped state-fork + audit-fork; this release adds runtime-graph fragment-fork + fragment-merge so parallel Construction Bolts each get a coherent `runtime-graph.json` entry post-merge. The orchestration sits in `aidlc-bolt.ts` `start --worktree` (after audit-fork, before the success-JSON) and `complete --merge` (after audit-merge, before the success-JSON), mirroring the existing fork/merge dance. The load-bearing piece is a `compile()` extension that populates `RuntimeStage.instances[]` for any Construction-phase stage whose `[started_at, completed_at OR now)` window contains ≥ 2 distinct `Bolt slug` values from `STATE_FORKED` rows; single-Bolt stages stay single-instance per the schema's optional `instances?` reservation. Audit count stays at **61** — no new event types; the fragment lifecycle rides on the existing BOLT_STARTED + STATE_FORKED + AUDIT_FORKED (fork) and BOLT_COMPLETED + STATE_MERGED + AUDIT_MERGED (merge) boundaries.

The fragment file lives at `<worktree>/aidlc-docs/runtime-graph.json` (gitignored, mirrors main). It's substrate-only in v0.5.0 — no v0.5.0 reader; v0.6.0's `--resume` is the consumer. fragment-fork's source-absent fallback (brownfield projects with no main runtime-graph.json yet) writes an empty graph anchored to the worktree's state cursor and emits `source_present: false` on stdout. fragment-merge is idempotent: re-runs after a successful merge or against a Bolt whose fragment-fork step failed exit cleanly with `status: "fragment-absent"`. Defense-in-depth removal pairs explicit fragment-merge during `complete --merge` with the implicit `git worktree remove` invoked by `aidlc-worktree merge` / `discard` — same pattern state-merge uses on the state side.

**Three forward-notes:**

* **`instances[].sensor_firings[]` per-Bolt attribution deferred.** This release introduces the per-Bolt nesting via `BoltInstance[]`, which means a later compile patch must populate BOTH the parent stage's `sensor_firings[]` AND each `BoltInstance.sensor_firings[]`. The parent rule is straightforward (per-stage filter by Timestamp window); the per-instance rule needs an attribution mechanism, likely Output-path under the Bolt's worktree path. This release leaves both empty arrays in lockstep so the next consumer sees a uniform substrate.
* **`instances[].memory_entries` + `memory_breakdown` deferred to per-stage memory.md lifecycle.** Per-Bolt memory.md doesn't exist yet; the per-stage memory.md lifecycle ships that shape in a later release. Every BoltInstance currently emits both fields as `null` (matches the v0.4.0 backfill rule — null = no per-Bolt memory.md history).
* **Defense-in-depth fragment removal is documented but not relied on.** The worktree fragment is removed by `aidlc-runtime fragment-merge` during `complete --merge` AND transitively by `git worktree remove` during `aidlc-worktree merge` / `discard`. The pair mirrors how state-merge + `git worktree remove` already pair on the state side. If fragment-merge fails after audit-merge succeeds, the unusual `BOLT_COMPLETED → STATE_MERGED → AUDIT_MERGED → BOLT_FAILED (Reason: fragment-merge-failed)` audit signature is the recovery surface; subsequent compile against main produces a coherent runtime-graph (the BOLT_FAILED at this position scores the instance `"approved"` because STATE_MERGED is already on record).

**Doc-drift correction (`docs/reference/19-runtime-graph.md` §10):** the prior wording said fork fires on `BOLT_FORKED` and merge on `AUDIT_MERGED`. `BOLT_FORKED` was a forward-reference doc-drift (not in `VALID_EVENT_TYPES`); §10 now reads "closed in v0.5.0 by `fragment-fork` (no new audit event; rides on STATE_FORKED + AUDIT_FORKED) and `fragment-merge` (no new audit event; rides on STATE_MERGED + AUDIT_MERGED)". §4 also gains a `failed` row covering the parent-stage rollup path; §7 retires the "deferred" framing for parallel-Bolt mid-flight recovery; new §11 documents the full fragment lifecycle including failure modes.
