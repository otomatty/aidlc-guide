## [0.5.10] - 2026-06-02

Teaches the deterministic orchestration engine (`aidlc-orchestrate next`) to resolve artifact paths. The compiled stage graph stores each stage's artifacts as vocabulary *names* (e.g. `decisions`), not file paths; the engine now turns those names into canonical `aidlc-docs/...` paths when it builds a `run-stage` directive, and drops `conditional_on: brownfield`/`greenfield` consumes-entries that don't match your workflow's Project Type. This is still engine-only groundwork — the engine stands beside the prose orchestrator and nothing in the workflow calls it yet, so your `/aidlc` runs are unchanged. No upgrade action required.

* The directive emitted by `bun .claude/tools/aidlc-orchestrate.ts next` now carries fully-resolved `consumes`/`produces` file paths instead of bare vocabulary names. A `produces` entry resolves under the directive's own stage (`aidlc-docs/<phase>/<stage>/<name>.md` for a non-per-unit stage); a `consumes` entry resolves under the stage that *produces* that artifact, because a consumed artifact lives in its producing stage's directory — so e.g. `application-design`'s consume of `requirements` resolves to `aidlc-docs/inception/requirements-analysis/requirements.md`, not under `application-design`. The five per-unit Construction stages (`nfr-requirements`, `nfr-design`, `functional-design`, `infrastructure-design`, `code-generation`, detected via their `for_each: unit-of-work` graph field) resolve to `aidlc-docs/construction/{unit-name}/<stage>/<name>.md`.
* A consumed artifact marked `conditional_on: brownfield` (or `greenfield`) is included only when it matches the `Project Type` recorded in `aidlc-docs/aidlc-state.md`; when the project type is unknown the engine keeps every entry. Path resolution and this filter both run in the engine (a deterministic tool), never delegated to the conductor.
