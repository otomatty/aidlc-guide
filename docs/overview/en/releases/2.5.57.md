## [2.5.57] - 2026-08-07

AI-DLC now speaks to you in your project's terms rather than its own. Three things a user reported all came from the same place: the assistant narrated its internals, hook names and messages described plumbing instead of purpose, and a new workflow opened with folders it was never going to use. Chat messages, approval gates, the composer's plan proposal, scope questions, error messages, and the onboarding doc are rewritten in plain developer terms; the sentences between steps are now written by the framework and relayed rather than improvised, with silence as the resting state; seven hooks and the intent-creation command are renamed to say what they do; and a record dir now contains only the phases your scope actually runs. Behavior is unchanged throughout: every stage, approval gate, audit event, and tool flag is identical, and the tests pinning those mechanics still pass.

**Upgrade:** re-copy your `dist/<harness>/` shell into the project. This is mandatory, not optional: the old hook files and their `settings.json` entries reference the old names, so a stale copy keeps using the old wiring. Kiro IDE users must first run the retired-hook cleanup in the [Kiro IDE install guide](https://github.com/awslabs/aidlc-workflows/blob/HEAD/docs/guide/harnesses/kiro-ide.md#install), because its overlay copy cannot delete old auto-discovered registrations and leaving them in place fires the old and new hooks together. Codex users additionally re-run the hook-trust pre-seed (`bun scripts/package.ts codex trust --project <abs-dir>`), because the trust hash covers the adapter command string and every renamed target changes it. An overlay copy can leave the retired, empty `tools/data/scaffold/` directories behind; they are harmless and can be removed manually. Existing intent records are untouched: nothing is ever deleted, so a record already carrying all five phase folders keeps them, and you can remove an empty one by hand if you want.

* Seven hooks renamed: `aidlc-audit-logger` to `aidlc-write-audit-log`, `aidlc-sync-statusline` to `aidlc-sync-workflow-state`, `aidlc-mint-presence` to `aidlc-record-human-turn`, `aidlc-runtime-compile` to `aidlc-rebuild-stage-graph`, `aidlc-stop` to `aidlc-continue-workflow`, `aidlc-dispatch-rules` to `aidlc-deliver-stage-rules`, `aidlc-sensor-fire` to `aidlc-run-sensors`. The other ten keep their names. On Claude Code the filename is the only label a waiting user sees, and `aidlc-sync-statusline` actively misled: it reconciles the Current Stage in `aidlc-state.md`, while the statusline is a separate hook that reads that file.
* `/aidlc --doctor` now reports heartbeats under the new hook names (for example `write-audit-log` rather than `audit-logger`), and the per-hook heartbeat and drop files under `.aidlc-hooks-health/` are renamed to match. The `.aidlc-stop-hook/` counter directory keeps its name so an in-flight workflow's no-progress counter is not orphaned.
* Kiro IDE registrations renamed: `aidlc-block` is now `aidlc-enforce-approval-gate` and `aidlc-mint` is now `aidlc-record-human-turn`. Every Kiro CLI and Kiro IDE registration now carries a plain-English description.
* Hook adapter target words follow the same vocabulary on Kiro CLI, Kiro IDE, and Codex (`stop` to `continue-workflow`, `mint` to `record-human-turn`, `block` to `enforce-approval-gate`, `pretool-block` to `guard-tool-call`, `state-sync` to `sync-workflow-state`, `runtime-compile` to `rebuild-stage-graph`, `dispatch-rules` to `deliver-stage-rules`). Old target words are not accepted: a hand-written registration or script that passes one is a no-op, so update it to the new word.
* `aidlc-utility intent-birth` is now `aidlc-utility intent-create`, and the workspace form `aidlc intent birth` is now `aidlc intent create` (matching `space create`). Scripts and CI that call the old name must be updated. Running the old name now tells you it was renamed and that the flags are unchanged, instead of printing the whole command list. An existing intent record named "birth" stays reachable via `intent switch birth`.
* Creating an intent now makes one artifact folder per phase the scope runs, plus `verification/` (created for every scope). A `bugfix` or `refactor` record has no `ideation/` or `operation/` folder at all; a `feature` or `enterprise` record still has all five. Previously a `bugfix` workflow opened with an empty `ideation/` and `operation/` beside the folders it would really use, reading as planned-then-abandoned work, while the audit trail already recorded the same decision as `PHASE_SKIPPED`. The folders created and the phases reported skipped now derive from one place, so they always agree.
* The `WORKSPACE_SCAFFOLDED` and stage-completion audit entries now report how many in-scope phase folders were created, instead of implying a fixed set.
* Removed `tools/data/scaffold/`, 26 empty directories shipped in every harness tree that no code read. Per-stage folders were never created up front and still are not: a stage's folder appears when it first writes an artifact. The user guide, CLI reference, orchestrator reference, and the Workspace Scaffold stage text said otherwise and are corrected.
* A "Talking to the user" voice contract now lives in the stage protocol every harness loads on every stage, so all five distributions inherit one voice. It governs wording only and states explicitly that mechanics, verbatim tool output, and audit vocabulary are unchanged.
* The sentences you read between steps are now written by the framework rather than improvised. Each instruction the workflow returns can carry the line that describes it, already worded in terms of your project, and the assistant relays that text instead of narrating what it just did. Where nothing is written for a moment, that moment passes in silence: no play-by-play, no naming the tool about to run, no reading a field back to you. The result is fewer sentences and more of them about your software. All five harnesses relay it identically.
* Entering a stage now says who is doing the work in ordinary job titles, not agent filenames: "The developer takes a look at the codebase first, then the architect builds on what comes back." The review step says what it is for ("Let me have the quality engineer check this over before you see it") rather than citing the protocol section that mandates it.
* The first thing said in a session is about your request rather than the framework starting up, and completing a workflow says your work is finished and written up.
* The welcome banner shown at session start describes scope in your terms: "Scope is set from your command, or auto-detected from what you describe" replaces "The orchestrator determines scope".
* The header on the rules delivered to each stage says what those rules are instead of which component resolved them, so an assistant quoting its own context back to you no longer quotes framework internals.
* The composer's plan proposal leads with a plain-language recommendation ("this looks like a small, well-understood change, so I suggest a short run") and the stage list, then shows the scores under a "Scoring detail (advisory)" heading. The scores, bands, and `method` line still appear in full, just below the recommendation instead of as the headline.
* Scope questions read plainly: a keyword match now asks "This looks like <name> work, so I'd run the <name> plan", and an unclear task says "None of the ready-made plans is an obvious fit" instead of "No stock scope clearly fits". The stage and gate counts and the `compose` affordance are unchanged.
* Error and refusal messages lead with a plain first sentence and keep the exact remedial command: the steering-token family, the stale-position and changed-route cases, the transport-budget warning, and the two autonomy refusals (which no longer mention the swarm). Blocked-action messages carry an `[aidlc]` prefix so a line on stderr is attributable. The refusal for changing stage status by hand explains that the workflow tools own it; the `set-status` refusal now tells you the status updates by itself and that `/aidlc --status` shows it. The creation summary says `Intent created:` rather than `Intent born:`.
* The onboarding doc (`CLAUDE.md` / `AGENTS.md`) opens with what AI-DLC does for you rather than a component inventory, and the sensors, tools, and hooks entries describe what they do in the reader's terms. `--help` wording for `compose`, `--new-scope`, and the auto-created workflow record is plainer.
* Approval-gate and completion templates ask in plain words (what was produced, what to look at, what happens next), the depth and test-strategy note explains itself, and the Bolt-planning questions drop the jargon while keeping Bolt and Unit of Work.
* Building a piece of your work now says so. Construction repeats the same stage once per unit, and those repetitions previously passed without any written line, so what filled them was the loop's own bookkeeping: which pass of the iteration it was, whether an approval gate had resolved, what a stage's output list came to. Each build pass now reads as one sentence naming the unit and the stage ("Now working on counter-core: the Functional Design pass"), and the pass that closes the stage says nothing because the approval gate follows immediately.
* "Bolt" is explained the first time you see it. Entering Construction now reads "Starting the first Bolt now: one build pass over the code, tests and checks for a piece of the work", and the delivery-planning questions and artifacts carry the same one-clause definition at first mention, for Bolt, walking skeleton, mob, Program Board, and any scoring model named by initials. Later mentions stay short.
* The walking-skeleton question in Practices Discovery asks something answerable: "Build a thin end-to-end slice first? A walking skeleton is a minimal version that runs the whole way through, built first to prove the pieces connect before the real features go in." It previously asked whether to "run the skeleton ceremony first", which was the framework's own phrasing for how it classifies your answer.
* The per-stage observation diary no longer opens by naming a framework component. Its first line, which appears in the diff every time a stage updates it, now reads "This file is kept up to date automatically while the stage runs."
* Loading a stage's rules no longer produces a sentence at all. The assistant was told not to print a progress message and wrote its own line in that slot instead ("Continuing to the stage directive", six times in one run); rule loading is not an event in your project, so no wording of it appears.
