## [0.5.0] - 2026-05-31

**The framework now learns from you, checks the work automatically, and is reshapeable without writing code.** Two things change for anyone running `/aidlc`: every approval gate now offers to capture what you corrected so the same correction is never needed twice, and deterministic checks (linter, type-check, required document sections, upstream coverage) fire automatically as agents write — an advisory second opinion you never have to ask for. The larger change is for harness engineers: stages, agents, scopes, rules, and sensors are all editable declarative files now, so you can reshape how AI-DLC behaves for your team by editing Markdown and JSON — no TypeScript. A new Harness Engineer Guide documents exactly that. Under the hood, this is the control-plane / data-plane cut: one compile at workflow start resolves rules and sensors per stage, and a runtime graph mirrors each run. This release also carries a **BREAKING** rename — every framework file now has an `aidlc-` prefix and the rules directory is flat (the `.claude/practices/` folder is gone). This entry consolidates the `0.4.1` → `0.4.13` patches; those headings stay below for historical reference.

**Upgrade.** Re-copy `aidlc-claude-code/.claude/` over your project's `.claude/`. Framework files now carry an `aidlc-` prefix and the rules directory is flat — re-target any customisations from `.claude/practices/` or `.claude/rules/aidlc/guardrails/` to `.claude/rules/aidlc-<scope>.md`, and rename hand-authored hooks that pin the old unprefixed hook filenames. The state template is unchanged from v0.4.0 (v7), so existing workspaces stay schema-compatible. A workspace mid-workflow with overlay customisations you can't easily re-target archives and re-inits per the pre-1.0 no-migration policy:

    mv aidlc-docs aidlc-docs-v04-archive && /aidlc --init --force --scope <scope>

**For everyone running `/aidlc`**

* **Gates now capture what you teach them.** Between a stage finishing and you approving it, the framework surfaces what the agent noticed during the stage — interpretations it had to make, places it deviated, tradeoffs it weighed — and asks "anything to add for next time?" You tick what is worth keeping and pick one of four headings; the framework saves it as a standing rule so the correction carries into the next workflow. Most stages surface nothing, which is healthy — the prompt only has substance when something genuinely came up. See [Rules and the Learning Loop](https://github.com/awslabs/aidlc-workflows/blob/HEAD/docs/guide/08-rules-and-the-learning-loop.md).
* **Automatic checks on every file write.** Four deterministic sensors — a linter, a type-checker, a required-sections check, and an upstream-coverage check — now run by themselves whenever an agent writes a stage's output. They are advisory: a finding leaves a note in the audit log pointing at exactly what is missing, but it never blocks your gate. The first time one fires in a workspace, a one-line banner points you at the guide.
* **`/aidlc --doctor --rule-drift`** flags where your team or project rules have drifted from the framework defaults — it quotes the conflicting default inline so you can review it. Advisory; it never fails the health check.
* **Architecture choices now get a written trade-off.** When a design decision has more than one viable approach, the design stage lays out Option A / Option B with reversibility and a recommendation tied to your non-functional requirements, then records the rejected alternatives in the ADR.
* **Richer post-compaction recovery.** A fresh session after a compaction can reconstruct more of where a workflow was, by reading the artifact tree, each stage's observation diary, the audit log, the state docs, and the new runtime graph.

**For harness engineers — reshape AI-DLC without code**

* **A new [Harness Engineer Guide](https://github.com/awslabs/aidlc-workflows/blob/HEAD/docs/harness-engineering/00-overview.md)** (`docs/harness-engineering/`, 8 chapters) is the headline. It walks through every change you can make by editing declarative files rather than TypeScript: the anatomy of a stage, adding a stage, adding an agent, defining a scope, authoring rules, authoring sensors, and giving agents team knowledge.
* **Rules are flat, layered Markdown you can read and edit.** `.claude/rules/aidlc-{org,team,project}.md` plus a file per phase. Scope comes from the filename — no `scope:` field. Resolution is **strict-additive**: every applicable rule from org → team → project → phase reaches the agent, nothing is silently overridden. The old `enforcement:` / `overrides:` keywords are gone; conflicts are caught when a rule is written, not hidden at runtime.
* **Sensors are authorable, and stages choose which ones fire.** A sensor is a small Markdown manifest under `.claude/sensors/` describing a check and how to run it. It says nothing about which stages use it — a stage imports the sensors it wants through a `sensors:` list in its frontmatter. Author a manifest, add its id to a stage, and the check rides along on that stage's file writes. The four shipped sensors are the worked examples.
* **The learning loop can wire a sensor in for you.** When a captured learning is "this stage should always run check X," the framework scaffolds the sensor manifest and adds it to that stage's `sensors:` import in one step.
* **Stages, agents, and scopes stay declarative.** A stage is a Markdown file with a frontmatter contract (what it consumes, produces, and which agent leads it); an agent is a persona file; a scope is an entry in `scope-mapping.json` deciding which of the 32 stages run for a kind of work. Editing any of them is a data change, documented end-to-end in the new guide.

**For developers — under the hood**

* **Control plane.** `aidlc-graph.ts compile` walks `.claude/rules/` and `.claude/sensors/` at workflow start, resolves the five-layer chain per stage, and bakes `rules_in_context` + `sensors_applicable` into every node of `stage-graph.json`. Runs under `withAuditLock` with atomic temp-rename writes. The `enforcement:` / `overrides:` keywords are removed; admission-time conflict checks (practices-discovery, the learning gate) replace runtime override resolution.
* **Data plane.** A new tool, `bun .claude/tools/aidlc-runtime.ts` (`compile` / `read`, plus `fragment-fork` / `fragment-merge` for parallel Construction Bolts), materialises a per-workflow `runtime-graph.json` by walking `audit.md` + per-stage `memory.md`. A PostToolUse hook recompiles it deterministically after every gate/transition write.
* **Sensor dispatch.** `bun .claude/tools/aidlc-sensor.ts` (`list` / `describe` / `fire`) routes to the four per-sensor scripts; the `aidlc-sensor-fire.ts` PostToolUse hook reads the active stage's `sensors_applicable` and fires the matching sensors on Write/Edit.
* **The learning gate is a tool.** `bun .claude/tools/aidlc-learnings.ts` (`surface` / `persist`) reads a stage's `memory.md`, emits candidates for the orchestrator's AskUserQuestion, and writes confirmed learnings to `.claude/rules/aidlc-{project,team}-learnings.md` — plus the two-write sensor bind — inside one `withAuditLock`.
* **Two new framework hooks (7 → 9):** `aidlc-sensor-fire.ts` and `aidlc-runtime-compile.ts`.
* **Test coverage for the learning-gate call seam.** `t86` now also pins the `SKILL.md` Stage-Advancement wiring that makes the orchestrator actually invoke `aidlc-learnings.ts surface` + `persist` at a gate (TEST_RUN_MODE-guarded), plus the Test-Run-block skip declaration — closing the gap where the tool (`t97`/`t99`) and the §13 prose (`t86`) could both pass while the orchestrator never called the gate.
* **Audit taxonomy 55 → 61 events.** Five sensor slots pre-registered, `MEMORY_EMPTY` for silent-diary detection, four `SENSOR_*` emitters wired, `RULE_LEARNED` + `SENSOR_PROPOSED` for the learning gate, and `GUARDRAIL_LOADED` for the doctor coverage row. The dead guardrail-*learning* subsystem (`GUARDRAIL_TRIGGERED` / `GUARDRAIL_LEARNED`, `aidlc-guardrail.ts`) was retired, netting 61. If you grepped audit logs for the two retired events, those rows are no longer emitted.
* **BREAKING — `aidlc-` filename prefix + flat rules layout + practices folder removed.** Every framework-shipped file under `.claude/` (tools, hooks, agents, knowledge directories) carries an `aidlc-` prefix. `.claude/rules/aidlc/{guardrails,phases}/` flattens to `.claude/rules/aidlc-{org,team,project,phase-<phase>}.md`; `.claude/practices/` is removed (team config now lives in `.claude/rules/aidlc-team.md`). `aidlc-knowledge/` becomes `knowledge/` with `aidlc-<role>-agent/` and `aidlc-shared/` subdirectories.
* **Documentation + install.** Docs are split three ways by reader — User Guide, Harness Engineer Guide, Developer Reference — all linked from the README. Install switched to Claude Code's native installer, Getting Started gains a full AWS Bedrock Setup section, and the shipped `.claude/settings.json` now sets `AWS_REGION`.
* `aidlc-claude-code/.claude/tools/aidlc-version.ts` — bumped 0.4.13 → 0.5.0.
