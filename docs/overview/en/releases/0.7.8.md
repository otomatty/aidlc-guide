## [0.7.8] - 2026-06-16

Stops the interactive `/aidlc` Stop hook from spamming the forwarding-loop nudge while you are answering a gate. When the conductor parks at an approval gate or in the Request-Changes loop, it ends its turn waiting for you — but the engine still reports the stage as in-flight, so the forwarding-loop Stop hook used to block the stop and re-inject the "you haven't finished the forwarding loop" nudge repeatedly until its 8-block cap bled out. The hook now reads the current stage's checkbox state and **allows** the stop when the stage is awaiting approval (`[?]`) or being revised (`[R]`) — the two states that exist only because the workflow is waiting on you. This is a positive-confirmation, fail-open carve-out: it only ever releases the stop more readily, never blocks more; a genuine mid-stage quit (or any other state) still falls through to the existing cap-bounded block. One core edit fixes the Claude and Kiro (and Codex) harnesses; re-copy your `dist/<harness>/` to pick it up.

* **Interactive approval gates and the Request-Changes loop no longer emit the repeated forwarding-loop nudge.** Previously up to ~8 "Stop hook" nudges could appear at a single gate while you typed your answer; now the hook allows the stop as soon as it sees the stage is awaiting approval or being revised.
* **Known follow-up — a mid-stage clarifying question still relies on the cap.** A question asked *before* the gate leaves the stage `[-]` in-progress, which is indistinguishable from a lazy mid-stage quit by checkbox state alone, so it is deliberately NOT carved out (a blanket `[-]` carve-out would gut the hook). The safe fix needs an engine-side "question pending" signal and is tracked as a follow-up. Immediate mitigation for either case: set `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP=1` (or `=2`) in `.claude/settings.local.json` `env` (or export it) to collapse the spam to a single nudge.
* No CLI surface change; no new commands or flags. The recursion bounds (`stop_hook_active`, the no-progress counter, and `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`) are unchanged.
