## [0.3.13] - 2026-05-19

Workshop-mode docs. New chapter `docs/guide/workshop-mode.md` documents the multi-developer manual recipe for running the `workshop` scope: each participant clones the shared remote, runs `aidlc-worktree create --slug <slug> --base <per-team-practices>` locally, then publishes the claim by pushing `bolt-<slug>` to origin (first push wins, late claimants get a non-fast-forward rejection). The recipe uses only primitives that already ship today — `aidlc-worktree create/discard`, `aidlc-bolt complete --merge`, plus ordinary `git push` — so no new CLI, audit events, or state changes. The chapter aligns with practices-aware orchestration: walking-skeleton stance, branching strategy, and merge target are all read from the team's affirmed `practices/team.md`, not chosen on the command line. Multi-failure halt-and-ask with `Merge-Held` survivors, batch-level gates, the `MERGE_DISPATCH_*` audit trail, and resume semantics are all documented as the user-facing surface. A future release may automate slug claiming once a real workshop dogfood surfaces a concrete requirement; until then, the recipe is the contract. Linked from `docs/guide/00-introduction.md`'s Guide Map.

* `docs/guide/workshop-mode.md` is the new chapter — claim semantics, facilitator setup, participant flow, 2-developer 3-Bolt worked example, multi-failure halt-and-ask with `aidlc-bolt hold-merge` / `release-merge` enforcement, `MERGE_DISPATCH_*` audit forensics, workshop resume semantics via `aidlc-worktree info --slug`'s `merge_held` field
