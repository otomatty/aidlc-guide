# aidlc-workflows 2.11.1

[更新履歴一覧](../changelog.md) · [改善点の日本語ガイド](../release-highlights.md)

## [2.11.1] - 2026-10-20

互換性: スクリプトに影響する変更があります

AI-DLC 2.11.1 は、2.11.0 以降にマージされた利用者に見える変更をまとめたリリースです。主な変更は次のとおりです。

- git worktree、入れ子のチェックアウト、clone に置いたコードも、Code Generation の承認まで届くようになりました。
- Guard Policy が off の場合、チャットが圧縮された後もビルドが続きます。
- 開いている Code Generation のゲートからの後戻りのジャンプは、最初の依頼で通ります。
- エージェントを一時停止した本人を、先へ進むよう促しません。
- プラグインは作者自身が付けた名前を持ち、更新をまたいで同じ場所に残る一つの AI-DLC カタログを共有し、Cursor と Kiro IDE では Bun なしで構成されます。
- 2.8.0 以降のどのリリースのプロジェクトも、止まらずに更新できます。
- 計画の質問、ゲート、再開と新しいチャット、Construction、すべてのハーネスで修正を行いました。

**更新方法:**

- `aidlc update` を実行してから、各プロジェクトで `aidlc config --yes` を実行し、ハーネスのランタイムを更新します。
- 複数のハーネスがあるプロジェクトでは、ハーネスごとに `aidlc config --harness <name> --yes` を実行します。
- 進行中の作業は更新の後もそのまま続きます。
- 手動コピーの利用者は、`aidlc-copy-runtime-2.11.1.tar.gz` の `runtime/<harness>/` ツリー全体を置き換えます。

**Claude Code または Codex で AI-DLC のプラグインを使う場合（この利用者だけに必要な手順）:**

- AI-DLC のプラグインカタログを、新しいフォルダーから一度だけ追加します。`/plugin marketplace add <folder>` または `codex plugin marketplace add <folder>` を使います。
- 追加するフォルダーは次のとおりです。
  - ネイティブ導入: インストーラーが表示し、`aidlc doctor --verbose` が示すフォルダー（`~/.local/share/aidlc/plugins`、Windows では `%LOCALAPPDATA%\aidlc\plugins`）。2.11.0 の `aidlc update` で更新した場合は、`aidlc use 2.11.1` を一度実行してこのフォルダーを作成します。
  - コピーしたプロジェクト: ランタイムの `plugins` フォルダー。
- 他の人が作ったプラグインは、その作者が再ビルドした後で新しい名前でインストールし、`/aidlc plugin list` が示す古い `aidlc-<name>@aidlc-plugins` のコピーを削除します。
- 2.11.0 のフォルダーから追加したプラグインは、後の更新でそのフォルダーが削除されるまで動作し続けます。
- プラグインをビルドまたはインストールするスクリプトについては、「スクリプトに影響する変更」（`Breaking for scripts`）の項目を参照してください。

* Claude Code、Codex CLI、GitHub Copilot、Cursor、Kiro CLI、Kiro IDE、opencode の `aidlc version` が `2.11.1` を表示します。
* Code Generation の承認の質問は、プロジェクト自身の git から見えない場所にコードがある場合も開くようになりました。
  * 対象: 子フォルダーまたは `.worktrees/` 配下の worktree、プロジェクトの外に置いたリポジトリの worktree をプロジェクト内の gitignore されたフォルダーに配置したもの、clone、サブモジュール、モノレポのパッケージ、別の場所にあるチェックアウトへのジャンクションやリンク、作業の開始後に追加した worktree、記録より前にコミットされたコード。
  * レビューからコードが見えない場所（`.claude/worktrees/<name>` のようなハーネスのフォルダー内の worktree、プロジェクトの外、別のドライブ）では、先へ進めない拒否の代わりに、質問の中で一度だけ `AI-DLC found no source changes under <where it looked>` と伝えます。本人はいつもどおり承認するか、変更を求めます。
  * strict または relaxed では、エージェントの最初の報告を、先へ進む方法を添えて一度だけ拒否し、次の報告で同じ質問を開きます。拒否が残るのは、誰もゲートに答えない場合（自律実行の Construction、在席確認がオフ、無人の実行）だけです。
* Guard Policy が off の場合（`enterprise` を除くすべての同梱スコープの既定）の変更は次のとおりです。
  * ビルドの途中でチャットが圧縮されても、エンジンの言葉で拒否せず、記録済みのビルドステップ（書き込み、コマンド、ブリーフ、開発者への引き継ぎ）のまま続けます。
  * 再レビューが完了しなかった Unit は、それより前の準備完了のレビューでゲートを開きます（relaxed でも同様です）。
  * 食い違う二つの Guard Policy の行（2.10.0 より前のリリースでチームメイトが書いたものなど）は一つにまとめます。どちらが後に設定されたかを記録から判断できない場合にだけ、その旨を一行で示します。
* 開いている Code Generation の承認の質問で、前のステージへ戻ることや、そのステージのやり直しを求めると、どの Guard Policy でも最初の依頼で通ります。
  * これまでは、エンジンの言葉で拒否され、質問が再び表示されていました（Kiro CLI ではこれが Request Changes として読まれ、新しい試行が始まっていました）。
  * GitHub Copilot では従来どおり、最初の依頼は一度拒否され、次のステップでその依頼を実行します。
* 本人が自分の言葉でエージェントを一時停止した場合（「ちょっと待って」「今日はここまで」）、AI-DLC のターン終了時の行がそれ以上先へ促すことはありません。
  * 実行がどれだけ長くなっても、エージェントが続けるか、一時停止するか、休憩するかを尋ねることはありません。本人はいつでも止めると言えます。
  * 作業を保留すると、作業の現在地と戻り方を示します: `Paused at <Stage> with everything saved. Pick it back up any time here, or with /aidlc --resume in a new chat.`
* 他の人が作ったプラグインは、Claude Code と Codex で作者が選んだ名前で表示されるようになりました。
  * 名前はマニフェストの `name` で、カタログは新しい任意のフィールド `"aidlc": {"marketplace": "<name>"}` で名付けます（省略時はプラグイン自身の名前）。そのため、二つのチームのプラグインを並べてインストールできます。
  * AI-DLC 自身のプラグインは `aidlc-<name>@aidlc-plugins` のままです（test-pro は `aidlc-test-pro@aidlc-plugins` のままで、2.11.0 から内容が変わったため 0.1.1 になりました）。
  * `aidlc plugin validate` と `aidlc plugin build` は、`aidlc` という名前、または `aidlc-` で始まる名前のカタログを、大文字・小文字を問わず拒否します。
  * 古いコピーと再ビルドしたものの両方がインストールされている間は、AI-DLC は再ビルドしたものを使います。`plugin sync`、`plugin list`、doctor は、古いコピーを削除するコマンド（`/plugin uninstall aidlc-<name>@aidlc-plugins` または `codex plugin remove aidlc-<name>@aidlc-plugins`）を示します。
* AI-DLC 自身のプラグインは、一度追加すればよい一つの `aidlc-plugins` カタログを共有します。
  * ネイティブ導入では、このカタログは `aidlc update`、`aidlc use`、`aidlc rollback` をまたいで同じ場所に残るフォルダーに置かれます（`~/.local/share/aidlc/plugins`、その環境変数が設定されている場合は `$XDG_DATA_HOME/aidlc/` 配下、Windows では `%LOCALAPPDATA%\aidlc\plugins`）。そのため、そこから追加したプラグインが二回後の更新で読み込まれなくなることはありません。
  * インストーラーはそのパスを表示し（`Plugin marketplace for Claude Code and Codex: <path> (add it once; updates keep it current)`）、`aidlc doctor --verbose` は Machine の下にそのパスを示します。
  * Codex では、プラグインのフォルダーをマーケットプレイスとして追加し、そのカタログは `.agents/plugins/` の下に置かれます。
* Kiro では、プラグインを `cp -r <projection>/.kiro <project>/` で配置すると `.kiro/aidlc-plugins/<name>/` に置かれるようになりました。そのため、二つ目のプラグインが一つ目を上書きすることはありません。このリリースより前に配置したプラグインは、その場所のまま動作し続けます。
* Cursor にインストールしたプラグインや Kiro IDE 向けに配置したプラグインは、ネイティブ導入であれば Bun なしでセッション開始時に構成されるようになりました。
  * 2.11.0 でビルドしたプラグインは Bun 専用のセッション開始フックを持ったままです。そのため、作者がこのリリースで再ビルドし、本人が再インストール（Cursor）するか新しいプロジェクションを配置（Kiro IDE）するまでは、引き続き PATH 上に Bun が必要です。
* プラグイン作者向けの変更は次のとおりです。
  * `aidlc plugin validate` と `aidlc plugin build` は、すべてのハーネスでネイティブに動作します。
  * チームのプラグインは、ベースのエージェントにステージを主導させることができ（`aidlc plugin validate --with <base root>` で確認します）、スコープの `include_stages` でベースのステージを名前で実行できます。
  * チームのプラグインはベースの後に構成され、ベースがオフの間は一時停止します。
  * コントリビューションは、コアのペルソナに文章を追加したり、ステージを必須にしたり（`adds.requires_stage`）できます。
  * ビルドは、別のユーザーが `/tmp` に残したロックフォルダーを無視します。
* スクリプトに影響する変更: `aidlc plugin validate` と `aidlc plugin build` は、ステージが別のプラグインのステージやエージェント（`requires_stage`、`lead_agent`、`support_agents`、`reviewer`）を名指ししているのに、そのプラグインが `dependencies` にないプラグインに対して、終了コード 1 で終わるようになりました。2.11.0 では、同じプラグインの検証とビルドが通っていました。エラーは直し方を示します: そのプラグインを `dependencies` の `"core"` の隣に（`"<base>@^1.2.0"` の形で）追加するか、名前を修正します。
* スクリプトに影響する変更: AI-DLC が同梱しないプラグインの `aidlc plugin build` は、ホストのプラグインをマニフェストの `name` で、カタログを `aidlc.marketplace`（省略時はプラグインの名前）で名付けるようになり、`aidlc-plugins` の中の `aidlc-<name>` ではなくなりました。ビルドの出力を `aidlc-<name>@aidlc-plugins` としてインストールするスクリプトは、`<name>@<catalogue>` としてインストールする必要があります。
* スクリプトに影響する変更: プラグイン自身のフォルダー（チェックアウトでは `dist/plugins/<name>/<harness>`、コピー用ランタイムでは `plugins/<name>/<harness>`）には `marketplace.json` が含まれなくなりました。2.11.0 の test-pro の README が示したようにそのパスで `/plugin marketplace add` や `codex plugin marketplace add` を実行するスクリプトは、代わりに `plugins` フォルダー（ネイティブ導入では前述のカタログのフォルダー）を追加する必要があります。Codex では、その場で置き換えたフォルダーについて、その一度の追加を行うまで `codex plugin list` が `marketplace root does not contain a supported manifest` と表示します。
* プラグインは構成されたまま残ります。
  * アップグレード（失われたものは sync が戻します）、プラグインの更新後の `aidlc config`、二つのセッションの同時開始、Kiro CLI から Kiro IDE への切り替え、Windows の改行コードのチェックアウトで、プラグインが追加したものが失われなくなりました。
  * `plugin select` や `aidlc config` でプラグインやそのベースをオフにすると、それが追加したものを取り除きます。オンに戻すと、どのように戻るかを示します。
  * プラグインの sync へ案内する行はすべて、Kiro CLI と opencode を含め、本人のツールで動くコマンドを示します。
* 2.8.0 から 2.11.0 までのどのリリースのプロジェクトも、構成済みのプラグインを含めて、止まらずにこのリリースへ更新できます。完了済みのステージの動作を変える更新でも、そのステージのやり直しを求めることはありません。更新後の行は更新の手順を示し、進行中の作業が続くことを伝えます。
* `aidlc update --channel preview` はリリース一覧をページ単位で読むようになり、一覧が 1 MiB を超えても動作し続けます。2.11.0 自体では、このコマンドは `exceeds the 1048576 byte download limit` で失敗します。`aidlc update --version <id>` で回避できます。
* `install.sh` と `aidlc uninstall` は、root しかユーザーがいないコンテナーや CI ジョブ向けに、明示的に指定する `--allow-root`（または `AIDLC_ALLOW_ROOT=1`）を受け付けます。
  * 指定しない場合や `sudo` の下では、引き続き root を拒否します。
  * プロジェクトの `.env` ファイルは、エンジンやエンジンが起動するツールに届かなくなりました。ネイティブのエンジンは、プロジェクトの bunfig の preload を実行しません。
* 初回のセットアップの変更は次のとおりです。
  * Kiro の選択肢を「Kiro CLI (V2)」と「Kiro」として示し、Enter で Kiro CLI (V2) を選びます。
  * 選んだプリセットは、ハーネスを変えて元に戻しても保持されます。
  * AI-DLC のステータスラインを使うかどうかは本人が選び、一度だけ尋ねます。本人の設定を断りなく置き換えることはありません。
* `aidlc config` の変更は次のとおりです。
  * 更新では、モデルや effort を設定するために編集したエージェントファイルを上書きせずに止まります。AI-DLC にすでに触れているチームの `AGENTS.md` は保持し（AI-DLC のブロックをその後に追加します）、UTF-8 でないルートのファイルは変更せずに名指しします。リポジトリの fsmonitor プログラムは実行しません。
  * 競合が起きた場合は、`--force` を付けて実行する正確な config コマンドを示し、すでに同意したダウンロードも引き継ぎます。
  * 別のフォルダーからプロジェクトのコマンドを実行した場合は、`aidlc` の直後にプロジェクトのフォルダーまたは `--project-dir` を指定する形を示します。
  * `aidlc config set|get|list` が端末上で動作します。どのファイルにも記録されていないスイッチを解除すると、その旨を伝えます。戻し方はどこでも一つの形で示します。
  * チェックを記録していないファイルでそのチェックをオンに戻すと、どのファイルがそれをオフにしたままにしているかを示します。
* `/aidlc --status` と doctor の変更は次のとおりです。
  * `/aidlc --status` は、何も選択していない clone で進行中の作業をそれぞれ名指しし、表示されたステージだけを数え、Unit の正確なステップを示します。一時停止中や完了済みの作業はそのとおりに読み取り、戻り方を示します。
  * doctor は、返答が記録されていないときに警告し、Agent Hooks でオフにした Kiro のフックを名指しします。git がないことを古いブランチとして報告しなくなりました。
  * Kiro では、2.11.0 から配置したプラグインがあっても、信頼の行が合格し、Kiro IDE への切り替えも通ります。
* 計画の質問の変更は次のとおりです。
  * 計画の質問は、作業を始める前に本人の返答を待ちます。本人のメッセージが AI-DLC に届かなかった場合も同じです。
  * 質問を出すきっかけになったメッセージで本人が求めた変更は、本人の回答として読み取ります。
  * Code Generation は承認済みの計画からだけ完了します。承認後に AI-DLC を更新しても、再び尋ねることはありません。
  * 計画を待つ間も、読み取り、スキャン、テストの実行、AI-DLC 自身のコマンド（本人が求めた更新を含む）は実行されます。
  * 承認のステップでは、ビルドで除外したものを示します。「それでもビルドして」は本人の言葉で伝えても動作します。
  * カスタム計画を承認すると、そのコマンドに空の `--skip` や `--add` が含まれていても計画を作成します。
* ゲートの変更は次のとおりです。
  * エージェントは記録済みのレビューから、止まらずに承認の質問へ進みます。
  * 各ステージの開始時に、全体の何番目のステージかを示します。
  * レビューのブロックは、前回のレビュー以降に変わった内容だけを示します。完了しなかったレビューは、その旨を一度だけ伝えます。
  * レビューの回数を使い切った後に作業が変わった場合は、もう一度の確認を提案します。
  * 要約の確認は作成するファイルだけを示し、「なぜ今か」の行はなくなりました。
  * ステージ自身の質問の時点や実行中にそのステージのスキップを求めると、スキップし、再び実行するコマンドを示します。一つのメッセージで承認とスキップを入力した場合は、どちらも一度ずつ実行します。
* 本人の言葉の読み取りの変更は次のとおりです。
  * 新しいチャットで、Unit またはバッチのチェックポイントに「2」と答えると Request Changes になります。
  * 「Functional Design をスキップして残りを承認」は、残りの承認も行います。
  * 新しいチャットで `/aidlc` だけを入力すると、尋ねられたまま答えていない質問を再び尋ねます。
  * 本人の言葉から答えた質問は、何を読み取ったかを示します。
  * プロジェクトの種類の変更は、そのもとになった言葉を示します。作業を始めたメッセージで既存のコードだと伝えた場合は、再び尋ねません。
  * 本人の返答の後に記録された質問は、回答が失われたと言う代わりに、その旨を伝えます。
* 二つのチャットと新しいチャットの変更は次のとおりです。
  * 作業ごとに選択を保持するので、二つのチャットが互いの選択を上書きすることはありません。
  * 新しい clone の保留中の作業は、二度目の再開なしで続きます。
  * 完了した作業に関する言葉には、完了済みであることと戻り方を示します。
  * 作業に参加していないチャットには、参加の手順を示します。
  * 一つのチャットで尋ねた検証コマンドの質問に、新しいチャットから答えられます。
  * 本人の `/aidlc` の行によって、進行中の作業を再開するか、本人の言葉で新しい作業を始めるかが決まります。
* Construction の変更は次のとおりです。
  * Unit が二つ以上の計画では、Inception の終わりに一度だけ、誰がビルドするか（Just me、または Several teams）を尋ねます。
  * 並行のバッチを取り込み（兄弟リポジトリでの競合は場所を示したうえで取り込みを完了します）、承認済みのテストを再び尋ねずに実行します。
  * 「一つずつビルドして」と伝えると、各 Unit を承認済みの計画からビルドします。
  * 最初のチームのステップでは、Unit ごとに一つの承認を提案します。
  * AI-DLC のすべての git 呼び出しは本人の git の設定（フック、LFS、マージドライバー、ファイルシステムモニター）で実行し、Unit はチームが指定した統合ブランチに取り込まれます。
  * 兄弟リポジトリを作業の途中で追加・削除できます。
  * 再び開いた計画がループしなくなりました。
  * 検証の質問は、実行しないテストとその理由を示し、コードの要約には実行しなかったテストを一覧にします。
  * `.aidlc-source-paths.json` でマシンローカルのツリーを除外できます。
  * `node_modules` などのパッケージマネージャーのフォルダー、および `.idea`、`.codegraph`、`DerivedData` は、ソースの境界の外に置かれます。
* Build and Test とチェックの変更は次のとおりです。
  * 理由を添えて N/A とした要件や、ユーザーストーリーを通じてビルドした要件を、未ビルドとして報告しなくなりました。
  * トレーサビリティは、親の下のサブ要件をたどります。
  * ステージ全体を読むチェックは、一度だけ報告します。
  * Bun のないネイティブ導入では、黙って合格にせず、プロジェクト自身の TypeScript を型チェックします。
  * TypeScript の ESLint 設定や、どのメジャーバージョンの ESLint でも、実際のリントの判定が出ます。
  * Requirements Analysis は、インテントステートメントとスコープ文書があればそれを引用します。
  * 生成したテストは、プロジェクト自身の型とスキーマからデータを組み立てます。
* Deployment Execution は、AWS CLI がインストールされていれば、デプロイを求める前にエージェント自身のシェルから AWS の ID を確認します。失敗した場合は、エラーと直し方を添えた一つの質問をし、確認に合格してからデプロイします。
* 本人が切り替えるチェックの変更は次のとおりです。
  * チェックをオフにするとすぐに適用し、すべての場所でオフにするかを提案します。
  * オンに戻すと、本人のローカルの上書きを解除してその旨を伝えます。チームのコミット済みの設定ファイルは変更せず、まだオフにしたままの設定を示します。
  * 引き継ぎの欠落、遅れて入ったソースの変更、レビューの上限は、本人への質問ではなくエージェント自身のステップです。
  * Kiro CLI と Kiro IDE では、push や再帰的な削除は拒否ではなく事前に確認します。
* 計画とスペースの変更は次のとおりです。
  * 計画の提案は計画の大きさを示し、ほかの計画を一覧にします。提案した計画は、作業を Unit に分けるかどうかを示します。
  * 計画名だけを入力すると、何のための作業かを尋ねます。
  * 新しい質問ファイルは、各質問に誰が答えるかを示し、職種ごとの質問をまとめます。
  * 新しいスペースや、フェーズの規則が出荷される前に作成したスペースにもフェーズの規則が入り、最初のステージが始まります。
  * スペースを切り替えると、追跡対象のインクルードを書き換えるのではなく、git で無視されるメソッドのコピーを書き出します。
  * スコープのガイドでは、`express` または `bugfix` にステージを加えて小さな変更を始める方法と、学習と要約の確認をオフにして計画を始める方法を示します。
* Claude Code と Codex の変更は次のとおりです。
  * `/aidlc --help` には、先にコマンドを実行せず、プロンプトのフックが答えます。ツール呼び出しやシェルコマンドの前のチェックは、一つのフックプロセスで実行します。
  * Claude Code では、作業を続ける行が Stop hook error ではなく Stop hook feedback として表示されます。
  * Codex では、一つのターンの中で数秒後に同じ言葉で再入力した返答（ターンが閉じる間の二度目の `1`）を、重複配信として捨てずに本人の返答として記録します。
  * Codex では、進展のないまま Stop フックが保持し続けるターンを、最初のブロックを再表示せずに上限で解放します。
  * Codex では、並行ビルドのワーカーを、承認設定が "never" の場合も含めて、許可を求めずに Codex のサブエージェントとして起動します。
  * Codex では、フックのリプレイキャッシュをプロジェクト内に、サイズの上限付きで置きます。
  * Codex では、2.11.0 からコピーしたプロジェクトが自身のツールで更新され、`config.toml` は変更されません。
* GitHub Copilot、Cursor、opencode の変更は次のとおりです。
  * GitHub Copilot は四つのガードチェックを一つのフックプロセスで実行するため、許可の確認が五回ではなく一回で済みます。`/aidlc` の後に入力した言葉が作業に届きます。ヘッドレスの `copilot -p` の実行に必要なのは、信頼済みのフォルダーだけです。
  * Cursor のネイティブのセットアップは、プロジェクトのルートに AI-DLC のファイルを残しません。クラッシュしたガードは何も拒否しません。
  * Copilot と Cursor では、`aidlc config models --check` は doctor と同じように、共有の effort 設定をセッションに任せます。
  * opencode では、一つのウィンドウの二つのチャットがそれぞれ自分の作業を扱います。`/aidlc` コマンドは opencode の 50 KiB の切り詰めを超えてスキル全体を運びます。チームの `opencode.jsonc` に AI-DLC の項目が追加されます。確認を求めるのは、再帰的な削除や push の前だけです。
* Kiro CLI の変更は次のとおりです。
  * Kiro の 3.0 へのアップグレード後も、AI-DLC 自身のコマンドは事前に許可されたままで、そのエージェントは Kiro CLI 2 が許可するものだけを書き込みます。
  * AI-DLC のチャットとその専門エージェントは、本人が追加した MCP サーバーを、呼び出しのたびに確認したうえで使います。config は `.kiro/settings/mcp.json` を保持します。
  * エージェントの選択画面の先頭に `aidlc` が表示されます。
  * エージェントは保存したモデルで始まります。
  * 起動しないヘルパーがステージを一時間止めてしまう場合に、本人の設定で Kiro のヘルパーのアイドル期限（`api.subagentTimeout`、既定は 3600 秒で、AI-DLC は設定しません）を下げる方法を、Kiro CLI のガイドで説明しています。
  * Windows では、`& | < > ^` やアポストロフィを含む語がそのままエンジンに届きます。
* Kiro IDE の変更は次のとおりです。
  * エージェント個別のモデルと effort、および自分の Unit だけを読む Unit レビュアーが、既定で適用されます。
  * コード計画を書く間に MCP の参照を実行します。
  * 計画名だけを入力すると、Default エージェントで最初のステップを始めます。
  * フックのカードは、メッセージ、書き込み、コマンドごとに一つ表示します。
  * 「はい」と答えると、Kiro IDE の Workflows が実際にオフになります。
  * Windows では、PowerShell やコマンドプロンプトが書き換えてしまう依頼も、変更されずにエンジンに届きます。コマンドプロンプトでのセットアップには、PowerShell への一度だけの切り替えを提案します。
* Windows では、別の OS で承認した Unit も承認済みのまま残り、Windows の改行コードのチェックアウトでもすべての承認が保持されます。センサーのスクリプトはツールのフォルダーに留まり、インストール中に開いている IDE には、終了して開き直すよう伝えます。
* `aidlc engine` のサブコマンドに `--help` を付けると、エラーではなくそのフラグを表示します。
* ガイドの変更は次のとおりです。
  * Getting Started は、何もない状態からの実際の一回の実行を、すべての画面を収めて示します。
  * 日常の操作、Core Concepts、CLI Commands のページは、現在の AI-DLC が表示する内容を示します。
  * インストールガイドは、以前のバージョンに戻す方法を説明します。
  * インストールのページは、Bun と Node.js が不要であることを示します。
