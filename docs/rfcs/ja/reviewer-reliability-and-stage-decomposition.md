# RFC: レビュアーの信頼性とステージ実行の分解

**ステータス:** チーム議論のためのドラフト
**著者:** AWS Labs
**範囲:** `core/` のオーケストレーションエンジン、ステージプロトコル、ハーネスの SKILL.md ループ
**関連:** 2.0.0 のレビュアー機構（#383）、0.7.12 のグラフコンパイル修正

---

## 1. 問題

ステージは、本文が成果物を生成した後に品質ゲートとして走る `reviewer` サブエージェントを
宣言できます。しかし実際には**レビュアーが確実には発火しません** — ときには完全に
飛ばされ、エラーも痕跡も残りません。

データの配管は健全ですが、*呼び出し*がそうではありません。レビュアーは、大きな
`run-stage` ディレクティブの中の 1 行の散文の指示であり、エンジンの中にそれを強制する
ものも、記録するものも、承認ゲートをそれに依存させるものもありません。勤勉なモデル
（Opus 4.8）はたいてい実行しますが、より弱いモデルや、長い文脈では静かに落とします。
これは「コンダクターがすべての回答タグを事前に埋めてしまい、停止フックがまだ待機中だと
判別できなかった」のと同じ失敗の種類です — **荷重を担う手順が、機械的に強制されるのでは
なくモデルの判断に委ねられている**のです。

この RFC は 2 つのトラックを提案します。

- **トラック 1（戦術的、低リスク）:** ディレクティブを再構成せずに、レビュアーを
  *強制可能で観測可能*にします — 監査イベントの対と、ゲートの前提条件です。信頼性を
  ただちに出荷でき、トラック 2 と前方互換です。
- **トラック 2（構造的、本当の修正）:** 一枚岩の `run-stage` ディレクティブを、その
  内在する 3 つのフェーズ — **質問する → 成果物を生成する → レビューする** — へ分解します。
  それぞれがエンジンの出力するディレクティブとなり、自分のターン境界・監査イベント・強制を
  持ちます。レビュアー*だけでなく*、「モデルが小さな手順を飛ばした」というバグの種類全体を
  一様に修正します。

---

## 2. 現在のレビュアーの仕組み（実装どおり）

一言でいえば、**レビュアーはコンパイルで焼き込まれた*データ*であるのに、散文が駆動する
*動作*である**ということです。*どの*レビュアーか、*何回*反復するかは、すべてコンパイル時に
検証され、ディレクティブとしてコンダクターまで届きます。しかし*それを呼び出すという行為*
は、モデルが実行してくれると信頼された、散文のチェックリストの中の 1 文です。データプレーンは
隙がなく、制御プレーンは提案にすぎません。

以下が、層ごとの全経路です。

### 2.1 層 1 — フロントマター（作者の宣言）

ステージは、YAML フロントマターで 2 つのフィールドを宣言してレビューにオプトインします。

```yaml
# core/aidlc-common/stages/inception/requirements-analysis.md
slug: requirements-analysis
mode: inline
reviewer: aidlc-product-lead-agent
reviewer_max_iterations: 2
```

現在、11 のステージがレビュアーを宣言しています: `requirements-analysis`、`user-stories`、
`rough-mockups`、`units-generation`、`application-design`、4 つの設計ステージ
（`functional-design`、`nfr-design`、`nfr-requirements`、`infrastructure-design`）、
そして `code-generation` です。出荷されるレビュアーのペルソナは 2 つ:
`aidlc-product-lead-agent`（プロダクト／要件のステージ）と
`aidlc-architecture-reviewer-agent`（設計／技術のステージ）です。どちらのペルソナファイルも
`disallowedTools: Task` を宣言しています — レビュアーは葉であり、自分のサブエージェントを
生み出せません。

### 2.2 層 2 — コンパイル（検証とノードへの焼き込み）

`aidlc-graph.ts compile` はフロントマターをパースし、`stage-graph.json` へ書かれる
`GraphStage` ノードへ 2 つのフィールドをコピーします。

```ts
// aidlc-graph.ts — GraphStage
reviewer?: string;                 // the agent to invoke after the body
reviewer_max_iterations?: number;  // review-cycle cap; defaults to 2
```

コンパイル時の検証は実効的で厳格です（stage-schema の規則 9）。`agents/*.md` のファイルが
無いエージェントを名指しする `reviewer` は**拒否**され、数値でない／ゼロ／負／整数でない／
レビュアー無しで存在する `reviewer_max_iterations` は**コンパイルを失敗させます**
（これが 2.0.2 の修正でした — そうした不正な設定は以前は通過し、静かにループを無効化して
いました）。明示的な上限なしにレビュアーが宣言された場合、コンパイラは既定で `2` を設定し、
`NaN` が `stage-graph.json` へ到達しないよう防御します。

したがってコンパイルの終わりには、ノードは決定論的に `reviewer` と
`reviewer_max_iterations` を持つか、どちらも持たないかのいずれかです。曖昧さはありません。

### 2.3 層 3 — ディレクティブ（エンジンがコンダクターへ手渡す）

エンジンがステージへルーティングすると、`buildRunStageDirective` がノードを読み、
レビュアーのフィールドを、出力する `run-stage` ディレクティブへそのままコピーします。

```ts
// aidlc-orchestrate.ts — buildRunStageDirective
if (node.reviewer) {
  directive.reviewer = node.reviewer;
  directive.reviewer_max_iterations = node.reviewer_max_iterations ?? 2;
}
```

**これは動きます。** ディレクティブは実際に、たとえば次のような内容でコンダクターへ届きます。

```json
{
  "kind": "run-stage",
  "stage": "requirements-analysis",
  "mode": "inline",
  "gate": true,
  "reviewer": "aidlc-product-lead-agent",
  "reviewer_max_iterations": 2,
  "stage_file": ".kiro/aidlc-common/stages/inception/requirements-analysis.md",
  ...
}
```

0.7.12 の修正がこれを端から端まで確認しました。修正前はコンパイラがフィールドを落として
おり、ディレクティブはレビュアーを運ばなかったため、§12a の「ディレクティブにレビュアーが
含まれるときにだけレビュアーを呼び出す」は常に何も見つけられず、飛ばしていました。その
バグは修正済みで、フィールドは存在します。*残る*不確実性は、完全に次の層にあります。

### 2.4 層 4 — 呼び出し（1 つのモデルのターンの中の散文 — ここが穴）

`run-stage` ディレクティブは**ひとかたまり**であり、コンダクターは、順序付きの
チェックリストとしてそれを辿るよう告げられます。ハーネスの `SKILL.md` の `gate: true` の
分岐から:

> ステージ本文が成果物を生成した後:
> 1. **レビュアーの手順（§12a）:** `directive.reviewer` があれば、（`Task` 経由で）
>    レビュアーをサブエージェントとして呼び出し、ステージ定義／Q&A／成果物のパスを渡し
>    （memory.md や plan.md は渡さない）、その `## Review` の判定を読む。反復が残っている
>    NOT-READY では、指摘を作成側へ返して再呼び出しする。READY または反復を使い切った
>    ときは先へ進む。
> 2. ステージ完了の検証を実行する
> 3. §13 の学習の儀式を実行する
> 4. 承認ゲートを提示する → `report --result approved`

そして `stage-protocol.md` の §12a がレビュアーの契約を綴っています。**別のサブエージェント**
として呼び出し、ステージ定義 + Q&A + 成果物のパスを渡し（作成側の日誌は決して渡さない）、
レビュアーが主要成果物へ **READY / NOT-READY** の判定を伴う `## Review` セクションを追記し、
コンダクターが成果物とレビューのあいだを `reviewer_max_iterations`（既定 2）までループし、
未解決の指摘を書き添えてゲートへ進む、というものです。

レビュアーのライフサイクル全体 — ディスパッチ、判定の読み取り、NOT-READY の再ループ — は、
**1 つのモデルのターンの中で実行される、4 項目からなる散文のチェックリストの手順 1** です。
「成果物が生成された」と「ゲートが提示された」のあいだに、エンジンとの往復はありません。

### 2.5 なぜ不確実なのか

呼び出しが 1 つのモデルのターンの中に散文として住んでいるため、4 つの構造上の穴が、それを
飛ばせるものにし、かつ検知できないものにしています。

- **ディレクティブの境界が無い。** コンダクターが*確実に*立ち止まる 2 つと対比してください。
  スコープ確認は自分自身の `ask` ディレクティブとして届き（これは構造的にターン境界を
  強制します — エンジンが制御を返して待ちます）、承認ゲートは `report`（エンジンが所有する
  別のツール呼び出し）を通じて確定されます。レビュアーにはそのどちらもありません — `ask` も、
  専用の `report` の結果も、エンジンとの往復もありません。モデルが一息で辿るチェックリストの
  4 項目のうちの 1 つにすぎません。
- **監査イベントが無い。** **`REVIEW_*` のイベント種別がまったく存在しません** — 確認済みです。
  `aidlc-audit.ts` の `VALID_EVENT_TYPES` にレビューのイベントはゼロです。したがって
  レビュアーが発火したか（しなかったか）は完全に不可視です。走ったことを記録するものは無く、
  飛ばされたことを検知するものも無く、`--doctor` はそれを示せず、実行時グラフには
  `sensor_firings` / `learnings_captured` の追跡に対応するレビュアーの相当物がありません。
  監査上の足跡を持たない、唯一の主要なステージの手順です。
- **ゲートの依存が無い。** `report --result approved` には、レビューが行われたという前提条件が
  ありません。コンダクターは成果物を生成し、手順 1 を飛ばし、§13 を実行して
  `report approved` できます — そしてエンジンは喜んで遷移を確定します。レビュアーは*品質*に
  とって荷重を担いますが、*前進*にとっては構造的に*任意*なのです。
- **実機で観測。** Kiro CLI の実行では、レビュアーは*実際に*発火しました — ただしそれは
  Opus 4.8 が勤勉だからであり、そのうえで**最初の**呼び出しは失敗しました（サブエージェントが、
  ファイルを読むツールが無く成果物を読めないと報告した）。コンダクターは、成果物のテキストを
  プロンプトへ埋め込んで再呼び出しし、自力で復旧しなければなりませんでした。もっと不注意な
  モデル、あるいは同じモデルでも文脈の圧力が強ければ、手順 1 を丸ごと落とし、誰も気づきません。

### 2.6 より深い観察

レビューは末尾にボルトで留められたゲートではなく、**ステージ自身の実行の第 3 フェーズ**です。
質問する → 成果物を生成する → レビューする。レビュアーが不確実なのは、あらゆる小さな手順が
不確実なのと同じ理由です。エンジンはステージ全体に対してディレクティブを 1 つ出力し、
モデルがどれも落とさずに全フェーズを順に辿ってくれると信頼しています。だからこそトラック 2 は、
レビュアーを特別扱いではなく、対称な 3 フェーズのうちの 1 つとして扱います。

### 2.7 すでに存在するもの（潜在的な分解）

トラック 2 が形式化する 3 フェーズの分割は、**すでに部分的に存在**しており、それがリスクを
下げます — 私たちは非形式的なパターンを第一級へ昇格させるのであって、ゼロから発明するのでは
ありません。

1. **ステージファイルはすでに実行モードを宣言している。** Construction の設計ステージは、
   散文で次を持ちます。
   - `QUESTION-ONLY mode` — ペルソナを読み込み、文脈を読み、質問を生成し、回答を集める。
     オーケストレーターへ戻る。
   - `ARTIFACT-ONLY mode` — 質問を飛ばし（すでに集め終わっている）、成果物を生成する。
   - `Full mode` — すべての手順を実行する（単一ユニット／直接呼び出しの既定）。

   ただしこれらは*コンダクターが自分で選ぶ散文のモード*であり、Bolt の質問／設計フェーズの
   分割にだけ配線されています。

2. **Bolt のフローはすでにフェーズでバッチ化している。** `stage-protocol.md` の
   「フェーズモード」は、Bolt のすべてのユニットで QUESTION-ONLY を走らせ、回答をゲートし、
   その後すべてのユニットで ARTIFACT-ONLY を走らせます。エンジンが統率するフェーズ分割は、
   Construction ではすでに実証済みのパターンです — ただし散文が駆動しており、ディレクティブ
   ではありません。

3. **`report` とユニット単位のループはすでに往復している。** ユニット単位の Construction
   ループはすでに「スライスを実行し、再び `next` し、エンジンが次のユニットを渡す」を
   行っています。「スライスを実行 → 報告 → エンジンが再出力」の機構は存在します。

つまりトラック 2 は、既存の Construction のパターンを、普遍的なステージ実行モデルへ
一般化するものです。

## 3. トラック 1 — レビュアーをその場で強制する（戦術的）

**目標:** ディレクティブの構造に**触れずに**、レビュアーを任意でなくし、観測可能にします。
静かな飛ばしを今すぐ止め、トラック 2 と前方互換を保ちます。

### 3.1 機構

1. **監査イベントを 2 つ追加**します（`aidlc-audit.ts` の `VALID_EVENT_TYPES` と
   `EVENT_HEADINGS`、`docs/reference/12-state-machine.md`、
   `knowledge/aidlc-shared/audit-format.md`）。
   - `REVIEW_REQUESTED` — コンダクターがレビュアーをディスパッチしたときに発行
     （フィールド: `Stage`、`Reviewer`、`Iteration`）。
   - `REVIEW_COMPLETED` — 判定を読んだときに発行（フィールド: `Stage`、`Reviewer`、
     `Verdict` = READY|NOT-READY、`Iteration`）。

2. **LLM の手書きではなく、ツールという行為者が発行**します。
   `aidlc-log.ts review --stage <slug> --reviewer <agent> --verdict <v> --iteration <n>` を
   追加します（既存の `decision` / `answer` の行為者を映したもの）。コンダクターは
   `## Review` の判定を読んだ直後にこれを呼びます。これにより監査証跡は信頼できるものに
   保たれます（ツールが行を書くという、ツール＝行為者の規律に従います）。モデルに手書きさせる
   のではありません。

3. **ゲートの前提条件。** `report --result approved`（およびそれが補完しうる gate-start）は、
   レビュアーを持つステージについて、そのステージの現在の反復に対する終端判定を持つ
   `REVIEW_COMPLETED` の行が監査の末尾に存在しない限り、**確定を拒否します**。存在しない
   場合は `error` ディレクティブを返します:
   *「<reviewer> が現在の出力をレビューしていないため、<slug> を承認へ提示できません。
   レビューを依頼し、その判定を記録してから、もう一度試してください。」*
   エンジンはステージのノードを読んでレビュアーが宣言されているかを知るため、これを
   決定論的に強制できます。

4. **`--doctor` が飛ばしを可視化する。** イベントが入れば、doctor は、対応する
   `REVIEW_COMPLETED` なしに `awaiting-approval` へ到達したレビュアー持ちのステージを
   示せます（多層防御。ゲートの前提条件がすでに防いでいるはずです）。

### 3.2 散文のまま残るもの

レビュアーのサブエージェントを呼び出す*行為*（レビュアーを対象とする `Task`、成果物と Q&A の
パスの受け渡し、上限までの NOT-READY の再ループ）は、コンダクター側の散文のまま残ります。
トラック 1 は呼び出しをエンジンへ移しません — **結果を必須にし、記録させる**だけです。
飛ばされたレビューは、静かな省略ではなく、ゲートでの明確な停止になります。

### 3.3 ハードブロックかソフトブロックか（プロダクトの判断）

- **ハードブロック（推奨）:** 記録された終端レビューなしに、レビュアー持ちのステージを
  承認できません。レビュアーを本当に荷重を担うものにします。
- **ソフトブロック:** ゲートで警告するが承認は許す。「人間が常に最終決定権を持つ」を文字どおり
  保ちますが、レビュアーは飛ばせるままです — それがまさにバグです。

推奨: **レビューが*行われたこと*にはハード、その*判定*にはソフト。** すなわち、レビュアーを
実行しなければならない（READY または N 回後の NOT-READY）が、NOT-READY の判定であっても、
指摘を書き添えたうえで人間がゲートで承認できる、というものです。これは内容に対する人間の
判断を上書きせずに、プロセスを強制します。

### 3.4 触れるファイル（トラック 1）

- `core/tools/aidlc-audit.ts` — 新しいイベント種別 2 つと見出し。
- `core/tools/aidlc-log.ts` — 新しい `review` サブコマンド（ツール行為者）。
- `core/tools/aidlc-orchestrate.ts` — レビュアー持ちステージに対する `report` の前提条件
  （node.reviewer を読み、監査の末尾を走査する）。
- `core/tools/aidlc-utility.ts` — `--doctor` のレビュアー飛ばし検査。
- `core/aidlc-common/protocols/stage-protocol.md` — §12a: 判定を読んだ後に
  `aidlc-log.ts review` を呼ぶこと、ゲートの前提条件を注記する。
- 4 つのハーネスの `skills/aidlc/SKILL.md` すべて — gate:true 分岐の手順 1: 承認の前に
  レビューの監査行を発行する。
- `docs/reference/12-state-machine.md`、`knowledge/aidlc-shared/audit-format.md` —
  新しいイベントを登録する。
- テスト: 監査イベントの往復（t48/t52 系）、ゲートの前提条件のテスト
  （REVIEW_COMPLETED なしでは approve が拒否され、あれば許される）、ドキュメントの件数同期。

### 3.5 リスク

低。ディレクティブの形の変更なし、状態機械のフェーズカーソルなし、ユニット単位／スウォームとの
相互作用なし。唯一の振る舞いの変更は、レビュアー持ちステージの承認が、記録されたレビューを
要求するようになることです — それが意図した契約です。完全に元へ戻せます。

### 3.6 限界

トラック 1 はレビュアーを**必須で監査可能**にしますが、*呼び出し*は依然としてモデルのターンの
中にあります — つまりモデルは依然として実行するかどうかを選びますが、実行せずにゲートへ
到達することはできません。兄弟の問題（質問と回答が事前に埋められたり急がされたりする）は
直しません。それがトラック 2 です。

## 4. トラック 2 — ステージをフェーズのディレクティブへ分解する（構造的）

**目標:** `run-stage` のひとかたまりを出力してモデルが全フェーズを辿ってくれると信頼するのを
やめます。代わりにエンジンが**フェーズごとにディレクティブを 1 つ**出力し、それぞれがターン
境界を強制し、観測可能かつ強制可能になります。レビュアーは特別扱いをやめ、単に第 3 の
フェーズになります。

### 4.1 3 つのフェーズ

すべてのステージは次のように分解されます。

1. **ask-questions** — ペルソナを読み込み、上流の成果物を読み、`<stage>-questions.md` を
   生成し、回答を集めて解決する。（既存の `QUESTION-ONLY` モード。）
2. **generate-artifact** — 回答済みの質問を読み、`produces[]` の成果物を生成し、日誌を保つ。
   （既存の `ARTIFACT-ONLY` モード。）
3. **review** — レビュアーのサブエージェントを呼び出し（ステージが宣言している場合のみ）、
   判定を読み、上限まで成果物とレビューをループする。（今日の §12a の散文。）

その後、既存の**ゲート**（§13 の学習と承認）がステージを閉じます。

質問を持たないステージ（一部の operation ステージ）やレビュアーを持たないステージでは、
エンジンがそのフェーズの出力を単に飛ばします — エンジンはどちらの事実もノードから
すでに知っています。

### 4.2 ディレクティブの流れ

```
next
  → run-questions      (conductor asks, collects, resolves; emits QUESTIONS_COLLECTED)
  → report --phase questions-collected
next
  → (optional answers checkpoint — can be an `ask` if the stage gates answers)
  → run-artifact       (conductor generates produces[]; emits ARTIFACT_PRODUCED)
  → report --phase artifact-produced
next
  → run-review         (emitted ONLY if node.reviewer; conductor invokes reviewer,
                        reads verdict; emits REVIEW_REQUESTED / REVIEW_COMPLETED)
  → report --phase review --verdict <ready|not-ready>
     ├─ not-ready & iter < cap → engine re-emits run-artifact (fix) then run-review
     └─ ready | iter exhausted → advance to gate
next
  → run-gate           (§13 learnings + approval, as today's gate)
  → report --result approved
```

各 `next` は状態を読む新しいエンジン呼び出しであり、各フェーズは離散的で記録された遷移です。
フェーズが飛ばされることは、もはや不可能になります — フェーズ N が報告するまで、エンジンは
フェーズ N+1 のディレクティブを出力しないからです。

### 4.3 新しいエンジンの状態: フェーズカーソル

エンジンは現在、*どのステージ*が現在かを追跡しています（`Current Stage` とチェックボックス）。
トラック 2 は*ステージ内のどのフェーズか*を加えます。選択肢:

- **(a) `aidlc-state.md` の `Stage Phase` フィールド**（`questions` | `artifact` |
  `review` | `gate`）。`report --phase` が進める。
- **(b) 監査の末尾から導出する** — 現在のステージについて最後のフェーズイベントが、いまどこに
  いるかを教えてくれる（新しい永続フィールドなし。実行時コンパイルがすでに位置を導出している
  のと一貫）。推奨: 新しい保存状態の不変条件を避け、監査を真実源とするパターンを再利用できます。

ディレクティブの種別は、新しい `phase` フィールドを持つ `run-stage` のままにする
（`directive.phase = "questions" | "artifact" | "review"`）か、別々の種別
（`run-questions` / `run-artifact` / `run-review`）にするかのどちらかです。`run-stage` の
`phase` フィールドは、ハーネスのループ表とディレクティブ検証への変更が少なく、別々の種別は
より自己説明的です。**推奨: `phase` の判別子を持つ 1 つの `run-stage` 種別** — 4 つの
SKILL.md の表への影響半径が小さいためです。

### 4.4 難所その 1: `for_each: unit-of-work` × フェーズ

Construction の設計ステージは、ユニットごとに**加えて**フェーズごとにもループします。
Bolt のフローはすでにこれらを織り交ぜており、フェーズモデルはその織り交ぜを表現しなければ
なりません。

```
Bolt (units U1..Un):
  for each unit:  run-stage phase=questions   (QUESTION-ONLY, per unit)
  → single answers gate covering the Bolt
  for each unit:  run-stage phase=artifact    (ARTIFACT-ONLY, per unit)
  for each unit:  run-stage phase=review      (per unit, if reviewer)
  → single Bolt-level approval gate
```

つまりループの入れ子は、questions/artifact については**フェーズ主体・ユニット従属**
（次のフェーズへ進む前に、すべてのユニットを 1 つのフェーズへ通す）ですが、review は
**ユニットごと**です（今日の「レビュアーはユニットごとに 1 回発火する」）。エンジンの
`emitForSlug` のユニット単位ドライバーは、すでにあるフェーズについてユニットを歩きます。
トラック 2 はこれを (フェーズ, ユニット) の対を歩くよう拡張します。ここが本当に複雑な部分で
あり、リスクの主な源です。

### 4.5 難所その 2: スウォーム

自律的な Construction は、`invoke-swarm` を通じてユニットをワークツリーへ展開します。
フェーズ分割はこれと共存しなければなりません。

- 各スウォームのワーカーは、自分のワークツリーで 3 フェーズすべてを実行するのか、それとも
  エンジンが展開の前にフェーズでバッチ化するのか。
- レビューはどこで起きるのか — ワーカーごと（ワークツリー内）か、マージ後に中央でか。

おそらく、スウォームはワークツリーごとの成果物と収束を所有し続け、**レビューはマージ結果に
対して中央で走る**でしょう（レビュアーの「独立していて、新鮮な目で見る」という立場に合います）。
ただしこれは独自の設計検討が必要です。スウォームはこのリポジトリでもっともリスクの高い
コードです。

### 4.6 移行の面

- **ディレクティブの型**（`aidlc-directive.ts`） — `phase` と `verdict` を追加。検証の更新。
- **エンジン**（`aidlc-orchestrate.ts`） — フェーズカーソルの解決、`report --phase`、
  フェーズとユニットのループ、スウォームとの相互作用。もっとも大きな変更です。
- **32 のステージファイル** — すべてのステージの Steps セクションを 3 フェーズの契約へ
  適合させる（今日、モードを宣言しているのは Bolt を意識した Construction のステージだけで、
  ideation／inception のステージは宣言していません）。
- **4 つのハーネスの SKILL.md** のループ表 — 新しいフェーズ分岐。
- **監査の分類体系** — `QUESTIONS_COLLECTED`、`ARTIFACT_PRODUCED`、`REVIEW_REQUESTED`、
  `REVIEW_COMPLETED`（後の 2 つはトラック 1 と共有）。
- **十数個ほどのテスト** — 現在の単一 `run-stage` の形を固定しているもの（t65/t66 の
  ディレクティブ形状、t114 の orchestrate-next、t118 のゲート軸、t130/t127 のランナー、
  通常の Bolt と自律スウォームの e2e スイート）。
- **ドキュメント** — stage-protocol の §12a/§3 の書き直し、状態機械の章、オーケストレーターの
  リファレンス、フェーズとステージのガイド。

### 4.7 リスク

高。状態機械、ユニット単位の Construction ループ、そしてスウォーム — もっとも安全性が
重要で、もっともテストされている 3 つのサブシステム — に触れます。独自のマイルストーン、
専用のブランチ、そして漸進的な展開（たとえば、まずユニット単位でないステージにフェーズ
モデルを着地させ、次に Construction、最後にスウォーム）に値します。

## 5. トラック 1 とトラック 2

| 軸 | トラック 1（その場で強制） | トラック 2（フェーズのディレクティブ） |
|------|----------------------------|----------------------------|
| レビュアーの飛ばしを直すか | はい（記録されたレビューなしにゲートが拒否する） | はい（エンジンがレビューのフェーズを出力する） |
| 質問／回答の性急さや事前埋めを直すか | いいえ | はい（各フェーズが自分のゲート付きターンを持つ） |
| ディレクティブ構造の変更 | なし | 新しい `phase` の判別子 + report の結果 |
| 新しいエンジンの状態 | なし（監査の末尾から導出） | フェーズカーソル（監査の末尾から導出） |
| ユニット単位／スウォームへの影響 | なし | 大きい（難所） |
| ステージファイルの変更 | §12a の散文のみ | 32 のステージすべてを 3 フェーズの契約へ適合 |
| テスト／ドキュメントの面 | 小さい | 大きい |
| リスク | 低く、可逆 | 高く、マイルストーン規模 |
| 信頼性までの時間 | 数日 | 数週間 |

**両者は排他的ではありません — トラック 1 はトラック 2 の監査モデルの厳密な部分集合です。**
トラック 1 で作る `REVIEW_REQUESTED` / `REVIEW_COMPLETED` のイベントと、ツール行為者の
`aidlc-log.ts review` は、そのままトラック 2 へ生き残ります（レビューフェーズの監査行に
なります）。したがってトラック 1 は捨てる作業ではなく、トラック 2 の最初の 1 個のレンガです。

## 6. 推奨

**2 トラックで進めます。**

1. **トラック 1 を今すぐやる。** 小さく、低リスクで、今週のうちに静かな飛ばしを止め、かつ
   前方互換です。パッチリリースとして出荷します。
2. **トラック 2 を、独自の RFC + マイルストーンとして予算化する** — チームが「モデルが小さな
   手順を飛ばした」という種類全体（レビュアー*も*質問*も*成果物*も*）を閉じたくなったときに。
   ステージの内在する 3 つのフェーズが、強制可能で観測可能な 3 つのエンジンの遷移になる、
   長期的に正しいアーキテクチャです — しかしこれは、このリポジトリで最大級の取り組みと同じ
   規模の状態機械の変更であり、レビュアーのパッチのついでに滑り込ませるべきではありません。

**避けるべきアンチパターン:** *レビュアーだけ*をディレクティブにして、質問と成果物は融合した
ままにする、という中途半端な分割です。それはトラック 2 の移行コストのほとんどを負いながら、
その概念的なきれいさを得られません — そして、レビューは対等な 3 フェーズのうちの 1 つである、
という枠組みとも矛盾します。3 つすべて（トラック 2）か、その場で強制（トラック 1）かであり、
レビュアーだけのディレクティブではありません。

## 7. チームへの未解決の問い

1. **ハードブロックかソフトブロックか**（トラック 1 §3.3）: レビュアー持ちのステージは、
   記録されたレビューなしに承認不能であるべきか。推奨: レビューが*行われたこと*にはハード、
   その*判定*にはソフト。
2. **トラック 2 の展開順** — ユニット単位でないステージが先、次に Construction、最後に
   スウォームか。それともフラグの裏で一度にか。
3. **トラック 2 のディレクティブの形** — `run-stage` の `phase` 判別子か、別々の
   `run-questions` / `run-artifact` / `run-review` の種別か。
4. **フェーズカーソル** — 監査の末尾から導出（推奨）か、保存される `Stage Phase` フィールドか。
5. **スウォームのレビュー** — ワーカーごとにワークツリー内か、マージ結果に対して中央でか。
6. **トラック 2 では questions/artifact もハードゲートにすべきか**、それとも観測可能に
   するだけか。（すなわち、`questions-collected` が報告されるまでエンジンは `artifact` の出力を
   *拒否*するのか、それとも単に追跡するだけか。）
