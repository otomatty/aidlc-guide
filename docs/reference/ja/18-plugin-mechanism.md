# プラグイン機構

> 対象読者: 第 2/3 層（チーム導入者、フレームワーク貢献者）。

> **パス表記。** 以下の `<harness-dir>/` はハーネスのランタイムディレクトリ（`.claude` / `.codex` / `.kiro` / `.aidlc`）、`plugins/<name>/` は作成したプラグインのソース、`dist/plugins/<name>/<harness>/` は出力されたインストール可能なホストプラグインを表します。

この章は、**AIDLC プラグイン**システムの正規リファレンスです。新しいステージ、エージェント、スコープ、メソッド/ルール、センサー、doctor チェック、および*既存コアステージへの加法的な変更*から成る、任意で所有・バージョン管理されるコントリビューションを、ハーネスに依存しないツリーとして一度だけ作成し、各ハーネス向けの**実際のホストプラグインとして出力**します。プラグインが `core/` を編集することはありません。すべてのプラグインを無効にしたインストールは、ベアコアとバイト単位で同一です。このシステムは、実証済みの唯一の非編集シーム（フェーズルールの加法的合成）をすべてのサーフェスへ一般化し、独自のインストーラーではなく各ホスト自身のプラグイン機構を通じて提供します。関連項目: [ステージ定義](15-stage-definition.md)（プラグインが作成する `plugin`/`number`/`when` を含むステージフロントマター）、[エンジンとスキルシステム](17-skill-system.md)（コンポーザーが供給しオーケストレーターがルーティングするグラフ）、[成果物ボキャブラリー](16-artifact-vocabulary.md)（名前空間のルール）、および作成手順の [プラグインの作成](https://github.com/awslabs/aidlc-workflows/blob/v2/docs/harness-engineering/10-authoring-a-plugin.md) を参照してください。

## 1. プラグインとは何か

プラグインは、宣言的マニフェストとコア形状のサブツリーを持つディレクトリ（かつ Git リポジトリ）です。次のことができます。

- 新しいステージ（番号は初回コンパイル時にエンジンが振る — プラグインは表示番号範囲を主張しない）、エージェント、スコープ、メソッド/ルール（スペースメモリのシードへ）、センサーを**追加**する。
- コントリビューションシーム（§6）を通じ、既存のコアステージを**加法的に変更**する。すなわち、ステージを編集せず、生成物、消費物、検証、指示を充実させる。

AIDLC チームが提供するファーストパーティプラグインと、それ以外のサードパーティプラグインは、**機構上は同一**です。構造、シーム、コンポーザー、ホストへのインストール経路は同じです。違いは来歴、すなわちプラグインのリポジトリ所有者とレビュー者だけです。`plugins/test-pro/` が参照フィクスチャです。

この機構の**設計原則**:

- **厳密な加法性、上書きはしない。** コントリビューションは*追加*のみを行います。構造サーフェスの集合和は可換であり、独立した作成者が安全に作業できる理由です。真の競合はプラグインの出所を含む合成エラーとなり、暗黙に後勝ちになることはありません。
- **コアの不変性。** プラグインが `core/` のファイルを編集することはなく、プラグインが提供するすべては自身のツリー内にあります。
- **可逆かつ無効時は不活性。** プラグインを無効にすると、それがないインストールと完全に同じ状態へ再合成されます。
- **スラッグが識別子。** ステージは重要なすべての場所（エッジ、ジャンプ、解決）でスラッグにより識別されます。`number` は表示/順序専用なので、プラグインステージを挿入してもコアの再採番や不安定化は起きません。

## 2. なぜインストール時にホストプラグインとして提供するのか

繰り返し検討された設計上の問いは、プラグインを*ビルド時*の成果物（中央で事前合成してコピーする）にするか、*インストール時*の成果物（利用者が選んだセットを利用者のマシンで合成する）にするかでした。この機構は**インストール時**を選びます。エコシステム全体（エヌピーエム、カーゴ、ヘルム、VS コード、ニックス）がすでに次の二つの構造的理由からこの形に収束しているためです。

- **組み合わせ爆発。** N 個のプラグインは最大 2ⁿ 個の有効化部分集合を生みます。中央ビルドではすべての組み合わせを事前合成できません。事前ビルドする価値がある唯一の成果物は、誰にとっても同一の**ベアコア**（空集合）です。
- **遅延解決。** 正しいプラグインセットと、同じステージへの二つのプラグインのコントリビューションをどうマージするかは、それらを選んだインストール時にしか分かりません。

配布媒体は独自の AIDLC インストーラーではなく、**ホスト自身のプラグインシステム**です。フレームワークが対象とするすべてのハーネスは、すでにマニフェスト優先かつ Git 配布のプラグインモデル（Claude の `.claude-plugin/`、Codex の `.codex-plugin/`）を備えています。AIDLC プラグインはその一つです。これは**ハイブリッド**です。ストアがあるホスト（Claude、Codex。opencode と Copilot もプロジェクトを「ストア」型レイアウトとして投影）では実プラグイン、ストアがない Kiro ではフォルダードロップを使います。結果は次のとおりです。

- **配布インフラは運用しない。** 顧客が自らのプラグインリポジトリ（Git、セマンティックバージョニングのタグ、`marketplace.json`）をホストします。一つのマーケットプレイスエントリで、混在する環境向けのプラグインを一覧できます。
- **信頼はホストネイティブ。** 組織の制限にはホストの管理対象許可リストを利用します（Claude の `strictKnownMarketplaces` はユーザーによる上書き不可、Codex はコンテンツハッシュ固定の信頼）。AIDLC 独自の信頼レイヤーは作りません。
- **コンポーザーはホストフックによってインストール時に実行される。** 組み合わせごとの事前ビルド済みツリーはなく、セッション開始フックが選択セットをローカルで合成します。

> **セキュリティに関する注記 — Kiro のフォルダードロップにはインストール時の信頼ゲートがありません。** Claude と Codex は、プラグインのフックが実行される*前に*、それぞれの信頼プロンプト（管理対象マーケットプレイス / ハッシュ固定の承認）を通してプラグインを仲介します。Kiro にはプラグインストアがないため、フォルダードロップ経路では、実行可能なプラグインファイルが**同等のゲートなしに**コピーされます。ツリーをドロップすること自体が信頼の決定です。Kiro IDE の投影には、`hooks/aidlc-plugin-compose.ts` にあるクロスプラットフォームの Bun ランチャーを実行する v2 の SessionStart 登録が含まれます。Kiro CLI の投影では、合成は明示的に実行するコマンドに委ねられます。どちらの Kiro プラグインのドロップも `git clone && run` と同様に扱ってください。コードを実行してもよいソースからのみインストールし、ドロップによる差分をレビューし、追従するブランチではなくレビュー済みのタグにプラグインリポジトリを固定してください。コンポーザー自体は加法的で `core/` を編集しませんが、ユーザーのプロセス権限で実行されます。

コントリビューションシーム（§6）が重要である理由はここにあります。これは構造的には VS コードの `contributes` とカーゴの加法的な機能集合和であり、この分野で最も合成しやすいモデルです。ファーストパーティ、サードパーティを問わず、ゲートキーピングなしに*すべての*プラグインが利用できます。

## 3. プラグインの構造とマニフェスト

プラグインツリーは `core/` の形を反映するため、パッケージャーはこれをすべてのハーネスへ投影できます。一度だけ作成すればハーネスに依存しません。

ツリーは*設計上の*サーフェスとして `core/` の完全な形を反映しています。✅ はパッケージャーが現在投影するサブツリー、⏳ は設計済みながら未投影のサブツリー（§7）を表します。

```text
plugins/<name>/
  .aidlc-plugin/plugin.json              # the manifest
  stages/<phase>/<slug>.md               # ✅ NEW stages (slug identity; number is display-only)
  sensors/aidlc-<id>.md                  # ✅ NEW sensor manifests
  tools/<id>.ts                          # ✅ sensor scripts (so a sensor can run)
  tools/<plugin>-doctor.ts               # ✅ optional /aidlc --doctor checks
  contributions/<phase>/<slug>.md        # ✅ ADDITIVE modifications to core stages (§6)
  agents/<plugin>-<role>-agent.md        # ✅ NEW agents (stem == frontmatter name)
  scopes/<plugin>-<name>.md              # ✅ NEW scopes (stem == frontmatter name)
  knowledge/<agent-slug>/…               # ✅ per-agent METHODOLOGY knowledge
  tests/                                 # the plugin's own content validation (integration tier)
  memory/{org,team,project}.md           # ⏳ method/rule additions → default-space seed (§7)
  memory/phases/<phase>.md               # ⏳
```

コアのスコープファイルはファイル名接頭辞 `aidlc-` を使います。プラグインのスコープファイルはこれをプラグイン接頭辞に置き換え（`<plugin>-<name>.md`）、ファイル名の語幹はフロントマターの `name` と一致します。プラグインのエージェントファイルも同じルールに従います。すなわち `<plugin>-<role>-agent.md` で、フロントマターの `name` は語幹と等しくなります。

`.aidlc-plugin/plugin.json` は**宣言的な**マニフェストです。トップレベルは一般的なホストプラグインマニフェストの形を反映しており（マーケットプレイスまたはホストツールが一覧、バージョン、信頼を扱えるように）、AIDLC 固有の設定はネストされた `aidlc` ブロックに分離されます。

```jsonc
{
  "name": "test-pro",                 // == dir name; "core", "aidlc", and "aidlc-*" are reserved; kebab-case
  "version": "0.1.0",                 // semver; checked against dependents' constraints
  "description": "…",
  "author": { "name": "AWS AIDLC" },
  "dependencies": ["core", "compliance@^1.2.0"],  // resolved vs git tags (<plugin>--v<version>)
  "aidlc": {
    "contributes": {                  // which subtrees this plugin ships
      "stages": "stages/", "agents": "agents/", "scopes": "scopes/",
      "sensors": "sensors/", "knowledge": "knowledge/",
      "tools": "tools/", "overlays": "contributions/"
    }
  }
}
```

決定論的で最小限の、作成済みプラグインリポジトリを作ります。

```bash
bun <tools-dir>/aidlc-plugin-create.ts <name> [targetDir]
```

CREATE は空でない対象を拒否し、マニフェストに加えて、名前空間付きの例となるステージ・スコープ・エージェントと tests の README を 1 つずつ出力します。結果は即座に妥当です。`hooks/compose.ts` は設計上存在しません。BUILD が同梱のフックを注入するためです。

作成したプラグインリポジトリは、ビルド前に検証します。

```bash
bun <tools-dir>/aidlc-plugin-validate.ts <plugin-root>
```

同梱のバリデーターは、AIDLC プロジェクトやフレームワークのチェックアウトなしに、オフラインで動きます。マニフェスト、ステージスキーマ、スコープとエージェントの同一性、プラグインローカルな成果物の衝突、`tools/` 配下に紛れ込んだテスト／フィクスチャの積荷、そしてベンダリングされた `hooks/compose.ts` をツール同梱のテンプレートと照合します。トップレベルの `aidlc plugin validate|build` ルートは、これと同じ実装へ委譲します。`create|test` ルートは [RFC #723 §2e](https://github.com/awslabs/aidlc-workflows/issues/723) へ延期されたままです。

同じ外部リポジトリから、ホスト投影を 1 つビルドします。

```bash
bun <tools-dir>/aidlc-plugin-build.ts <plugin-root> <harness> [outDir]
```

ビルダーは書き込み前に検証を行い、既定の出力先は `<plugin-root>/dist/<harness>/` です。チェックアウト側のパッケージャーと同梱のビルダーは、同じエミッターを呼びます。ハーネスマニフェストが引き続き真実源です。パッケージングはその投影レコードを `tools/data/plugin-targets.json` へ出力し、スタンドアロンのビルダーはそれをオフラインで消費します。

選択済みのインストールを変更せずに、合成をテストします。

```bash
bun <tools-dir>/aidlc-plugin-test.ts <plugin-root> \
  --install <project-root> [--harness <name>]
```

このツールは投影をビルドし、マニフェスト由来のインストールルートだけを使い捨ての候補へコピーし、本物の合成フックを 2 回実行して、1 回目がドロップなしであること、合成後のグラフが綺麗でプラグインのステージとスコープを含むこと、2 回目がバイト単位で安定していることを要求します。ハーネスのリーフを共有する場合は `--harness` が必要です。`--dist` は、RFC #722 マイルストーン 2 がリリース済みランタイムバンドルの経路を提供するまで予約されたままです。

コントリビューションパスはプラグイン相対であり、プラグインルートの外へ出てはいけません。トップレベルは**寛容**です（前方互換性とツール間の許容性のため、未知のキーを保持します）。`aidlc` ブロックは**厳格**です（作成時のタイプミスを捉えるため、未知のキーを拒否します）。投影は現在もディレクトリ慣例（`stages/`、`sensors/`、`tools/`、`contributions/`、`scopes/`、`agents/`、`knowledge/`）でコンテンツを発見するため、宣言された各値は正規のディレクトリと一致していなければなりません。設定可能なルーティングは延期されています。`memory` の宣言は、そのサブツリーを投影できるようになるまで拒否されます。ステージ番号は表示専用であるため、プラグインはマニフェスト内で番号範囲を要求しません。`overlays` は正規の `contributions/` に対するマニフェスト上の名称で、コピーではなくマージ時に消費されます。

## 4. 合成モデル

コンポーザーは「ベアコア + 選択したプラグイン」に対して一度実行され、有効なインストールを書き出します。起動方法にかかわらず、**同じコンポーザー**が実行されます。

| ホスト | トリガー | 信頼 |
|------|---------|-------|
| **Claude** | セッション開始フック（セッション生成時に即時実行） | 管理対象許可リスト（`strictKnownMarketplaces`） |
| **Codex** | セッション開始フック（初回の対話時に遅延実行） | 一回限りの信頼プロンプト、コンテンツハッシュ固定 |
| **Kiro**（CLI/IDE） | フォルダードロップ後に `bun <plugin>/hooks/compose.ts` を手動実行（§9 を参照。`.kiro.hook` の自動実行と `aidlc plugin compose` CLI は未接続） | 該当なし — フォルダードロップ配布 |

手順（トリガーにかかわらず同一）:

1. **解決** — 選択したプラグインとその推移的な `dependencies` 閉包を、公開済みバージョンに対して解決します。
2. **新しいプリミティブをコピー** — 各プラグインの `stages`/`agents`/`scopes`/`knowledge`/`sensors`/`tools` サブツリーを対応するハーネスルートへコピーし、`{{HARNESS_DIR}}` トークンをハーネスの実ディレクトリへ置換します。`memory` は引き続き延期されています（§7）。
3. **コントリビューションをマージ** — ステージへの有効な各コントリビューションを対象ステージのソースへ畳み込みます（§6）。構造サーフェスは集合和を取り、プローズフラグメントはアンカー位置に挿入します。
4. **コンパイル** — `aidlc-graph compile` が `stage-graph.json` と `scope-grid.json` を再生成します。オーケストレーターは完全にこれらに基づいてルーティングするため、プラグインステージは合成された瞬間に実行対象となり、プローズやスキルの編集は不要です。

合成は独立したオーバーレイの連続ではなく一つの多方向マージなので、**同じステージにコントリビュートする二つのプラグインは真にマージされます**。構造上の追加は集合和を取り、プローズフラグメントは決定的な順序になります。一方がもう一方を黙って上書きすることはありません。合成に関してランタイムは**読み取り専用**のままです。マージはセッションごとではなく、すべて合成時に起きます。マージ対象はコンパイル済み JSON ではなく**ステージソース**であるため、その後の `aidlc-graph compile`（たとえば rebuild-stage-graph フック）をまたいでも**永続的**であり、**冪等**です。各セッション開始時に再実行しても、新たに合成されるものはありません。

エンジンの再インストールは、グラフのコンパイルとは別物です。新しい `dist/<harness>/` をコピーするとコンパイル済みグラフとコアのステージソースが上書きされるため、プラグイン所有のファイルとサイドカーは残ったまま、グラフのエントリとコントリビューションのマージだけが消えることがあります。エンジンをアップグレードしたら、そのたびに `/aidlc plugin sync` を実行してください。合成フックを持つホストでは、次のセッション開始時にもサーフェスが修復されます。診断の **合成済みプラグイン面** 検査は、プラグインのグラフエントリの欠落と、構造上またはプローズのコントリビューションの陳腐化の両方を検出します。読み取れない、あるいは不正な有効プラグインのサイドカーや、存在しないステージを対象とするレコードも、スキップされるのではなく検査を失敗させます。いったん来歴が壊れると、既に合成された構造上の値を安全に帰属させることはできないため、不正なサイドカーからの復旧は、素のエンジンを入れ直し、そのサイドカーを削除してから `plugin sync` を実行する手順で行ってください。

## 5. 選択

プラグインは追加し、インストールが選択します。プラグインを合成すると、そのファイルがインストールへコピーされ、加法的なコントリビューションがマージされますが、そのインストールの利用者に見えるのは `<harness-dir>/tools/data/harness.json` に名前が挙がったプラグインだけです。

```json
{
  "harnessDir": ".claude",
  "rulesSubdir": "rules",
  "plugins": ["aidlc", "test-pro"]
}
```

`plugins` キーは任意です。存在しない場合はインストール済みのすべてのプラグインが有効になり、既存のインストールが維持され、出荷されるコアはバイト単位で同一に保たれます。存在する場合、そのリストが有効セットです。`aidlc` は暗黙のコアプラグインであり、これを省略するとコアのステージ/スコープ/ランナーが無効になります。ただしファイルはインストールされたまま残り、再度有効化できます。三つの Initialization ステージは例外です。ブートストラップにはプラグインの帰属がないため、これらのステージは有効なすべてのスコープで常に有効です。

選択の確認や変更には、決定的なユーティリティコマンドを使います。

```bash
bun <harness-dir>/tools/aidlc-utility.ts select-plugins
bun <harness-dir>/tools/aidlc-utility.ts select-plugins test-pro
bun <harness-dir>/tools/aidlc-utility.ts select-plugins aidlc,test-pro
```

`select-plugins` は、既知のセット（`aidlc` に加え、コンパイル済みノードとスコープファイルに見つかるプラグイン名）に対して名前を検証し、`harness.json` を書き込み、グラフを再コンパイルし、ステージ/スコープランナーを再生成し、生成される SKILL.md のスコープ/ステージ表を一つのトランザクションで更新します。`harness.json`、`stage-graph.json`、`scope-grid.json` のスナップショットを取り、後段の再生成ステップが失敗した場合は三つすべてを復元し、復元された選択に対して再生成チェーンを再実行するため、インストールが中途半端な状態のまま残ることはありません。`/aidlc --doctor` は有効なプラグインとプラグインごとの有効ステージ数を報告し、グラフの `enabled:false` フラグが `harness.json` と食い違う場合はハードフェイルします。

`aidlc plugin sync` は、インストール済みプラグイン合成のコマンドラインフロントです。発見されたプラグインルートの `hooks/compose.ts` ファイルを実行し、プラグインルートが一つも構成されていない場合は `no installed plugins; nothing to sync` を出力してクリーンに終了します。ルートは構成されているのにどのルートも `hooks/compose.ts` を持たない場合は、各ルートと理由を名指しして終了コード 1 で終了します。混在するセットの場合は、スキップする各ルートについて警告し、有効なルートを合成して終了コード 0 で終了します。

コンパイル済みの `stage-graph.json` は、インストール済みの全ステージセットを保持します。無効なノードは `"enabled": false` を持ち、有効なノードはこのキーを省略します。ランタイムローダーが無効なノードをフィルタリングするため、ランナー、状態行、スコープ表、オーケストレーションには選択されたグラフだけが見えます。`loadStageGraphAll()` はドクターと選択ツール専用に予約されています。ステージ番号は完全なグラフから割り当てられるため、プラグインを無効化して後で再有効化しても番号は正確に保たれます。選択フィルターが対象とするのはステージ、スコープ、ランナーです。無効なプラグインの `agents/` と `knowledge/` のファイルはディスク上に残り、かつ読み込み可能なままです（エージェント名簿とナレッジ検索は選択でフィルタリングされません）。それらのエージェントをディスパッチするはずのステージがフィルタリングされるため、何かに参照されない限り不活性です。

コンパイル済みのスコープグリッドには、有効なスコープ識別情報だけが含まれます。無効なプラグインのスコープファイルはディスク上に残りますが、プラグインが再度選択されるまでは有効なランタイムスコープではありません。コアが無効で、有効なプラグインスコープ所有者がちょうど一つの場合、フリーフォーム/デフォルトスコープのフォールバックは、そのプラグインのアルファベット順で最初のスコープを使います。複数のプラグインスコープ所有者が有効で、コアの優先される `classic` フォールバックが使えない場合、オーケストレーターはエラーとなり、明示的な `--scope` を求めます。

プラグインを無効化すると、そのプラグイン自身のファイルだけでなく、コアステージへマージした内容も取り除かれます。合成は、実際に適用した構造上の追加（対象ステージごとの produces / sensors / `required` と任意の `conditional_on` を含む完全な consume エントリ / scopes / required_sections）と、適用に成功した各フラグメントのアンカー・順序・ハッシュを、`tools/data/plugin-contrib-<key>.json` のプラグイン別サイドカーに記録します。挿入されたプローズフラグメントは、自身のセンチネルマーカーも持ちます。無効化時、`select-plugins` は同じロールバックトランザクションの中で両方をインストール済みのステージソースから取り除くため、無効化されたプラグインのコントリビューションが有効なステージを操り続けることはありません。再有効化すると、次のセッション開始時に復元されます。プラグインの合成フックが再マージし、バイト単位で同一になります。

合成フックと `select-plugins` は、これらの変更を同じワークスペースロックで直列化します。ロックはインストール済みステージの編集、プラグイン別サイドカー、選択の書き込み、グラフ／グリッドのコンパイル、選択のロールバックにまたがるため、並行するプラグインフックが互いの集合和更新を失うことはなく、無効化が合成と競合して追跡されないコントリビューションを有効なまま残すこともありません。

選択はコンパイル時に閉包チェックされます。有効なステージは、そのプロデューサーステージがすべて無効化されている成果物を必須にできません。エラーは、消費側ステージ、成果物、無効化されたプロデューサーステージ、それらを提供するプラグインを名指しした上で、それらのプラグインを有効にするか消費側を無効にするよう指示します。これにより、必須入力が枯渇したままステージをルーティングしかねないプラグインのみの選択を捕捉します。無効なステージを指す `requires_stage` エッジはエラーには**なりません**（依存先が決して実行されないなら順序エッジは空虚に成立します。プラグインのみのインストールがプラグインステージをコアステージの後に順序付けるのは正当です）が、ドクターはそのようにドロップされたエッジを勧告として一覧します。

`select-plugins` はまた、アクティブなワークフローを立ち往生させる変更を拒否します。実行中のワークフローのスコープを所有するプラグイン、またはプランに保留中の EXECUTE ステージを所有するプラグインの無効化は、各依存関係を名指しして拒否されます（先にワークフローを完了または休止させるか、プラグインを有効のままにしてください）。すでに立ち往生を起こしている選択には、ドクターがハードフェイルします。

選択がすでに存在する場合、プラグインを合成しても自動では有効になりません。合成フックは引き続きプラグイン自身のファイル（ステージ、スコープ、エージェント、ナレッジ、センサー、ツール — すべてランタイムでフィルタリングされます）をコピーし、そのプラグインを公開するための `select-plugins` コマンドを名指しした勧告ドロップを記録しますが、無効の間はコアステージのソースへコントリビューションをマージ**しません**。マージ済みのコントリビューションは選択フィルターを迂回するため、マージしてしまうと無効化時の除去がセッション開始のたびに巻き戻されてしまうからです。選択キーがない場合、合成されたプラグインは直ちにアクティブになり、従来の現状が維持されます。

`bundle` は今日、意図的に使われていません。この語は将来あり得る「プラグインの集合（collection of plugins）」概念のために予約されており、プラグインの所有権は常に `plugin:` で表現します。

### プラグインの doctor チェック

有効化されたプラグインは `tools/<plugin>-doctor.ts` を出荷できます。`/aidlc --doctor` は
合成後のハーネスの tools ディレクトリでそのスクリプトを見つけ、シェルを介さず Bun で直接
実行します。実行時には `AIDLC_PROJECT_DIR`、`AIDLC_HARNESS_DIR`、`AIDLC_PLUGIN_NAME` が
設定されます。無効なプラグインのスクリプトは不活性なままです。`harness.json` に `plugins`
の選択がない場合は、完全なステージ／スコープのメタデータから判明するすべてのインストール済み
プラグインが対象になります。発見にはそのプラグインがステージまたはスコープを少なくとも 1 つ
所有していることが必要で、ツール、センサー、ナレッジだけを出荷するプラグインは doctor が
発見できる識別を持ちません。

スクリプトは標準出力へ JSON オブジェクトを 1 つ書きます。

```json
{
  "checks": [
    {
      "pass": false,
      "label": "required connector is installed",
      "fix": "install the connector and re-run doctor",
      "severity": "error"
    }
  ]
}
```

`severity` の既定は `error` です。失敗した error のチェックは doctor を失敗させ、失敗した
`advisory` のチェックは終了コードを変えずに表示・エクスポートされます。合格したチェックは
通常どおり描画されます。doctor はインストール済みプラグインをコードの信頼境界として扱い
つつ、失敗を封じ込めます。起動エラー、タイムアウト（既定 10 秒。正の整数を渡す
`AIDLC_PLUGIN_DOCTOR_TIMEOUT_MS` で上書き可能）、非ゼロ終了、不正な JSON や形、壊れた
エントリは、doctor をクラッシュさせるのではなく有界な所見になります。出力はプラグインごとに
50 行のチェック、標準出力は 256 KiB、label と fix は 300 文字が上限です。

## 6. コントリビューションシーム

**コントリビューション**とは、プラグインが名前付き既存ステージを加法的に変更するために提供する `contributions/<phase>/<slug>.md` のファイルです。対象そのものを編集することはありません。

```yaml
---
target: build-and-test        # the existing core stage being enriched
plugin: test-pro
adds:                         # STRUCTURAL — set-unioned into the stage node
  produces:
    - test-pro-regression-suite            # plugin-namespaced (§8)
  consumes:
    - artifact: test-pro-testability-requirements
      required: false
  sensors:
    - coverage-threshold
  required_sections:
    - "Branch Coverage"        # declared H2 (merged into the stage; not machine-enforced yet — see §9)
fragments:                    # PROSE — spliced into the stage body
  - anchor: after-step:8
    order: 100
---

## fragment: after-step:8

### Step 8a (test-pro): Branch + coverage enrichment
…prose the agent reads, inserted after the target stage's Step 8…
```

`bundle:` は予約済みで未使用です。プラグインの所有権には `plugin:` と書いてください。

**マージの意味論:**

- **構造サーフェス** — 対象ステージのソースフロントマターへ**集合和**を取ります。可換で順序に依存せず、調整していない作成者間でも安全です。*現在実装済み:* `produces`、`consumes`（成果物 + `required` + `conditional_on` をそれぞれ保持）、`sensors`、`scopes`、`required_sections`。`adds.scopes` には 2 つのガードレールがあります。スコープの識別ファイルが既にインストールされていること（`scopes/<name>.md` の無い名前は全 SKIP のファントムとして解決されてしまう）、そしてそのインストール済みファイルの `plugin:` フロントマターがコントリビュートするプラグイン名と正確に一致すること — コアステージをコアや他プラグインのスコープ配下に置くことは、他方の所有者が合意していない選択セマンティクスの変更であり、所有権は名前接頭辞規則ではなくファイルが宣言する所有者から来ます（ダッシュ接頭辞はプラグイン名間で重複し得ます。コアスコープは `plugin:` を宣言せず、決してマージされません）。違反エントリはマージされず、ログ付きでドロップされます。*未マージ（延期）:* `adds.requires_stage`。コントリビューションで宣言はできますが、合成フックはマージせずドロップログへ記録します（`--doctor` で確認可能）。よって欠落が黙殺されることはありません。実装されると他と同様に集合和を取ります。
- **プローズフラグメント**（ステップ/質問プローズの `fragments`）— 宣言されたアンカー位置でステージ本文へ挿入し、`(order, plugin)` により決定的に並べます。挿入される各ブロックはコンテンツハッシュ付きセンチネルで囲まれ、そのアンカー・順序・ハッシュがコントリビューションのサイドカーへ永続化されるため、再合成は冪等であり、更新されたフラグメントは以前のブロックを置換し、プローズだけのプラグインも検証可能な来歴を保ちます。フックの実行順にかかわらず、別々のプラグインのブロックは `(order, plugin)` で交互配置されます。エージェントは実行時にベース本文と順序付けられたフラグメントを読み取ります。
- **上書きは決してしない。** コントリビューションができるのは追加だけです。ステージの `lead_agent` の変更、`consumes[].required` の緩和、フィールドの削除、既存ステッププローズの置換はできません。アップストリームの挙動を*変更*する真の必要性はフレームワークレベルの判断であり、プラグイン内の静かなパッチではありません。

**フラグメントアンカー:**

| アンカー | フラグメントの挿入位置 |
|--------|------------------------|
| `after-step:<n>` | `### Step <n>` のコンテンツ直後（次の見出しの前） |
| `before-step:<n>` | `### Step <n>` の直前 |
| `after-questions` | 質問生成ステップの後 |
| `end-of-steps` | `## Steps` ブロックの末尾 |
| `in:<Compartment>` | 指定された `## <Compartment>` ブロックの末尾 |

**サーフェス別** — アップストリーム変更の種類ごとにプラグインが使う方法です。「ステータス」は、合成フックが現在マージするものと、設計済みながら延期されているものを示します。

| 変更 | 機構 | ステータス |
|--------|-----------|--------|
| ステージに新しい質問をさせる | 質問プローズの `fragments` | ✅ 実装済み |
| ステージに追加成果物を生成させる | `adds.produces` + それを出力する `fragments` ステップ | ✅ 実装済み |
| ステージに新しいセクションを要求させる | `adds.required_sections` | ✅ マージ済み（⚠️ 宣言的 — まだ機械的には強制されない、§9） |
| ステージに検証を追加する | `adds.sensors`（マニフェストと `tools/` スクリプトを提供） | ✅ 実装済み |
| 消費エッジを追加する | `adds.consumes` | ✅ 実装済み |
| `requires_stage` エッジを追加する | `adds.requires_stage` | ⏳ 延期（宣言 → ログ、未マージ） |
| 既存ステージをプラグインスコープに含める | `adds.scopes`（自プラグインのスコープのみ。インストール済み識別ファイルが必要） | ✅ 実装済み |
| フェーズポリシー / ガードレールを注入する | `memory/phases/<p>.md` をデフォルトスペースのシードへ提供（§7） | ⏳ 延期（未投影） |

## 7. メソッド/ルール、エージェント、ナレッジ、スコープ、アクティベーション

このセクションでは、新しいステージとコントリビューションシームを超えたサーフェスを、作成者を誤解させないようステータスを付けて説明します。

**メソッド/ルール → メモリシード** *(⏳ 延期).* フレームワークのルールレイヤーは、`core/memory/` からシードされるスペースごとの**メモリ**ツリー（`aidlc/spaces/<space>/memory/{org,team,project}.md`、`phases/<phase>.md`）です。設計上は、プラグインが `memory/phases/<p>.md` を提供し、そのシードに集合和を取ります。パッケージャーはまだプラグインの `memory/` ツリーを投影しないため、現在は効果がありません。

**エージェント** *(✅ 投影・合成済み).* プラグインは新しいペルソナを `agents/<plugin>-<role>-agent.md` として提供します。フロントマターの `name` はファイル名の語幹と等しく、`plugin: <plugin>` を持ちます。合成はコアや他のプラグインを上書きすることなく `<harness>/agents/` へコピーします。同一内容のファイルは冪等にスキップされ、同じ宛先に異なる内容がある場合はドロップログへ記録されます。

Kiro では、合成が `.kiro/agents/` のペルソナから未対応の `disallowedTools: Task` 行を取り除きます。入れ子の委譲は Kiro のネイティブなエージェントツール設定によって引き続き利用できません。`disallowedTools` に別の値がある場合はドロップログへ記録され、そのペルソナはコピーされません。再合成が既存のペルソナを移行するのは、それが投影導入前のコンポーザーが作った、同一プラグイン由来の変更されていない完全な複製である場合だけです。編集済みや他由来のファイルは、従来どおり上書きしない挙動を保ちます。すでに合成済みの未対応の値はそのまま残され、再合成の前に削除すべきファイルを名指しする degraded 診断が付きます。

Kiro CLI、Codex、OpenCode では、エンジンロスター内の Markdown ペルソナは `mode: inline` に対してのみ利用可能です。ネイティブディスパッチにはさらに、ハーネスごとのディスパッチサーフェスが必要です。Kiro CLI では手書きの agent-v1 JSON とコンダクターの `trustedAgents` リストへの登録、Codex ではエージェント設定 TOML（出荷される `aidlc-*-agent.toml` の形）、OpenCode ではネイティブの `.opencode/agents/` サブエージェントファイルです。Kiro IDE はその代わりに、インストールされたエージェント Markdown 自体をディスパッチしますが、それは `tools:` が空でなく、かつ `permissions.rules` に整形式の `capability` / `effect` / `match` エントリが少なくとも 1 つ含まれる場合に限られます。空の permissions、rules の欠落や空、不正なエントリは拒否されます。したがってコンポーズは、ディスパッチトポロジー（リードとサポートに対する `mob`、`pipeline`、`subagent`。モードにかかわらず、ゲート付きステージの `reviewer:` も対象）が、完全にインストールされたディスパッチサーフェスを持たないエージェントを名指しするプラグインステージを拒否し、そのステージ、エージェント、修復方法をコンポーズのドロップログへ記録します。Kiro CLI では JSON と `trustedAgents` 登録が独立して検査され、片方しかない場合でもステージは拒否されます。Kiro IDE では、インストールされる `.md` に必要な 2 つのブロックを両方書くか、ステージを `mode: inline` に変更してください。IDE の経路が `aidlc.json` を読むことはありません。OpenCode — コンポーズ自身がネイティブサーフェスを出力する唯一のハーネス — では、プラグインが同梱するペルソナがネイティブツイン出力を通過できる場合（閉じたフロントマターで、投影不能な `disallowedTools` がない）にサーフェスとして数えられます。Kiro/Codex のサーフェスは常に手書きなので、プラグイン自身のファイルがこれらの検査を満たすことはありません。不足しているサーフェスを手書きしてコンポーズを再実行すれば、ステージは受理されます。Markdown ペルソナは、それを併用する受理済みインラインステージのために引き続き合成されます。

`agent-team` はスキーマ上予約されていますがランタイムのコンシューマーが存在しないため、コンポーズはそれを選択するプラグインステージを、黙ってインライン扱いにするのではなく、すべてのハーネスで拒否します。インストール済みのステージパーサーが利用できない場合、Kiro/Codex/OpenCode のコンポーズはフェイルクローズします。明示的な `mode: inline` スカラーを持ち `reviewer:` を持たないステージだけが受理されます（引用符付きスカラー形式も認識されます）。no-clobber なアップグレードは古いフックが合成したステージを削除できないため、これらのディスパッチ検査に失敗する既存ステージはディスク上に残りますが、修復方法を名指しする劣化ヘルス行を出力します。

**ナレッジ = 方法論のみ** *(✅ 投影・合成済み).* プラグインはエージェントごとの方法論ナレッジを `knowledge/<agent-slug>/` に提供し、`<harness>/knowledge/<agent-slug>/` へ合成されます。ドメイン/スペースナレッジ（`aidlc/spaces/<space>/knowledge/`）は、ブートストラップ時に空のユーザーランタイム状態であり、プラグインは提供もシードも行いません。

**スコープ** *(✅ 投影・合成済み).* プラグインスコープの識別情報は `scopes/<plugin>-<name>.md` の一つのファイルであり、フロントマターの `name` はファイル名の語幹と等しく、`plugin: <plugin>` を持ちます。合成は上書きすることなく `<harness>/scopes/` へコピーします。プラグインが作成したステージのメンバーシップは、それらのステージの `scopes:` フロントマターを通じて機能します。プラグインスコープは `freeform_default: true` を設定して、優先されるコアの `classic` 既定が無効なときに自身を指名できます。指名を主張できるのは有効なスコープのうち最大 1 つで、曖昧な選択セットはグラフコンパイルが拒否します。既存のコアステージへのプラグインスコープの追加は、コントリビューションの `adds.scopes`（§6）で機能します — 自プラグインのスコープのみで、マージの前にスコープファイルがインストールされている必要があります。

**アクティベーション（`when:`）** *(⚠️ 解析済み、未評価).* ステージは構造化された `when:` 述語を持てます。`{producer-in-plan: X}` はスキーマ検証・解析されますが、**まだそれを評価するエンジンコンシューマーはありません**。`aidlc-graph` が将来の実装先です。したがって、`when:` を持つステージは現在、宣言されたスコープの下で無条件に EXECUTE されます。プラグイン自身のステージが存在するのはプラグインが選択セットに含まれる場合だけなので、「このプラグインが有効か」はすでに合成時の事実です。

**`plugin.json` の `aidlc.contributes`。** VALIDATE はこのブロックを読み、未知のキーを拒否し、現在投影されているすべてのサブツリーについて正規の値と正確に一致することを要求します。BUILD と TEST も同じ指摘で停止し、直接の出力処理は、出力を置き換える前にパス契約を再度アサートします。エミッターは依然として、マニフェストの任意パスを経由するのではなくディレクトリ慣例でバイトを発見します。設定可能なルーティングは延期されたままです。`memory` は、その投影が存在するようになるまで拒否されます。`aidlc.lock.json` も読み取りません。現在、コンポーザーがロックファイルから解決するものはありません。

## 8. マルチテナントガード

互いに調整を行わない独立した作成者の安全は、次によって確保されます。

- **名前空間化。** コントリビュートする成果物の論理名には `<plugin>-` 接頭辞を付けます。`core-*` は予約済みです。プラグインのステージ、エージェント、スコープ、センサーは、選択セット全体およびコアに対してスラッグが一意であるべきです。プリミティブファイルの衝突は no-clobber（上書きせず）で、出所付きでドロップログに記録されます（暗黙のシャドーイングはありません）。
- **依存関係解決。** `dependencies` は Git タグに対してセマンティックバージョニングで解決します。循環は拒否され、満たせない依存関係は要求プラグイン名を含む合成エラーになります。
- **決定的な順序。** 唯一の非可換サーフェスであるプローズフラグメントは、ロード順ではなく明示的な `(order, plugin)` で順序付けられます。
- **競合は可視化される。** 同じステージで同じフラグメントアンカー・同じ順序、満たせないプラグイン間エッジ、プリミティブパスの重複といった真に非可換な衝突は、オーバーレイ順で解決するのではなく、出所付きでドロップまたは拒否されます。

## 9. 実装済みの出力、インストール、および実例

共有のプラグインエミッターが、作成済みのルート 1 つをホストプラグイン 1 つへ投影します。`bun scripts/package.ts` は、検出した一次配布の `plugins/<name>/` ルートに対してこれを呼び、`aidlc-plugin-build.ts` は外部のプラグインリポジトリから呼びます。各投影には `.aidlc-plugin-projection.json` が含まれ、置き換えの権威を論理プラグインと正確なハーネスへ束縛します。加えてホストネイティブマニフェスト（`.claude-plugin/` / `.codex-plugin/` / Copilot の `.plugin/` / `.kiro-plugin/` / `.opencode-plugin/` / `.cursor-plugin/`）、`marketplace.json`、合成フック、プラグインコンテンツが含まれます（ステージは完全な `number`/`plugin`/`when` フロントマターを持ち、スキーマがネイティブに受け入れます）。有効な一致マーカーを持たない空でない出力が掃除されることは決してなく、強制バイパスもありません。Cursor はプラグインエージェントの合成入力を、Cursor が自動検出するルートの `agents/` の外側にあたる `aidlc/agents/` に置きます。合成はハーネストークンを解決し名前付きモデル固定を取り除いたうえで、単一のネイティブコピーをインストール済みの `.cursor/agents/` の構成へ投影します。合成フックは、GNU 固有シェルを使わない Bun の単一ポータブル `compose.ts` で、**ハーネス非依存**です。プラグインルートは `CLAUDE_PLUGIN_ROOT | PLUGIN_ROOT | AIDLC_PLUGIN_ROOT`、プロジェクトディレクトリは `CLAUDE_PROJECT_DIR | AIDLC_PROJECT_DIR | PWD`（Codex はプロジェクトディレクトリ変数を設定しないため PWD がフォールバック）、ハーネスのリーフは各ホストのコマンドまたは Cursor のランチャーが供給する `AIDLC_HARNESS_DIR` から解決します。Cursor のランチャーはさらに SessionStart の `workspace_roots` を解析し、AI-DLC の Cursor インストールを持つ唯一のルートを選び、複数のルートが該当する場合は `AIDLC_PROJECT_DIR` で 1 つを指定しない限り拒否します。新しいステージ / スコープ / エージェント / ナレッジ / センサー / ツールを上書きせずにコピーし、シームを冪等にマージし（コンテンツハッシュ付きセンチネル挿入、書き込み前比較）、ドロップすべきコントリビューション（対象欠落、不正なアンカー、インストール済みエンジンが受け付けないキー）はセッションを失敗させず、プラグインごとの `<hooksHealthDir>/plugin-compose-<key>.drops` ファイルに記録します。これはコアフックが書き込み `/aidlc --doctor` が走査する、同じスペース単位のヘルスディレクトリです。インストール済みのテスト／フィクスチャの積荷は、合成を行ったハーネスのリーフをキーとする、ハーネスごとの `plugin-compose-installed-tool-payloads-<harness>.drops` レコードで別途監査します。この走査は、修正後のプラグイン投影にもうそのパスが含まれていない場合でも当該ハーネスのインストール済み tools ツリーを歩くため、あるハーネスでの綺麗な合成が別のハーネスの助言を消すことはありません。古い合成バージョンはツールファイルの来歴を保存していなかったため、レガシーなファイルは、たまたま次に合成したプラグインへ帰属させることなく報告します。センサーマニフェストにはコピー時の追加ガードがあります。発見処理は `sensors/` をフラットに走査し `aidlc-<id>.md` に一致するベース名だけをインデックスするため、それ以外の名前（またはサブディレクトリ内）のプラグインマニフェストは合成こそ成功するものの決して発火しません。合成はそのようなマニフェストを拒否し、ファイル名と要求される形を名指しする劣化ドロップを記録します。古い合成フックが既に配置してしまったものも次回実行時に同様に報告されるため、名前を誤ったセンサーがディスク上で黙って死んでいることはありません。

出力されたホストマニフェストがプラグインの身元の正典です。合成はホストパッケージ ID `aidlc-<name>` を論理名 `<name>` へ逆引きし、`plugin:` フィールドが異なる所有ステージ・スコープ・エージェント・コントリビューションの内容を拒否します。着信するスコープ／エージェント名は各ファイルの受理時に予約されるため、1 つのプラグインツリー内の重複した身元はコンパイル前にドロップされます。構造リストの比較は、引用符付きと引用符なしの YAML スカラーを正規化します。合成はまた、realpath をキーとするワークスペースロックをトランザクション全体にわたって保持します。グラフコンパイルが失敗した場合、新しくコピーされたファイルとコントリビューションの書き込みは、再試行マーカーが書かれる前に復元されます。

出力される SessionStart コマンドは、まず `PATH` 上の `aidlc` を探し、利用できる場合は `aidlc plugin sync` を実行します。CLI が利用できない場合、ポータブルなランチャーは bun による `hooks/compose.ts` の直接呼び出しへフォールバックします。

Cursor が出力するフックは、Cursor のフラットな camelCase スキーマ（`hooks.sessionStart[].command`）を使い、`./hooks/aidlc-plugin-compose.ts .cursor` を呼び出します。この Bun ランチャーは `Bun.which` と `process.execPath` を使って `aidlc` を探索し、隣接する `compose.ts` を実行します。Windows ネイティブ環境で `sh -c` に依存しない、ポータブルな方式です。Kiro IDE の v2 SessionStart 登録は、投影をワークスペースルートへフォルダードロップした後、同じランチャーを `.kiro kiro-ide` 付きで使います。

**ホスト別のインストール:**

```bash
# Claude Code
/plugin marketplace add <repo-or-path>/dist/plugins/<name>/claude
/plugin install aidlc-<name>@aidlc-plugins        # SessionStart hook composes on next session

# Codex CLI (in a git repo)
codex plugin marketplace add <…>/dist/plugins/<name>/codex
codex plugin add aidlc-<name>@aidlc-plugins       # approve the one-time hook trust

# Kiro (no store — folder-drop, then run the composer explicitly).
# PLUGIN_ROOT is the emitted projection dir (it carries hooks/compose.ts + the
# plugin content); PROJECT_DIR is the install you dropped .kiro into.
PLUGIN_ROOT="$(pwd)/dist/plugins/<name>/kiro"
cp -r "$PLUGIN_ROOT"/. <project>/
AIDLC_PLUGIN_ROOT="$PLUGIN_ROOT" AIDLC_PROJECT_DIR="<project>" \
  AIDLC_HARNESS_DIR=.kiro bun "$PLUGIN_ROOT/hooks/compose.ts"
# ^ the one working invocation today. A `.kiro.hook` auto-fire and an
#   `aidlc plugin compose` wrapper CLI are designed but NOT yet wired (see Status).
```

その後、`/aidlc --doctor` は有効セットを反映します（例: `core + test-pro` では 34 ステージのグラフ、`select-plugins` で絞り込んだ場合はフィルター済みグラフ）。スコープ指定実行（`/aidlc --scope enterprise`）は、各ステージのスコープがパス上に置く場所へプラグインステージをルーティングします。

**実例 — 混在環境におけるテストプロ。** プラットフォームチームは `test-pro` を一度だけ公開します（リポジトリを検証し、`aidlc-plugin-build.ts` で対応する各ハーネス投影をビルドし、`aidlc-plugin-test.ts` で各投影を使い捨てのインストール候補に対してテストし、`<plugin>--v<version>` タグをプッシュし、生成されたマーケットプレイスのメタデータを公開します）。Claude チームは `/plugin install`、Codex チームは `codex plugin add`（信頼を一度承認）、Kiro チームは `git pull` の後に上記のとおりコンポーザーを明示的に実行します。いずれの場合も、コンポーザーはテストプロの二つの新しいステージ**と**、`build-and-test`/`nfr-requirements`/`nfr-design`/`performance-validation` へのコントリビューションをマージします。結果は同じ、拡張済みで 34 ステージ、診断が正常なインストールです。7 つのハーネス投影すべて（Claude、Codex、Cursor、Kiro CLI、Kiro IDE、opencode、GitHub Copilot）で検証済みです。

**ステータス。** 実装・検証済み: `number`/`name`/`plugin`/`when` のスキーマサポート（`aidlc-stage-schema.ts`）、作成時の `plugin` 所有権をコンパイル済みステージノードへ引き継ぐコンパイル側の処理（コアはこのフィールドを省略）、`harness.json` + `select-plugins` によるインストール時選択（全グラフの永続化、フィルター済みランタイムロード、閉包チェック、ランナーの刈り込み、doctor の行、合成の助言ドロップを含む）、選択状態を考慮した `tools/<plugin>-doctor.ts` チェック（有界かつ失敗を明示する実行）、スタンドアロンかつオフラインの `aidlc-plugin-create.ts`・`aidlc-plugin-validate.ts`・`aidlc-plugin-build.ts`・`aidlc-plugin-test.ts` という作成用ツール群（決定論的な雛形、同梱の合成フックテンプレート、マニフェスト由来のハーネス対象データ、正規のコントリビューションパス検証、プラグイン／ハーネスに束縛された出力マーカー）、それらと同じツールへ委譲するトップレベルの `aidlc plugin validate|build` ルート、プラグイン名前空間付きのステージ / スコープランナー生成、パッケージャーとスタンドアロンで共有するエミッター（発見されたすべてのハーネス投影）、プラグインの `stages/`・`scopes/`・`agents/`・`knowledge/`・`sensors/`・`tools/` の投影と no-clobber 合成、ハーネス非依存の合成フック（`scripts/plugin-hooks-template/compose.ts`）、再利用可能な `tests/harness/plugin-kit.ts` のビルド、共有の合成サブプロセス／ドロップ読み取り、委譲されたコンテンツ検証、ライブ呼び出しの各ヘルパー、`produces` / `consumes` / `sensors` / `scopes`（自プラグイン、インストール済みファイルでガード）/ `required_sections` とプローズフラグメントのコントリビューションシーム（コンテンツハッシュ付き、冪等、決定的順序）。`tests/integration/t188-plugin-compose.test.ts`（合成機構）、`tests/integration/t224-plugin-selection.test.ts`（選択）、`tests/integration/t300-plugin-kit.test.ts`（再利用可能なキット）、`tests/integration/t327-plugin-author-routes.test.ts`（トップレベルの作成ルート）、`tests/unit/t314-plugin-validate.test.ts`（オフラインバリデーター）、`tests/unit/t315-plugin-build.test.ts`（バイト同一性を保つ隔離ビルダー）、`tests/unit/t316-plugin-test.test.ts`（隔離された候補合成ティア）、`tests/unit/t317-plugin-create.test.ts`（隔離されたツールチェーン全体の雛形）、`tests/unit/t313-plugin-doctor-checks.test.ts`（doctor ランナー）、および各プラグイン自身の `tests/`（コンテンツ、統合ティアに接続）が保護します。トップレベルの `aidlc plugin create|test` ルートは RFC #723 §2e へ延期されたままで、`aidlc-plugin-test --dist` は RFC #722 マイルストーン 2 がリリース経路を提供するまで予約されたままです。**延期 / 未接続:** プラグインの `memory/` サブツリーの投影・マージと、設定可能な `aidlc.contributes` ルーティング、`adds.requires_stage` のマージ（宣言 → ログ）、`when:` 述語の評価（解析済み、エンジンコンシューマーなし）、マージ済み `required_sections` の機械的強制（フィールドはマージ・検証されるもののコンパイル済みノードに届かず、提供される必須セクションセンサーはテンプレートから期待値を導くため、宣言されたセクションの欠落でステージが失敗することはまだない）、`after-questions` フラグメントアンカー（`locateAnchor` にケースがなく「不明なアンカー」をドロップログに記録するため、`after-step:<n>` を使用）、任意のロックファイルまたは `dependencies` の読み取り。NEW スラグの番号シードはエッジ対応です。初回コンパイルは各フェーズの新規ステージ群を、それら自身の `requires_stage` エッジで順序付け（同点は authored `number:` ヒント、次にスラグで決着）、その順に次の空き連番を割り当てます — 番号の値はすべてエンジンが所有し（作者は何も主張しないため、調整していないプラグイン同士が衝突できません）、複数ステージのプラグインのサブ DAG はファイル名に関係なくフロー順にシードされ、既に固定済みの行は JSON の値を保持します。authored `name:` は新規スラグの表示名をシードします。

## 9. 不変条件

- **コアは不変。** プラグインが `core/` を編集することはありません。
- **加法性のみ。** コントリビューションは追加し、上書き・削除は決してしません。
- **無効時は不活性。** すべてのプラグインを無効にすると、ベアコアとバイト単位で同一になります。
- **一つのコンポーザー、ホストが起動。** 実行場所にかかわらず同じコードが合成します。中央で事前ビルドされる唯一の成果物はベアコアです。
- **プラグインはホストプラグインそのもの。** パッケージャーは実際の `.claude-plugin/` / `.codex-plugin/` / Copilot の `.plugin/` / `.kiro-plugin/` マニフェストを出力し、ホストのネイティブコマンドでインストールされます。AIDLC は配布インフラを運用しません。
- **スラッグが識別子、番号は表示専用。** プラグインステージを挿入してもコアの再採番は起きません。
- **信頼はホストネイティブ。** 組織の制限にはホストの管理対象許可リストを使い、AIDLC 独自の信頼レイヤーは作りません。
- **ゲートキーピングなし。** ファーストパーティとサードパーティのプラグインは機構上同等で、違いは来歴だけです。
