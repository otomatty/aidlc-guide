# 構築フェーズ -- ステージリファレンス（3.1～3.7）

## フェーズの概要

構築フェーズでは、インセプションで作成した設計成果物を、動作しテスト済みの
ソフトウェアへと変換します。機能設計、非機能要件と設計、インフラストラクチャ
設計、コード生成、ビルド／テスト検証、CI パイプライン設定にわたる 7 つの
ステージ（3.1～3.7）で構成されます。

構築は AI-DLC 方法論における 5 フェーズのうち第 4 フェーズです。コンパイル
済みのスコープグリッドにより、実行するステージとスキップするステージが
決まります。ランタイムのユニットバッチは `unit-of-work-dependency.md`
（ステージ 2.7）に由来します。デリバリー計画（ステージ 2.9）は承認済みの
実行単位計画を作成します — これは計画の内容であり、ウォークの情報源では
ありません。

すべてのステージは、承認ゲート、質問形式、完了メッセージ、状態追跡について
`stage-protocol.md` に従います。

> **パス規約。** 各ワークフローの成果物は、対応する**意図レコードディレクトリ**
> `aidlc/spaces/<space>/intents/<YYMMDD>-<label>/` に格納されます（`<space>` は
> 非デフォルトのスペースを使用していない限り `default` です。
> `<YYMMDD>-<label>` は意図ディレクトリを示し、`260624` のような短い UTC 日付
> プレフィックスと、レコードを時系列に並べられる短いケバブケースのラベルで
> 構成されます）。以降の `<record>/` はこのディレクトリの短縮表記です。たとえば
> `<record>/construction/{unit-name}/functional-design/` は
> `aidlc/spaces/default/intents/<YYMMDD>-<label>/construction/{unit-name}/functional-design/`
> に展開されます。ディレクトリ名は人が読めるラベルであり、正規の識別子は
> `intents.json` レジストリ行に保存された UUIDv7 です。（意図ごとのレイアウト
> より前に作成されたプロジェクトではフラットツリーを使用しており、エンジンが
> 初回実行時に移行します。）

## 構築のウォーク

[実行単位](../../guide/glossary.md) は、デリバリー計画（2.9）で計画された構築の
デリバリースライスです。Definition of Done、確信度仮説、所有権を持つ 1 つ
以上のユニットで構成されます。構築の**既定のウォークはステージ優先**です。
1 つのステージをすべてのユニットに実行してから次のステージへ進み、コード生成が
最後になります。このウォークは、まだ 2.9 の計画をランタイム境界としては扱い
ません。オプトインの `Construction Iteration: unit-major` ウォーク（1 ユニットを
すべてのユニット単位ステージに通してから次のユニットへ進む）が、ユニットごとの
実行単位に近い形です。

`BOLT_STARTED` / `BOLT_COMPLETED` はスウォーム／ワークツリー経路で発行され、
既定のゲート付き実行では記録されません。ランタイムバッチは
`unit-of-work-dependency.md`（ステージ 2.7）から再計算されます。ステージ 2.9 の
`bolt-plan.md` は計画成果物です（順序、実行単位ごとの DoD、ワーキングスケルトン
マーカー）。ワーキングスケルトンの姿勢は `org.md` → `team.md` → `project.md` の
順に解決され（最も限定的な空でない記述が勝ちます）、bolt-plan のマーカーは、
この解決済みの姿勢に対する参考情報です（`PRACTICES_OVERRIDE` /
`bolt-plan-marker-conflict`）。既定のウォークでは、ワーキングスケルトンゲートは
スコープ内で最初の構築 EXECUTE ステージです。
ステージ 3.6（ビルドとテスト）および 3.7（CI パイプライン）は、すべてのユニット
を対象に最後に**一度だけ**実行します。

```
Default walk (stage-major):
  First in-scope Construction EXECUTE stage for every Unit
  → Walking-skeleton gate
  → Ladder prompt (fires once): "Continue autonomously" or "Gate every Bolt"
  Then the next stage for every Unit, code-generation last

Opt-in (`Construction Iteration: unit-major`):
  Each Unit through every per-unit stage, then the next Unit

After all Units:
  3.6 Build and Test (runs once across the full codebase)
  3.7 CI Pipeline    (runs once, conditional)
```

各設計ステージファイル（3.1～3.4）は、QUESTION-ONLY および ARTIFACT-ONLY
の実行モードをサポートします。詳細は各ステージファイルを参照してください。
コード生成の手順 3 の**計画の承認は、構築中を含め、生成前に必ず
ハードストップ**します。通常の構築時に**エンジンによって抑制**される
のは、その手順 7 のユニット単位の完了承認ゲートだけであり、最後のユニットが
確定した後に単一のステージレベルの完了ゲートに置き換えられます。自律スウォーム
の下では、このゲートは最終の DAG バッチが収束した後にのみ発火します（中間
バッチはゲートなしでマージされます）。ユニット単位の完了ゲートは
直接起動（例: `/aidlc --stage code-generation`）では残ります。

**コンストラクションの反復順序（オプトイン）。** 既定では、エンジンはユニット単位
のコンストラクションステージをステージ優先で反復します。すべてのユニットに 3.1 を
実行してから、すべてのユニットに 3.2 を実行する、といった順序で、3.5 コード生成が
すべてのユニットで最後になります。状態ファイル
の「ランタイム状態」見出し配下に `Construction Iteration: unit-major` が記録されて
いる場合（デリバリー計画で `aidlc-state.ts set-construction-iteration unit-major`
により設定するか、人が設定します）、エンジンは代わりにユニット優先で処理します。
実行単位の構築順序にある各ユニットについて、次のユニットを開始する前に 4 つの
設計文書（3.1～3.4）を作成し、続けてそのコードを生成（3.5）します。つまり最初の
動くコードは、すべてのユニットの設計後ではなく、1 ユニットの設計後に生まれます。
コード生成のユニット単位のプラン承認（手順 3）は生成前に引き続きハードストップし、
このノブが設定されている間は自律的コンストラクションのスウォームは発火しません
（構築の所有者はこのウォークであり、実行単位の構築順に直列で進みます。自律
スウォームモードの下での並列バッチはステージ優先の領分です）。ステージごとの承認ゲートの数と
仕組みは変わりません。ユニット優先では、コード生成を含むユニットごとのグリッド
全体を完了した後に、ステージ順で遅れて発火し、ステージごとに 1 回の人による承認を
行います。これを有効に
するのは厳密に `unit-major` という値だけで、未設定または `stage-major` が既定です。

**ユニット単位バッチウェーブ（任意、ステージ優先のみ）。** 既定のステージ優先
ウォークでは、エンジンは 4 つのインライン設計ステージ（3.1〜3.4）のいずれかに
対して `directive.wave` を発行することが **できます**（MAY）。ウェーブは自己修復
された 1 つの DAG スナップショットから導出され、コンダクターが
`runtime-graph.json` を読んだり兄弟パスを導出したりすることはありません。
コード生成（3.5、`workspace_requires: true`）は **決してウェーブ対象になりません**。
並行するビルダーが共有ワークスペースへの書き込みで衝突するためであり
（スウォーム経路のユニットごとのワークツリーは、まさにこの分離のために存在します）、
またそのステップ 3「プラン承認」はあらゆる実行モードで必須のハードストップであり、
ビルダーの戻りメッセージへ折り畳めないためです。

各エントリは、種別に応じて解決された `consumes`、存在しない `consumes` の明示、
すべての `produces`、該当する必須の部分集合、ユニットローカルの日誌パス、ビルド
状態、対レビューの状態、そしてウェーブ完了受領記録がまだ必要かどうかを運びます。
ビルダーは親のステージファイル、インラインコンテキストのロスター、警告、蓄積された
ステアリング内容をそのまま受け取ります。ブロックされたビルダーが差し止めるのは
該当する必須パスであり、任意パスや種別上免除されたパスではありません。ビルドと
レビューの後、`unit complete --wave` がライブエントリを検証し、ユニット日誌の
エントリを親日誌へ冪等に集約し、`UNIT_COMPLETED` を発行します。エンジンは、該当
するすべてのユニットがそれらの証跡を揃えるまで現在のバッチを保持し、その後に依存
する後続バッチまたは単一のステージゲートを許可します。ウェーブは
`Construction Iteration: unit-major` では決して適用されず、並列ディスパッチの
プリミティブを持たないハーネスはエントリを直列に処理します。完全な契約は
`stage-protocol-construction.md` §「ユニット単位バッチウェーブ」を参照してください。

**並列バッチ。** 2 つ以上のユニットが依存関係の充足を共有し、互いに依存していない
場合、コンダクターは 1 つのアシスタントメッセージで N 回の `Task` 呼び出しを
発行し、そのコード生成ステージを並行して実行します。自律スウォームの下では、
エンジンはすべての DAG バッチを収束させたうえで、コード生成のステージゲートを
**1 回だけ**提示します — 中間バッチはゲートなしでマージされます。監査イベント
（`BOLT_STARTED`、`BOLT_COMPLETED`）はスウォーム経路でユニット／ワークツリー
ごとに発行され、`SWARM_COMPLETED` がバッチを閉じます。既定のゲート付き実行では
`BOLT_*` は記録されません。

**失敗時の処理。** コード生成の失敗は自律モードにかかわらず、常に構築を停止します。
選択肢は再試行（失敗したユニットだけを再実行）、スキップ（`[S]` を記録して続行。
依存するユニットも失敗する可能性があります）、または中止です。並列バッチ内で成功
した兄弟の実行単位は、`[x]` の状態と成果物を維持します。正規仕様については
`stage-protocol-construction.md` の §「構築の実行単位ゲート」を参照してください。

## ステージ 3.1: 機能設計

### メタデータ

| 項目 | 値 |
|------|----|
| ステージ | 3.1 |
| フェーズ | 構築 |
| 実行 | CONDITIONAL（実行計画に従う） |
| 条件 | 新しいデータモデル、複雑なビジネスロジック、またはビジネスルールの設計が必要。新しいビジネスロジックのない単純なロジック変更ならスキップ。 |
| ユニット単位 | はい |
| 主担当エージェント | AIDLC アーキテクトエージェント |
| 支援エージェント | AIDLC 開発者エージェント |
| モード | インライン |
| 入力 | 作業ユニット定義、ストーリーマップ、要件、ドメイン設計成果物 |
| 出力 | `<record>/construction/{unit-name}/functional-design/` — 機能仕様、ルール、エンティティ、条件付き: フロントエンドコンポーネント |

### 目的

単一の作業ユニットについて、ビジネスロジック、ドメインモデル、ルールを設計します。
AIDLC アーキテクトエージェントが主導し、AIDLC 開発者エージェントが技術的実現可能性の
入力を提供します。

### 入力

- `<record>/inception/units-generation/unit-of-work.md` からのユニット定義
- `<record>/inception/units-generation/unit-of-work-story-map.md` からの割り当て済みストーリー
- `<record>/inception/requirements-analysis/requirements.md` からの要件
- `<record>/inception/domain-design/` からのドメイン設計成果物

### 手順

1. **ユニットコンテキストを読む** — ユニット定義、割り当て済みストーリー、要件、
   ドメイン設計成果物を読みます。

2. **機能設計計画を作成する** — ユニットのスコープを分析し、コンテキストに適した
   質問と `[Answer]:` タグを用いて、次の場所に質問ファイルを作成します。
   `<record>/construction/{unit-name}/functional-design/functional-design-questions.md`
   着目点:
   - ビジネスロジックのワークフローとアルゴリズム
   - ドメインモデルとエンティティ関係
   - ビジネスルール、制約、検証ロジック
   - データフローと変換
   - 他ユニットまたは外部システムとの統合点
   - エラー処理とエッジケース
   - フロントエンドコンポーネント（コンポーネント階層、プロパティ／状態、
     操作フロー、フォーム検証）
   - ビジネスシナリオ（エンドツーエンドのユーザージャーニー、正常／異常パス、
     並行性のエッジケース）

3. **回答を収集して分析する** — `stage-protocol.md` の質問フローに従って回答を
   収集します（対話モードの選択を提示し、回答を集め、ファイルへ書き戻す）。
   曖昧さの分析は必須です。
   - 曖昧な回答を特定する（「混在」「わからない」「場合による」「おそらく」など）
   - 回答間の矛盾を確認する
   - 成果物生成に必要な欠落詳細に印を付ける
   - 曖昧さが 1 つでもあれば、フォローアップ質問を作成し、解決してから進む

4. **成果物を生成する** — 次を
   `<record>/construction/{unit-name}/functional-design/` に生成します。
   - **機能仕様**: ユニットのビジネスロジック向けの詳細な
     アルゴリズム、ワークフロー、データ変換、処理順序、決定木
   - **ルール**: 決定ルール、検証ロジック、制約、ポリシー、条件付き
     振る舞い、ビジネス不変条件
   - **エンティティ**: エンティティ、関係、データ構造、属性、
     ライフサイクル状態、エンティティ相互作用パターン
   - **フロントエンドコンポーネント**（条件付き — ユニットにフロントエンド／UI が
     含まれる場合のみ）: コンポーネント階層、プロパティ／状態設計、操作フロー、
     フォーム検証ルール、API 統合点

5. **完了を準備する** — ユニットの機能設計成果物を検証します。状態は編集せず、
   ゲート結果を `aidlc-orchestrate.ts` を通じて報告します。

6. **完了** — 完了メッセージと承認ゲートを提示します。

### 出力

| 成果物 | 説明 |
|--------|------|
| 機能仕様 | アルゴリズム、ワークフロー、データ変換、処理順序、決定木 |
| ルール | 決定ルール、検証ロジック、制約、ポリシー、条件付き振る舞い |
| エンティティ | エンティティ、関係、データ構造、属性、ライフサイクル状態 |
| フロントエンドコンポーネント | （条件付き）コンポーネント階層、プロパティ／状態、操作フロー、フォーム検証、API 統合 |



### 承認ゲート

厳格な 2 選択肢: Approve / Request Changes。

### 注記

- 質問ファイルはステージ成果物と同じ場所に置きます。
  `<record>/construction/{unit-name}/functional-design/functional-design-questions.md`
- フロントエンドコンポーネント成果物は、ユニットにフロントエンド／UI 作業が
  含まれる場合のみ生成します。
- すべての質問は 3 モード対話フロー（Guide me / I'll edit the file / Chat）を
  使用します。

## ステージ 3.2: NFR 要件

### メタデータ

| 項目 | 値 |
|------|----|
| ステージ | 3.2 |
| フェーズ | 構築 |
| 実行 | CONDITIONAL（実行計画に従う） |
| 条件 | パフォーマンス、セキュリティ、スケーラビリティ、信頼性、または可観測性の要件が必要、あるいは技術スタック選定が必要。NFR 要件がなく技術スタックが既に決まっている場合はスキップ。 |
| ユニット単位 | はい |
| 主担当エージェント | AIDLC アーキテクトエージェント |
| 支援エージェント | AIDLC 開発セキュリティ運用エージェント、AIDLC コンプライアンスエージェント、AIDLC 品質エージェント |
| モード | インライン |
| 入力 | 機能設計成果物、要件、リバースエンジニアリング成果物 |
| 出力 | `<record>/construction/{unit-name}/nfr-requirements/` — パフォーマンス要件、セキュリティ要件、スケーラビリティ要件、信頼性要件、可観測性要件、技術スタック決定 |

### 目的

単一ユニットについて、パフォーマンス、セキュリティ、スケーラビリティ、信頼性、
可観測性、技術選定にわたる非機能要件を定義します。AIDLC アーキテクトエージェントが主導し、
AIDLC 開発セキュリティ運用エージェントがセキュリティ入力、AIDLC コンプライアンス
エージェントが規制入力、AIDLC 品質エージェントがテスト容易性と測定可能性の入力を
提供します。

### 入力

- `<record>/construction/{unit-name}/functional-design/` からの機能設計成果物
  （存在する場合）
- `<record>/inception/requirements-analysis/requirements.md` からの要件
- `aidlc/spaces/<active-space>/codekb/<repo>/` からのリバースエンジニアリング成果物
  （存在する場合）

### 手順

1. **先行成果物を読む** — 機能設計成果物（存在する場合）、要件、
   リバースエンジニアリング成果物を読みます。

2. **NFR カテゴリを評価する** — 次の NFR カテゴリでユニットを分析します。
   - **パフォーマンス**: 応答時間、スループット、レイテンシ目標、リソース使用率
   - **セキュリティ**: 認証、認可、データ保護、コンプライアンス要件
   - **スケーラビリティ**: 負荷処理、成長予測、スケーリング戦略

- ブラウンフィールド: ファイルをその場で変更する。次のような複製は作らない
  `ClassName_modified.java`
- テスト自動化のため、対話的な UI 要素に `data-testid` 属性を付ける
- レビューの前に、このユニットが作成・変更・削除したアプリケーションソースの
  パスをすべて列挙する、エンジン必須の随伴ファイル `source-manifest.json` を書く。
  シェルコマンド、スキャフォールディング、ジェネレーターが書いたファイルも含める
- NFR 要件、NFR 設計、および Testing Contract のカバレッジ床に由来する測定可能な
  品質目標は、入力であって提案ではない。ステップを通すために、定義済みの目標を
  緩和・引き下げ・無効化してはならない（テストやビルド設定のしきい値設定を含む）。
  代わりにギャップを表面化させる。

### 入力

- `<record>/construction/{unit-name}/functional-design/` からの機能設計
  （存在する場合）
- `<record>/construction/{unit-name}/nfr-requirements/` からの NFR 要件
  （存在する場合）
- `<record>/construction/{unit-name}/nfr-design/` からの NFR 設計（存在する場合）
- `<record>/construction/{unit-name}/infrastructure-design/` からの
  インフラストラクチャ設計（存在する場合）
- `<record>/inception/domain-design/` からのドメイン設計
- `<record>/inception/units-generation/unit-of-work.md` からのユニット定義
- `<record>/inception/units-generation/unit-of-work-story-map.md` からの
  ストーリーマップ

### 手順

このステージは**二部構成**です。計画の後に生成を行います。

#### 第 1 部 — 計画（手順 1～3）

1. **ユニット成果物をすべて読む** — 現在のユニットの設計成果物をすべて読みます
   （機能設計、NFR 要件、NFR 設計、インフラストラクチャ設計、ドメイン設計、
   ユニット定義、ストーリーマップ）。

2. **コード生成計画を作成する** — 各実装ステップにチェックボックスを付けた詳細計画を
   次の場所に作成します。
   `<record>/construction/{unit-name}/code-generation/code-generation-plan.md`
   ストーリーからコードステップへの追跡可能性を含め、各計画ステップを実装する
   ユーザーストーリーへ対応付けます。

   `aidlc-testing-posture.ts render` を実行し、その完全な
   `## Testing Contract` JSON ブロックを計画へ貼り付けます。リゾルバは
   org/team/project の Testing Posture セクションを加法的に読みます。プロジェクトの
   カバレッジや統合に関する注記は適用されたままですが、チームの方法論を消し去る
   ことはありません。矛盾する、より狭い方法論は拒否されます。

   この契約は、方法論固有の計画プロファイルを提供します。

   - **TDD** — 該当するすべてのテスト可能な層（データ、リポジトリ、ビジネス
     ロジック、API、フロントエンド）に対する Red/Green/Refactor。
   - **BDD** — 観測可能な機能スライスの前に実行可能な振る舞いシナリオを書き、
     その後に層をまたぐ実装、シナリオのグリーン化、リファクタリングが続きます。
     層ローカルの TDD へは変換されません。
   - **ATDD** — 層をまたぐ完全な機能実装の前に実行可能な受け入れテストを書き、
     その後に受け入れテストのグリーン化とリファクタリングが続きます。
   - **カスタム／混合** — 確認済みの正確な順序がそのまま維持されます。シナリオ
     ファーストの BDD と、実装後の下位レベルユニットテストのような組み合わせも
     含みます。
   - **テスト後書き** — 該当するすべてのテスト可能な層に対して、実装の後に
     テストを書きます。

   グリーンフィールドの計画は、最初の Red／シナリオ／受け入れステップの前に
   最小限の実行可能なテストコマンドをブートストラップします。ブラウンフィールドの
   計画は、既存のコマンドを先に検証します。選択されたテスト戦略が量／種類を
   与え、スコープがその床（カバレッジ/CI、対象を絞った回帰、または追加の床
   なし）を加えます。どちらの義務も他方を置き換えません。Minimal の下では、
   バグ／セキュリティの対象を絞った回帰が、欠陥を再現できる最も狭いレベルで
   ある場合に限り、統合/E2E テストを 1 つ追加できます。

   **計画へのテストファイル含有は必須です。** 計画には必ず次のステップを含めます。
   - ユニットテストファイル（主要振る舞いをカバーするコンポーネント／モジュールごと）
   - テスト設定（テストランナー設定、または同等）

   計画がテストファイルのステップを省略している場合、ユーザーへ提示する前に
   追加しなければなりません。テストはビルドとテストへ先送りしません。あの
   ステージは検証と拡張であり、ゼロからの作成ではありません。

   明確な実行順序と追跡性のため、各計画ステップに連番を付けます
   （手順 1、手順 2、など）。

   あわせて、計画の承認より前に
   `<record>/construction/{unit-name}/code-generation/unit-test-instructions.md`
   も作成します。有効なテスト戦略に合わせます。
   - **Minimal**: 要件駆動のユニットテスト（要件ごとに 1 テスト、コンポーネント
     ごとに正常系の下限）、合計でおよそ 5～15 テスト
   - **Standard**: コンポーネントごとに 5～8 テスト、主要な振る舞いをカバー
   - **Comprehensive**: コンポーネントごとに 10～15 テスト、網羅的にカバー

   テストフレームワークのセットアップと設定、最初のテストファーストサイクルの
   前に利用可能な正確な実行可能コマンド、期待するカバレッジ目標、モック／スタブの
   指針、テストデータ管理を含めます。
   すべての実行コマンドは、正確なテストファイルパスまたは正確なユニットフィルタに
   より、このユニットへスコープを限定しなければなりません。ビルドとテストは
   すべてのユニットのコマンドを実行するため、`npm test` のようなプロジェクト全体を
   対象とする素のコマンドは許容されません。

   ユニットテスト指示のサマリーは、計画サマリーと合わせて提示します。

3. **計画の承認** — `code-generation-plan.md`、その Testing Contract、および
   `unit-test-instructions.md` について承認を求めます。改訂の場合は、まず以前の
   `[Answer]:` を空欄へリセットします。両ファイルが最終化された後に
   `aidlc-testing-posture.ts fingerprint --unit <unit>` を実行し、その後
   `<record>/construction/{unit-name}/code-generation/code-generation-questions.md`
   を、その `[Approval Fingerprint]`、**Plan Approval** の質問、空欄の
   `[Answer]:` で作成またはリセットし、構造化質問として提示してターンを
   停止します。
   - 「計画を承認」— コード生成へ進む
   - Request Changes — 計画を改訂する

   タグへの記入は、人間が応答した後にのみ行います。変更要求は記録され、必要に
   応じて両方のファイルが改訂され、契約／フィンガープリントが再生成され、
   再提示の前に Plan Approval タグはリセットされます。承認後の計画／指示の変更、
   または Testing Posture／スコープ／戦略／種別の変更はフィンガープリントを
   無効化し、承認を再開します。転送ループの継続は決して承認ではありません。

#### 第 2 部 — 生成（手順 4～7）

4. **コードを生成する** — 委任する前に、ユーザーへ次を表示します。
   「[N] 件の計画ステップについてコードを生成します。プロジェクトの複雑さに
   より数分かかることがあります。完了時にサマリーを示します。」

   `Task` ツールで AIDLC 開発者エージェントのサブエージェント
   （`subagent_type="aidlc-developer-agent"`）へ委任します。

   **サブエージェントへ渡すコンテキスト:**
   - プロンプト最初の 1 行として、正確な対象マーカー
     `AIDLC-UNIT: <directive.unit>`（`unit` を持たない単一反復ディレクティブの
     場合は現在のユニット名）。文脈上の依存関係に追加のマーカーは付けません。
   - 2 行目として、承認済み計画からの
     `AIDLC-TESTING-CONTRACT: <contract_sha256>`。ディスパッチガードは、欠落・
     相違・陳腐化したハッシュを拒否します。
   - `agents/aidlc-developer-agent.md` の主担当ペルソナと、
     `.claude/knowledge/aidlc-developer-agent/` のナレッジ（サブエージェントは
     会話履歴にアクセスできないためプロンプトに含める）
   - **現在のユニットのみ**の設計成果物（全ユニットではない）
   - インセプションフェーズ成果物それぞれの 1～2 行サマリーとファイルパス
     （要件サマリー、ストーリーサマリー、アプリ設計サマリー）— 全文が必要なら
     サブエージェントが個別ファイルを読めます
   - 承認済みのコード生成計画（全文）
   - 承認済みのユニットテスト指示（全文）
   - プロジェクトワークスペースの詳細（言語、フレームワーク、規約を
     `aidlc-state.md` から）
   - 各計画ステップを順に実行し、完了時にチェックボックスを付ける指示
   - 承認済みの Testing Contract が正典です。サブエージェントは独立して
     memory を再解決せず、承認済みの TDD、BDD、ATDD、テスト後書き、または
     カスタム／混合プロファイルをそのまま実行します。
   - NFR 要件、NFR 設計、および Testing Contract のカバレッジ床に由来する
     測定可能な品質目標は、入力であって提案ではありません。サブエージェントは、
     ステップを通すために、定義済みの目標（テストやビルド設定のしきい値設定を
     含む）を決して緩和・引き下げ・無効化してはならず、代わりにギャップを
     表面化させなければなりません。

   **コンテキスト予算:** 現在のユニットの設計成果物だけを渡し、全ユニット分の設計成果物は渡しません。
   インセプション成果物は全文埋め込みではなく、ファイルパス付きで要約します。
   サブエージェントはワークスペース内にすべてのコード、テストファイル、設定
   成果物を生成します。

5. **コードサマリーとソースマニフェストを生成する** — サブエージェント完了後、
   次を作成します。
   `<record>/construction/{unit-name}/code-generation/code-summary.md`
   記載内容:
   - 作成／変更したファイル
   - 主要な実装上の決定
   - テストカバレッジの要約
   - 計画からの逸脱

   あわせて
   `<record>/construction/{unit-name}/code-generation/source-manifest.json`
   も作成します。これは厳格なバージョン 1 の JSON 随伴ファイルであり、宣言された
   `produces[]` 成果物ではありません。`stage: "code-generation"`、正確なユニット名、
   そしてこのユニットが作成・変更・削除したアプリケーションソースのパス
   （シェル、スキャフォールディング、ジェネレーターが書いたファイルを含む）を
   すべて含む `writes` 配列を記録します。パスは POSIX 相対で、グロブや `..` は
   使いません。末尾の `/` は生成されたディレクトリツリーを主張します。メイン
   ワークスペースのマルチリポジトリ実行では、各エントリが記録済みの `repo` を
   名指しします。実行単位をホストするワークツリー内では、パスは選択された
   リポジトリからの相対で、`repo` は省略します。

   エンジンはこのスキーマを検証し、これがない終端のユニット単位レビューの記録を
   拒否します。そのバイト列と主張は `Unit Source Fingerprint` に組み込まれ、
   新鮮なレビュー済みマニフェストのいずれにも含まれないステージソースパスの
   変更は完了をブロックします。

6. **完了を準備する** — ユニットのコードとサマリー成果物を検証します。
   状態は編集せず、ゲート結果を `aidlc-orchestrate.ts` を通じて報告します。

7. **完了** — 完了メッセージと承認ゲートを提示します。

### 出力

| 成果物 | 説明 |
|--------|------|
| コード生成計画 | チェックボックス、ストーリー追跡性、手順順序付きの詳細計画 |
| コード生成質問 | 永続化された Plan Approval の質問と明示的な人間の回答 |
| ユニットテスト指示 | ユニットごとのセットアップ、スコープ限定の実行コマンド、カバレッジ、モック、テストデータ |
| コードサマリー | 作成／変更ファイル、決定、テストカバレッジ、計画からの逸脱 |
| traceability.json | 割り当てられた上流 ID をコード／テスト対象でカバーする構造化データ |
| source-manifest.json | エンジン必須の厳格な随伴帰属インデックス。意図的に `produces[]` には含めない |
| （アプリケーションコード） | ワークスペースルートへ書き出された全ソース、テスト、設定 |



### 承認ゲート

厳格な 2 選択肢: Approve / Request Changes。

### 注記

- **二部構成**: 計画フェーズ（手順 1～3）はユーザー対話と計画承認付きでインライン
  実行します。生成フェーズ（手順 4～7）は `Task` ツール経由で AIDLC 開発者
  エージェントのサブエージェントへ委任します。構築の大半のステージが完全に
  インラインである点と異なります。
- **開発者エージェントのサブエージェント**: コード生成はインライン実行ではなく、
  `subagent_type="aidlc-developer-agent"`（`Task` ツール経由の委任）を使います。
  構築でサブエージェントを使う唯一のステージです。サブエージェントはセッションの
  ツール一式を継承します（AIDLC 開発者エージェントは `tools:` 許可リストを宣言しない）
  ため、読み取り・編集・書き込み・検索・シェル・ユーザー質問、および継承した
  MCP ツールに到達できます。
- **コンテキスト予算**: サブエージェントへ渡すのは現在のユニットの設計成果物のみです。
  インセプションフェーズ成果物は 1～2 行とファイルパスで要約し、必要なものだけを
  選択的に読ませます。
- **テストファイルの必須含有**: テストファイルはコード生成計画の一部でなければ
  なりません。ステージ 3.6（ビルドとテスト）はテストを検証・拡張しますが、
  ゼロからは作成しません。
- **ソースマニフェストの強制**: `source-manifest.json` はエンジンが検証するもの
  であり、Markdown の `required-sections` の対象ではありません。その厳格な
  スキーマと `Unit Source Fingerprint` が、正確パス／ディレクトリのソース主張
  すべてを拘束します。エンジンは、これが欠落または無効な場合に終端レビューを
  拒否し、新鮮なレビュー済み主張の和集合の外でソースが変更された場合にステージ
  完了を拒否します。
- **ユニットスコープの実行**: ユニットごとのテスト指示ファイルは、正確なテスト
  パスまたは正確なユニットフィルタを使うため、ユニット横断の実行ステージが
  ユニットごとにプロジェクト全体のスイートを再実行することはありません。
- **ブラウンフィールドへの配慮**: ブラウンフィールドでは、サブエージェントは
  複製を作らず既存ファイルをその場で変更します。

## ステージ 3.6: ビルドとテスト

### メタデータ

| 項目 | 値 |
|------|----|
| ステージ | 3.6 |
| フェーズ | 構築 |
| 実行 | ALWAYS（すべてのユニット完了後） |
| 条件 | すべてのユニット単位ステージ完了後に一度だけ常に実行します。 |
| ユニット単位 | いいえ（全ユニットに対して一度実行） |
| 主担当エージェント | AIDLC 品質エージェント |
| 支援エージェント | AIDLC 開発セキュリティ運用エージェント |
| モード | インライン |
| 入力 | 全ユニットのコード生成出力すべて |
| 出力 | `<record>/construction/build-and-test/` — ビルド手順、統合テスト手順、パフォーマンステスト手順、セキュリティテスト手順、ビルドとテストのサマリー、テスト結果、および条件付きの追加テスト手順ファイル |

### 目的

ユニット横断のテスト手順を生成し、ユニットごとのユニットテスト指示を取り込んだ
うえで、シェル経由でビルドとテストを実際に実行します。このステージは**全ユニット
横断**で動作し、ユニット単位ではありません。AIDLC 品質エージェントが主導し、
AIDLC 開発セキュリティ運用エージェントがセキュリティテストの専門知識を提供します。

### 入力

- `<record>/construction/*/code-generation/code-summary.md` からの全ユニットの
  コード生成出力
- `<record>/construction/*/code-generation/unit-test-instructions.md` からの
  ユニットごとのテスト指示
- 各ユニットの `nfr-requirements/` および `nfr-design/` ディレクトリ配下の
  該当するすべての成果物
- ステージレベルまたはユニット単位の `code-generation-plan.md` にある、
  承認済みのすべての `## Testing Contract`

### 手順

1. **テスト要件を分析する** — 全ユニットのコード生成サマリーとユニットごとの
   テスト指示を読みます。NFR 要件、NFR 設計、および承認済みのすべての
   Testing Contract に由来する測定可能な目標について、ソースを網羅した
   インベントリを構築します。各目標について、安定した ID、ソースのパス／
   セクション、期待値、実際の値を得るためのチェック、そしてその目標を所有する
   後続の検証ステージ（あれば）を記録します。必要なテスト種別をすべて一覧化
   します。

2. **ビルド手順を生成する** — 次を作成します。
   `<record>/construction/build-and-test/build-instructions.md`:
   - 依存関係のインストール手順
   - 環境整備（環境変数、設定ファイル、ローカルサービス）
   - ビルドコマンド（コンパイル、バンドル、トランスパイル）
   - ビルド検証手順
   - よくあるビルド問題のトラブルシューティング

3-7. **追加のテスト手順を生成する** — 有効なテスト戦略を参照し、対応する
   ユニット横断の手順ファイルを生成します。
   - **Minimal**: 追加ファイルは生成しません。ユニットテストはコード生成が
     ユニットごとにカバーします。
   - **Standard**: 主要な境界とユニット横断の相互作用について
     `integration-test-instructions.md` を生成します。
   - **Comprehensive**: 統合テスト手順に加え、パフォーマンス NFR がある場合は
     `performance-test-instructions.md` を、セキュリティ NFR がある場合は
     `security-test-instructions.md` を生成します。
   - いずれの戦略でも、プロジェクトの文脈が求める場合は、契約、エンドツーエンド、
     アクセシビリティ、その他の名前付き手順ファイルを追加します。

   すべてのファイルは `<record>/construction/build-and-test/` に置きます。
   各ファイルには、フレームワークのセットアップ、実行コマンドとフィルタ、
   カバレッジ目標、テストデータまたは環境の準備を含めます。

8. **ビルドとテストのサマリーを生成する** — 次を作成します。
   `<record>/construction/build-and-test/build-and-test-summary.md`:
   - 全体のビルド状態と前提条件
   - テスト種別インベントリ（生成したテスト種別）
   - ユニットごとのカバレッジ期待値
   - Target ID、Source、Expected、Actual、Evidence、Owning Stage、Verdict を
     持つ目標検証マトリクス（Target Verification Matrix）
   - 該当する目標は `Pending` で開始します。`N/A` が有効なのは、ソースを網羅した
     インベントリが該当する測定可能な目標を見つけられなかった場合だけです
   - 準備状況の評価（ビルド準備、テスト準備、デプロイ準備）
   - 既知の制限や未解決事項

9. **ビルドとテストを実行する** — 手順ファイルに記載したビルドおよびテスト
    コマンドを**シェル経由で**実行を試みます。

    a. **ビルド**: ビルド手順からビルドコマンドをシェルで実行し、出力を捕捉します。
    b. **ユニットテスト**: 各ユニットの
       `code-generation/unit-test-instructions.md` からコマンドを収集し、同一の
       コマンドを重複排除して、異なるコマンドごとに一度だけ実行します。コマンドは
       ユニットにスコープされているはずです。プロジェクト全体を対象とするコマンドが
       含まれる場合は一度だけ実行し、ユニットごとには実行しません。二重計上せずに
       ユニットごとの合否を報告します。
    c. **統合テスト**（該当する場合）: 統合テストコマンドを実行し、結果を捕捉します。
    d. **その他の該当するチェック**: パフォーマンス、セキュリティ、契約、E2E、
       アクセシビリティ、その他の生成済み手順ファイルにある該当するコマンドを
       すべて実行します。先送りできるのは、デプロイ済みまたは本番相当の環境を
       必要とし、かつ現在の実行計画に所有する検証ステージが名指しされている
       チェックだけです。そのステージと期待される証拠パスを記録します。その目標は
       `Unverified` のままであり、このステージを成功にすることはできません。
       予定された所有ステージがなければ、単に `Unverified` です。
    e. **最終化して結果を報告する**: あらゆる終了経路で、次を作成または更新します。
       `<record>/construction/build-and-test/test-results.md` と
       `build-and-test-summary.md`
       - ビルド状態（成功／失敗＋出力）
       - テスト結果（合計、成功、失敗、スキップ）
       - 失敗の詳細（テスト名、アサーション、スタックトレース）
       - カバレッジレポート（テストフレームワークが対応する場合）
       - 最終化された目標検証マトリクス。該当するすべての目標が、実際の値、証拠、
         所有ステージ、そして最終的な `Met`、`Not Met`、`Unverified` のいずれかの
         判定を持ちます。手順 9 の後に `Pending` の判定は残りません。
       - `## Loop-Back Log`（失敗エスカレーションはしごの段 3 または段 4 が
         ループバックを発火させた場合のみ）: 試行ごとに 1 つの
         `### Loop-back N -- <ISO timestamp>` エントリ（診断／根本原因ステージ／
         計画された修正／推定影響）。追記専用で、再実行後も残ります
         （ループバック再入時は Modify であり、決して Redo ではありません）。

    **失敗エスカレーションはしご:** ビルドまたはテストのコマンドが失敗した場合、
    あるいは該当する目標が `Not Met` または `Unverified` の場合、このステージは
    失敗しています。どの失敗種別でも、同じはしごへ入る前にマトリクスとサマリーを
    最終化します。目標の引き下げ・緩和・無効化は、決して許容される修正では
    ありません。

    1. **ステージ内修正（最大 2 回）** — このステージ自身の担当範囲内にある
       根本原因（テスト設定、ビルドスクリプト、環境整備、または実行可能な目標
       チェック）向け: 証拠を読み、失敗している設定や足場を特定し、修正を適用し、
       失敗したステップを再実行し、目標マトリクスを更新します。
    2. **分類して影響を見積もる** — ステージ内の試行を使い果たしたとき、または
       診断が上流を指すとき: 根本原因が生成されたソースまたはテストコードに
       あるのか — 欠陥の大小を問わず — あるいはコード生成のアプローチ選択
       （ライブラリ／バージョン、コンテナイメージ、インスタンスタイプ、
       アルゴリズム、フラグ）にあるのかを判断します。交換可能な次元での修正を
       見つけ、その影響（工数、金銭的コスト、リスク）を必ず見積もります。
       影響を見積もっていない工数の思い込みで、実行可能な経路をスコープ外と
       宣言してはなりません。
    3. **自律的な有界ループバック** — `Construction Autonomy Mode:
       autonomous` であり、影響見積もり済みの修正が存在し、`## Loop-Back Log`
       のエントリが 3 件未満の場合: 診断＋影響見積もり済み修正を記録し、
       エンジン経由でコード生成へジャンプして戻り、Construction プロトコル
       モジュール（`aidlc-common/protocols/stage-protocol-construction.md`）の
       「Build-and-Test failure loop-back」に従った確定認識ルートで前方へ
       リプレイします。失敗した実行のゲートは提示されず、その学習の儀式は
       最終的に成功する実行へ委ねられます。
    4. **停止して確認（halt-and-ask）** — ゲート付き／未設定モード、上限の
       使い果たし、または特定可能な修正がない場合: 失敗を記録し、Construction
       プロトコルモジュール
       （`aidlc-common/protocols/stage-protocol-construction.md`）の
       halt-and-ask 質問を提示します — 候補の修正が存在する場合は影響見積もり
       付きの 3 選択肢バリアント（Retry with fix [推定影響] / Accept failure /
       Abort）、段 2 で修正が見つからなかった場合は修正なしの 2 選択肢
       バリアント（Accept failure / Abort）です。

    **ループバックのリプレイ経路:** コード生成がユニットのライフサイクル
    受領記録を一度も使用していない場合、保持された成果物は全カバー済みの
    `gate: true` ファストパスを取れます。そのゲートの前に、計画された修正と
    決定論的な Modify/Keep の判断を適用します。ライフサイクル行が 1 つでも
    存在すると、受領記録モードは固定化され、ジャンプはユニット単位の作業を
    再発行します。`unit start` / `unit complete` を再発行し、対象ユニットへ
    Modify を、残りへ Keep を適用し、宣言されたレビュアーをユニットごとに
    実行します。`STAGE_JUMPED` は以前のすべてのレビューを無効化するため、
    どちらの経路も、確定／承認ゲートの前に、該当するすべてのユニットについて
    現在試行の新しい `REVIEW_COMPLETED` を必ず記録しなければなりません。
    unit-major の下では自律スウォームは決して発火せず、リプレイは直列の
    ユニット単位ウォークに従い、それでも追加の人間のターンを必要としません。

    リプレイは、既に承認済みのコード生成計画を修復します。その Plan Approval の
    `[Answer]:` を保持し、差分を Loop-Back Log に記録し、ゲートでの
    「Retry with fix」を改訂されたアプローチに対する人間の再承認として扱います。

    **スウォームの安価な経路:** ジャンプは新しい正確なステージ試行の
    `Run floor` 境界トークンを生成するため、古い収束行はカウントされません。
    古い worktree／ブランチを破棄し、新しい `prepare` を実行します。`finalize`
    は現在の prepare スタンプを要求するため、それらを新しい試行へ引き継ぐことは
    できません。まず `check` を実行します。グリーンなユニットはビルダーの
    ターンをスキップできますが、`finalize --claimed` へ入る前に、新しい
    worktree 内で終端の現在試行レビュアー受領記録が依然として必要です。
    `finalize` は、その受領記録の現在の成果物フィンガープリントと試行スタンプの
    両方を検証します。

    単一ステージ実行（`--single`）は段 2 で停止します — 移動すべき
    メインワークフローの位置が存在しないためです。影響見積もり済みの選択肢は
    記録され、その実行の分離実行サマリーで提示されます。

    **成功時:** 成功の準備状況判定には、すべてのコマンドが成功し、該当する
    すべての目標が `Met` であること — または該当する目標がない場合は説明付きの
    単一の `N/A` 行 — が必要です。

10. **完了を準備する** — ビルド／テストの証拠を検証します。ステージや
    フェーズの状態は編集せず、報告されたゲート結果が遷移を所有します。

11. **完了** — 完了メッセージと承認ゲートを提示します。

### 出力

| 成果物 | 説明 | 条件 |
|--------|------|------|
| ビルド手順 | 依存関係インストール、環境整備、ビルドコマンド、トラブルシューティング | 常時 |
| 統合テスト手順 | 前提条件、ユニット横断テスト、外部依存、データ準備 | Standard／Comprehensive |
| パフォーマンステスト手順 | 負荷テスト、NFR シナリオ、ベースライン、ストレス／ソーク | NFR パフォーマンスがある場合 |
| セキュリティテスト手順 | SAST／DAST、認証テスト、インジェクションテスト、コンプライアンス | NFR セキュリティがある場合 |
| 契約テスト手順 | コンシューマ駆動契約、スキーマ検証、API 互換 | マイクロサービスの場合 |
| エンドツーエンドテスト手順 | ブラウザ自動化、ユーザージャーニー、クロスブラウザ | UI 主導の場合 |
| アクセシビリティテスト手順 | WCAG 準拠、スクリーンリーダー、キーボード操作 | ユーザー向け UI の場合 |
| ビルドとテストのサマリー | 全体状態、テストインベントリ、カバレッジ、準備状況評価 | 常時 |
| テスト結果 | 実際のビルド／テスト実行結果、合否、カバレッジ | 常時 |



### 承認ゲート

厳格な 2 選択肢: Approve / Request Changes。

### 注記

- **実際のシェル実行**: このステージはテスト手順を文書化するだけでなく、シェル経由で
  ビルドとテストコマンドを実際に実行し、実結果を捕捉します。コードベースに対して
  実コマンドを実行する数少ないステージのひとつです。
- **品質目標の証拠**: ソースを網羅したマトリクスは、あらゆる終了経路で最終化
  されます。デプロイ環境が必要なチェックは後続の所有ステージを名指しできますが、
  `Unverified` のままです。`Not Met` と `Unverified` はどちらも失敗のはしごへ
  入ります。
- **失敗エスカレーションはしご**: ステージ内修正は 2 回までに制限されます。
  根本原因が上流の生成コードまたはコード生成のアプローチ選択にある場合、この
  ステージは修正を分類してその影響を見積もり、コード生成への有界な自律
  ループバック（最大 3 回、test-results.md の追記専用 `## Loop-Back Log` で
  カウント）を実行するか、影響見積もり付きの halt-and-ask 質問を提示します。
  Construction プロトコルモジュール
  （`aidlc-common/protocols/stage-protocol-construction.md`）の
  「Build-and-Test failure loop-back」を参照してください。再入は確定認識型で、
  承認済み計画を保持し、該当するすべてのコード生成ユニットが現在試行の新しい
  レビューを得るまでゲートに到達できません。
- **条件付きテスト種別**: パフォーマンステスト、セキュリティテスト、契約テスト、
  エンドツーエンドテスト、アクセシビリティテストは、関連条件が満たされる場合のみ
  生成します（NFR 要件の存在、マイクロサービスアーキテクチャ、UI 主導アプリ、
  ユーザー向けインターフェース）。
- **ユニット横断スコープ**: ユニット単位のステージ 3.1～3.5 と異なり、ビルドとテストは
  すべてのユニットが生成したコード全体に対して一度実行します。個別ユニットではなく、
  統合されたコードベースを検証します。
- **フェーズ完了**: このステージ（該当すれば 3.7 とともに）が構築フェーズの終わりを
  示します。最終の承認済み報告により、エンジンが構築を完了としてマークし、
  運用への遷移を原子的に行います。

## ステージ 3.7: CI パイプライン

### メタデータ

| 項目 | 値 |
|------|----|
| ステージ | 3.7 |
| フェーズ | 構築 |
| 実行 | CONDITIONAL（十分な CI が既にある場合はスキップ） |
| 条件 | CI パイプラインの作成または大幅な変更が必要な場合に実行 |
| ユニット単位 | いいえ（全ユニットに対して一度実行） |
| 主担当エージェント | AIDLC パイプライン・デプロイエージェント |
| 支援エージェント | （なし） |
| モード | インライン |
| 入力 | ステージ 3.5 のコード生成出力、ステージ 3.6 のビルド／テスト結果 |
| 出力 | `<record>/construction/ci-pipeline/` — CI 設定、品質ゲート、CI パイプライン質問 |

### 目的

品質ゲート、成果物管理、ビルド／テスト自動化を備えた CI（継続的インテグレーション）
パイプラインを設定します。AIDLC パイプライン・デプロイエージェントが主導し、
支援エージェントはありません。

### 入力

- `<record>/construction/build-and-test/` からのビルド／テスト結果
- `<record>/construction/infrastructure-design/` からのインフラストラクチャ設計
  （存在する場合）
- 既存の CI 設定のためのワークスペースプロファイル

### 手順

1. **先行コンテキストを読み込む** — ビルド／テスト結果、インフラストラクチャ設計
   （存在する場合）、既存 CI 設定のためのワークスペースプロファイルを読みます。

2. **明確化の質問を生成する** — 次の質問を含むファイルを作成します。
   `<record>/construction/ci-pipeline/ci-pipeline-questions.md`
   - 使用中の CI ツールは何か？
   - ブランチ戦略は何か？
   - マージ前に必要な品質ゲートは何か？
   - 使用する成果物リポジトリは何か（ECR、S3 など）？

   例示する CI ツールと成果物ストア:

   ```
   CodePipeline, CodeBuild, GitHub Actions, Jenkins
   ECR, CodeArtifact, S3
   ```

   `stage-protocol.md` の質問フローに従います。

3. **回答を収集して分析する** — 既存インフラとチーム能力に対して CI の選択を検証します。

4. **成果物を生成する** — CI パイプライン設定（ビルド仕様やワークフロー YAML、
   または同等）、品質ゲート定義、成果物リポジトリ設定を作成します。

5. **フェーズ境界検証** — 構築から運用への検証チェックを実行します。
   - アーキテクチャからコード、テストへの整合
   - すべてのコードが設計へ追跡できること
   - 受け入れ基準に対するテストカバレッジ
   - 結果を `<record>/verification/phase-check-construction.md` へ書き出す

6. **完了を準備する** — CI と境界の成果物を検証します。ステージや
   フェーズの状態は編集せず、報告されたゲート結果が遷移を所有します。

7. **完了** — 完了メッセージと承認ゲートを提示します。

### 出力

| 成果物 | 説明 |
|--------|------|
| CI 設定 | CI パイプライン設定（ビルド仕様、ワークフロー YAML など） |
| 品質ゲート | マージ／昇格のための品質ゲート定義 |
| CI パイプライン質問 | 回答付きの明確化の質問 |



### 承認ゲート

厳格な 2 選択肢: Approve / Request Changes。

### 注記

- **フェーズ境界検証**: これは構築フェーズの最終ステージです。構築から運用への
  フェーズ境界検証チェック（`stage-protocol-governance.md` のセクション 13）を実行し、
  アーキテクチャがコードへ、コードがテストへ追跡できることを検証します。結果は
  `<record>/verification/phase-check-construction.md` に書き出します。
- **条件付き実行**: プロジェクトに十分な CI パイプラインが既にある場合、この
  ステージはスキップされます。デリバリー計画の実行計画が実行有無を決めます。
- **ユニット後実行**: ステージ 3.6 と同様、すべてのユニット単位作業の完了後に
  一度実行し、ユニット単位ではありません。

## フェーズのまとめ

構築フェーズは、段階的な構築フローにより、インセプションの設計を動作する
ソフトウェアへ変換します。

**ユニット単位ステージ（3.1～3.5）:**
- 3.1 機能設計 — ビジネスロジック、ドメインモデル、ルール（アーキテクト主導）
- 3.2 NFR 要件 — パフォーマンス、セキュリティ、スケーラビリティ、信頼性、
  可観測性、技術スタック（アーキテクト主導）
- 3.3 NFR 設計 — NFR カテゴリ向けの具体パターン（アーキテクト主導）
- 3.4 インフラストラクチャ設計 — デプロイ、サービス、監視、CI／CD
  （AWS プラットフォーム主導）
- 3.5 コード生成 — 計画＋生成の二部構成をサブエージェント経由（開発者主導）

**ユニット後ステージ（3.6～3.7）:**
- 3.6 ビルドとテスト — 手順生成＋失敗診断付きの実際のシェル実行（品質主導）
- 3.7 CI パイプライン — CI 設定＋フェーズ境界検証（パイプライン・デプロイ主導）

**主な特性:**
- ステージ 3.1～3.4 は CONDITIONAL、3.5～3.6 は ALWAYS 実行、3.7 は CONDITIONAL
- 条件付きステージはすべてデリバリー計画の実行計画に従う
- 既定のウォークはステージ優先（1 つのステージをすべてのユニットに実行してから
  次のステージへ）。オプトインの `unit-major` ウォークは、次のユニットを開始する
  前に 1 ユニットをすべてのユニット単位ステージに通す
- NFR 成果物は上流リファレンスより粒度を拡張（要件 6 ファイル、設計 6 ファイル）
- インフラストラクチャ設計は監視と CI／CD の専用ファイルを含む 5 成果物へ拡張
- コード生成はコンテキスト予算制御付きで AIDLC 開発者エージェントのサブエージェントを使用
- ビルドとテストは実コマンド実行と自動失敗診断を行う
- CI パイプラインは運用へ移行する前にフェーズ境界検証を含む

**上流リファレンスからの意図的な逸脱:**
- NFR 要件: 6 ファイル（リファレンスの 2 から拡張）
- NFR 設計: 論理コンポーネントを含む 6 ファイル（リファレンスの 2 から拡張）
- インフラストラクチャ設計: 3 ファイル — 統合された
  `infrastructure-specification.md`（デプロイ＋サービス＋共有）に加え、専用の
  `monitoring-design.md` と `cicd-pipeline.md`
- 計画／質問ファイルをステージ成果物と同じ場所に配置
