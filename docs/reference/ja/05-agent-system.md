# エージェントシステム

> 対象読者: ティア 2/3（チーム導入者、フレームワークコントリビューター）。

この章は、エージェントアーキテクチャを文書化します。具体的には、エージェントがどのように構造化され、設定され、フレームワークによって読み込まれ、またどのように追加・変更されるかを扱います。

利用者向けのエージェント説明は、[ユーザーガイド -- エージェント](../guide/06-agents.md) を参照してください。

---

## エージェントの構造

著述されるエージェントはいずれも、`core/agents/` に置かれるフラットな `.md` ファイルで、YAML のメタデータ部とそれに続く Markdown 本文から成ります。パッケージャーはそれらのペルソナを各ハーネスのエージェントサーフェスへ射影し、コンダクターは射影されたファイルを読んで、インライン作業や委譲実行を組み立てます。

### メタデータ部の契約

著述されるコアのエージェントファイルには、いずれも次の YAML メタデータ部を含めなければなりません。

```yaml
---
name: aidlc-architect-agent               # Agent identifier (matches filename without .md)
description: >                      # Brief role summary (shown in Claude Code agent list)
  System architect responsible for domain design,
  NFR design, and component decomposition.
disallowedTools: Task               # Agents cannot spawn subagents
tier: judgment                      # judgment | balanced | templated (see Agent Tiers)
---
```

| 項目 | 必須 | 説明 |
|-------|----------|-------------|
| `name` | はい | エージェント識別子。ファイル名と一致しなければなりません |
| `description` | はい | 役割の短い要約 |
| `tools` | いいえ | 任意の許可一覧です。省略すると完全なセッションツールセットを継承します。列挙するとエージェントは絞り込まれ、`mcp__<server>__<tool>` 識別子も明示しない限り継承済み MCP ツールは落ちます |
| `disallowedTools` | 著述されるコアでは必須 | `Task` を含めなければなりません。委譲を行うのはコンダクターだけです。ハーネスがネイティブに別のツールポリシー面を使う場合、パッケージャーはこの Claude 方言のキーを削除または変換します |
| `tier` | はい | `judgment`、`balanced`、`templated` のいずれかです。これは作成元側のダイヤルであり、パッケージャーが各ハーネスのネイティブなモデル／推論量キーへ射影します（後述のエージェントティアを参照）。生の `model:` / `effort:` は作成元のメタデータ部には決して現れません。これらは `dist/<harness>/` における射影結果です |

Kiro IDE はこのコア契約を別の形に射影します。`disallowedTools` を削除し、
`tools: ["read", "write", "shell"]` を追加し、機能単位にスコープされた
`permissions.rules` を追加します。`tools:` から `subagent` を省くことが、IDE の
ネイティブな語彙で同じ「入れ子の委譲を許さない」制約を担います。

### Markdown 本文セクション

メタデータ部の下では、Markdown 本文が次を定義します。

| 節 | 目的 |
|---------|---------|
| **中核責務** | そのエージェントが何を行うか |
| **連携** | 入力元／協働相手／引き渡し先 |
| **メモリフォーカス** | 関連する場合に参照する、エージェント固有のメモリトピック |
| **主要原則** | そのエージェントの行動指針 |

## 共有設定

著述された 14 体すべてのエージェントは、共通の設定ベースラインを共有します。Claude Code では、どれも `tools:` の許可一覧を宣言していないため、すべてのエージェントは**完全なセッションツールセット**とプロビジョニングされた MCP ツールを継承し、出荷時点の拒否は `disallowedTools: Task` です。他のハーネスは同じ意図をネイティブな面へ射影します。Kiro のエージェント Markdown は `disallowedTools` を省略し、Kiro CLI の委譲先 JSON は `tools` から `subagent` を省き、Kiro IDE の委譲先 `tools:` 許可も同様に委譲を除外します。

### Claude Code のセッションツールセット

Claude Code のエージェントは、次を含む組み込みツールを継承します。

| ツール | 目的 |
|------|---------|
| 読み取り | ファイルシステムからファイルを読む |
| 編集 | ファイル内で正確な文字列置換を行う |
| 書き込み | ファイルシステムへファイルを書き込む |
| ファイル照合 | 高速なファイルパターン照合 |
| 内容検索 | 高速検索器を使った内容検索 |
| ユーザーへの質問 | 対話的なユーザープロンプト（メインスレッドのステージのみ） |

### 共通の禁止 Claude Code ツール

| ツール | 理由 |
|------|--------|
| タスク起動 | エージェントは委譲されたワーカーとして動作します。`Task` 呼び出しを行うのは `SKILL.md` コンダクターだけです。Claude では `disallowedTools: Task` で強制し、他のハーネスではネイティブな拒否／許可一覧の同等機構を使います。 |

### 各ペルソナが使うことを想定されているツール

Claude Code では、すべてのエージェントが継承によりシェルとウェブ検索へ到達できます。この表が記録しているのは、方法論が各ペルソナに対してそのステージ作業の中で**使うことを期待している**かどうかであって、エージェント別の付与ではありません。Claude のペルソナを本当に制限したい場合は、任意の `tools:` の許可一覧を追加してください（その場合、`mcp__<server>__<tool>` 識別子も列挙しない限り継承済み MCP は落ちます）。

| ツール | 使用を期待する担当 |
|------|---------------------|
| シェル | クラウド基盤、開発セキュリティ、開発、品質、パイプライン配備、運用の各エージェント |
| ウェブ検索 | プロダクト、デザイン、コンプライアンスの各エージェント |

### エージェントティア

各エージェントにおける作成元側のダイヤルは `tier:` です。これはそのペルソナが行う仕事の**種類**を示し、パッケージャー（`bun scripts/package.ts`）がそれを各ハーネスのネイティブなモデル／推論量形式へ射影します。以前の挙動（バージョン 2.2.15 から 2.2.19。さらにそれ以前はキーが無効な `modelOverride:` でした）は、各エージェントごとに生の `model: opus|sonnet` を固定しており、その結果としてより大きなモデルで実行中のセッションまで強制的にダウングレードしていました。ティア射影はその固定を置き換えるものです。

| ティア | エージェント | 意味 |
|------|--------|---------|
| `judgment` | アーキテクト、クラウド基盤、コンプライアンス、コンポーザー、デザイン、開発、開発セキュリティ、プロダクト、品質 | 曖昧さの中で複数制約を推論し、その出力が下流へ波及する仕事です。決してダウングレードされず、セッションのモデルと推論量の両方を継承します |
| `balanced` | アーキテクチャレビュー、プロダクトリード | 明示的な基準に照らして新規入力をレビューする、レビュー形状の仕事です。Claude Code、Codex、opencode では中規模モデルを低い推論量で使います（Kiro、Cursor、Copilot では全ティアと同様にセッションのモデルを継承します） |
| `templated` | デリバリー、運用、パイプライン配備 | 主としてパターン追従型の出力であり、方法論自体がすでにナレッジに入っています（デリバリープラン、CI/CD YAML、運用手順書）。Claude Code、Codex、opencode では中規模モデルを低い推論量で使います（Kiro、Cursor、Copilot では全ティアと同様にセッションのモデルを継承します） |

`balanced` と `templated` は、現在どのハーネスでもまったく同一に射影されます。どちらも中規模モデルを `medium` の推論量で固定します。2 つの名前を分けて保っているのは、両者が異なる「仕事」を表しており、どちらか一方だけを他方と独立に再調整しうるからです。ティア名が 2 つあるからといって、読者が 2 つの異なる射影を推測すべきではありません。セッションの推論量を継承するティアは `judgment` だけです。

ハーネスごとの射影は次のとおりです（`core/tools/aidlc-tiers.ts` が唯一の正本です）。

| ティア | Claude Code（`.md` のメタデータ部） | Codex CLI（TOML） | Kiro CLI のエージェント JSON / Kiro IDE の `.md` | Kiro CLI の cli.json にある `chat.modelDefaults` | opencode（`.md` のメタデータ部） | Copilot（`.md` のメタデータ部） | Cursor（`.md` のメタデータ部） |
|------|-------------------------------|-------------------|--------------------------------------|-------------------------------------|-----------------------------|-----------------------------|--------------------------|
| `judgment` | `model: inherit`、`effort:` 行なし | `model`／`model_reasoning_effort` キーなし（設定のセッション既定値が適用される） | フィールドを省略（スキーマのフォールバック: ユーザーの既定モデル） | ティア項目なし | `model:`／`variant:` キーなし（`opencode.json` のセッション既定値が適用される） | 省略（セッションのモデルを継承） | `model:` を省略（セッションのモデルを継承） |
| `balanced` | `model: sonnet`、`effort: medium` | `model = "openai.gpt-5.6-terra"`、`model_reasoning_effort = "medium"` | フィールドを省略（下記参照） | ティア項目なし | `model: amazon-bedrock/global.anthropic.claude-sonnet-4-6`、`variant: medium` | 省略（セッションのモデルを継承） | `model:` を省略（下記参照） |
| `templated` | `model: sonnet`、`effort: medium` | `model = "openai.gpt-5.6-terra"`、`model_reasoning_effort = "medium"` | フィールドを省略（下記参照） | ティア項目なし | `model: amazon-bedrock/global.anthropic.claude-sonnet-4-6`、`variant: medium` | 省略（セッションのモデルを継承） | `model:` を省略（下記参照） |

この表を支える重要事実:

- **継承機構は省略です。** Claude Code では、`.md` のエージェントに `effort:` キーがないとセッションの推論量を継承し、逆に `effort:` を固定すると双方向にセッションを上書きします（固定値は下限ではなく上限です）。したがって「書かないこと」が契約なのは `judgment` だけであり、`balanced` と `templated` はどちらも `effort: medium` を固定します。Codex では、役割用 TOML に `model` がなければ、出荷済み設定のセッション既定値で起動します（codex-cli 0.139.0 と 0.142.5 で実環境検証済み。現在診断ツールが強制する最小バージョンは、コンパクト化セッションの即時リロードに対応した 0.145.0 です）。Kiro CLI では、エージェント用バージョン 1 スキーマが `model` 不在時のフォールバックを文書化しています。すなわち「指定されなければ既定モデルを使う」です。Kiro IDE も同様に、エージェント `.md` が `model:` を省略していればセッションのモデルを継承します。
- **Kiro ではモデルを固定しません。** 出荷時に固定したモデル ID は、そのモデルがユーザーのインストールで有効な場合にしか解決できません。他のモデルで動くセッションでは、委譲されたスポーンがすべて `Invalid model ID` で拒否され、しかも Kiro は Claude 方言のティア別名（`opus`/`sonnet`）を受け付けません。つまり普遍的に安全な固定値は存在しないのです。そのため Kiro ではすべてのティアが `"model"`（および `.md` フロントマターの `model:` 行）を省略し、全エージェントがセッションのモデルを継承します。`TIER_PROJECTIONS` の kiro スロットと `kiroModelDefaults()` の機構は、インストールごとに解決可能な固定機構が現れた場合に備えて、休止状態のまま残されています。
- **Kiro にはエージェント単位の推論量設定面がありません。** Kiro CLI はエージェント JSON に推論量類似キーがあると閉鎖的に失敗するため、モデルごとの推論量既定値は CLI 設定の `chat.modelDefaults[<modelId>].output_config.effort` に乗せるしかありません。どのティアもモデルを固定しないため、出荷されるのは著者が記述した条件付きの項目だけです（`claude-opus-4.8` → `xhigh`。セッションが実際にそのモデルで動く場合にのみ適用されます）。このファイルは CLI 専用であり、Kiro IDE は CLI 設定を完全に無視して、拡張機能埋め込みのモデルごとの既定値（またはユーザーの `/effort` セッション状態）を適用します。
- **Cursor でもモデルを固定しません。** Cursor で利用できるモデルはプランに依存し（Free アカウントは名前付きモデルをすべて拒否し、`Auto` しか実行できません）、モデルを固定したエージェントは下位プランでインストールが確実に失敗します。そのため Cursor ではすべてのティアが `.md` フロントマターの `model:` 行を省略し（Cursor にはエージェント単位の推論量キーがなく、推論量はモデル ID の接尾辞に乗ります）、全エージェントがセッションのモデルを継承します。`TIER_PROJECTIONS` の cursor スロットはモデル専用で、プランに依存しない固定機構が現れた場合に備えて休止状態のまま残されています。

### ティア上限（コスト上書き）

プロジェクトは、どのエージェントファイルも編集せずに、パッケージ化時点ですべての射影に上限をかけられます。

- **永続ノブ:** スペースメモリ層ファイル（`core/memory/org.md` → `team.md` → `project.md`、最後の書き手が優先）の YAML メタデータ部にある `tier_cap:` キーです。プロジェクトは組織上限を下げることも上げることもできます。例: `tier_cap: balanced` は、全ハーネスの射影で `judgment` を `balanced` へ統合します（Kiro ではどのティアもモデルを固定しないため、この上限は効果を持ちません。すべてのティアがすでにセッションのモデルを継承しています）。
- **呼び出し単位の上書き:** `AIDLC_TIER_CAP` 環境変数は、1 回のパッケージャー実行に限ってメモリ層に勝ちます（`AIDLC_TIER_CAP=templated bun scripts/package.ts`）。メモリ上限が有効な状態で一度だけ上限なしでビルドしたい場合は、最上位ティアである `judgment` を設定してください。これはメモリ層より優先され、何も制限しません（空値は上限なしではなく未設定を意味します）。

この 2 つのノブはスコープが異なります。メモリ上限はリポジトリと共に移動するため、書き込みモードでも `--check` モードでも適用されます（上限付きの配布物をコミットしたプロジェクトは、その状態で自己整合になります）。一方、環境変数は一回限りの書き込みノブであり、`--check` では無視されます。差分検知器は、コミット済み配布物が何を正当に元にしてビルドされたかを比較するため、CI やテストランナー環境に紛れた `AIDLC_TIER_CAP` が差分検知を失敗させても隠してもいけません（パッケージャーはそれを無視したとき通知を出力します）。またパッケージャーは、上限が有効な実行では毎回、どの上限がどこから来たかも表示します。

単一のエージェントだけを除外したい場合は、代わりにインストール済み `dist/<harness>/` コピー内の射影済み値を編集してください（たとえば Claude のエージェント `.md` 1 つに `model: opus` を設定するなど）。この編集は配布物の外殻を再コピーするまで残ります。

**所見:**
- アーキテクトは最も広くステージへ関与しています（3 フェーズにまたがる 10 ステージ）。
- 全 14 エージェントの構成では、9 体が `judgment` ティアを持ち、5 体が Claude Code、Codex、opencode でそれより 1 段下がります（2 体の `balanced` レビュワーと 3 体の `templated` プランナー。Kiro、Cursor、Copilot では全ティアがセッションのモデルと推論量を継承するため、段が下がるエージェントはありません）。段を下げたエージェントは、明示的チェックリストに対するレビュー、または主としてテンプレート化された計画／CI/CD／運用手順書作業を担います。上のマトリクスが対象としているのは 11 体のドメイン専門エージェントです。
- コンプライアンスは純粋に助言的な立場で動作します（4 つの支援ステージ、主担当ステージは 0）。
- 11 体中 6 体がシェルへアクセスでき、いずれも CLI 対話が必要な役割です。
- 3 体のエージェントが調査タスクのためにウェブ検索へアクセスできます。

## エージェントを追加する方法

エージェント表示名とナレッジファイル例は、各エージェントの `.md` メタデータ部にある `display_name` と `examples` フィールドが正本です。TypeScript の編集は不要です。完全な手順（必須メタデータ部フィールド、検証手順、自動検証される部分と手動検証部分の境界）は [コントリビューション: エージェントの追加](11-contributing.md#エージェントの追加) を参照してください。以下は手順の要約です。

1. `core/agents/{name}-agent.md` を、必須メタデータ部の `name`、`display_name`、`examples`、`description`、`disallowedTools`（`Task` を含む）、`tier` とともに作成します。コアのメタデータ部に生の `model:` / `effort:` を書いてはいけません。これらは射影結果です（上のエージェントティアを参照）。任意の `tools:` の許可一覧は継承ツールセットを絞り込みます。完全なセッションツールセットを継承するなら省略してください。`core/tools/aidlc-lib.ts` の `loadAgents()` は、次回呼び出し時にそのファイルを発見します。
2. `core/knowledge/{name}-agent/` にナレッジファイルを追加します。
3. そのエージェントが参加するステージファイル `core/aidlc-common/stages/` にエージェントを追加します。各ステージのメタデータ部にある `lead_agent` / `support_agents` を設定してください。コンパイル済み `tools/data/stage-graph.json` は、そのメタデータ部から `bun scripts/package.ts` により生成されます。手編集してはいけません（`package.ts --check` の差分検知器が、手編集した配布物に対して CI を失敗させます）。
4. 配布物を再生成します。`bun scripts/package.ts` を実行し、その後 `--check` で差分がないことを確認します。
5. 手動管理のナレッジ表に、そのエージェントから例への行を追加します（スペースレベルのチームナレッジディレクトリは `aidlc/knowledge/{name}-agent/` であり、内容があるときにチームが作成します。エンジンは足場を作りません）。
6. テストを更新します。ファイル存在用のスモークテスト、ステージとエージェントの相互参照用フィーチャーテストを追加します。
7. このファイルと [エージェント技術リファレンス](https://github.com/awslabs/aidlc-workflows/blob/HEAD/docs/reference/agents/) の文書を更新します。

## エージェントを変更する方法

- **ツールを変更する:** メタデータ部に `tools:` の許可一覧を追加または編集してエージェントを絞り込んでください。完全なセッションツールセットを継承するなら省略します。`tools:` 一覧は、`mcp__<server>__<tool>` 識別子も併記しない限り継承済み MCP ツールを落とします。
- **ティアを変更する:** `tier:` を `judgment`、`balanced`、`templated` のいずれかへ編集し、`bun scripts/package.ts` で再生成してください。代わりに、インストール済みコピー内の単一エージェントだけに特定モデルを強制したい場合は、`dist/<harness>/` のエージェントファイルにある射影済み `model:` を直接編集します（Claude Code は別名、完全識別子、`inherit` を受け入れます）。
- **振る舞いを変更する:** Markdown 本文セクション（責務、原則）を編集します。
- **ステージ割り当てを変更する:** 対応するステージファイル（`core/aidlc-common/stages/`）の `lead_agent`／`support_agents` を編集し、その後 `bun scripts/package.ts` で再生成してください。コンパイル済みステージグラフはステージのメタデータ部由来であり、手編集はしません。
