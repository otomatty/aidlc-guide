根本設計 — ステージ所要時間導出の正しい作り方

15ラウンドのレビュー往復（レビュー戦記参照）から逆算した、 「そもそもどう実装すべきだったか / これからどう直すか」の設計解説

0. 結論の先出し

痛みの根源は「計測器として設計されていないログから、状態機械を逆算していた」こと。
本当の根本解は書き手（AI-DLC エンジン）側にあるが、本プロジェクトでは変更禁止。 読み手側でできる根本策は4つ — ① プロパティベーステスト（敵対的探索の機械化）、 ② 帰属のタイムライン分割化（二重計上を表現不可能に）、 ③ 照合ロジックの一点集約、④ ポーリングの単純化（賢い条件を捨てる）。 着手順もこの順が最適。

1. 診断 — なぜ15ラウンドも指摘が出たのか

監査ログは診断用の追跡記録であって、時間計測のためのデータ構造ではありません。 計測に必要な3つの性質が欠けており、その穴を読み手がヒューリスティクスで埋めた結果、 それぞれがバグ群になりました:

ログに欠けている性質→読み手がやった代替→生まれたバグ群
相関IDがないどの COMPLETED がどの STARTED の相手か、イベント自身は知らない
→
ステージ名 + 時刻で推測同名再実行・シャードまたぎ・時計ずれ・skip 終端を場合分け
→
ペアリング系 4件+永久に開いた区間 / 2つの試行が0分に潰れる退行 / 孤立完了の乗っ取り
大半のイベントに Stage がない成果物・センサー等のイベントは「誰の作業か」を運ばない
→
「直近に開いた区間」へ帰属並行区間・末尾ギャップ・着手前イベントを場合分け
→
帰属系 6件実時間7分に活動11分 / 他ステージの作業を課金 / 末尾の持ち主違い
順序保証がない秒解像度 + クローン毎シャード + 時計ずれ。全順序は存在しない
→
読み手が比較関数で順序を発明同一秒の tie-break、特例の追加
→
順序系 2件NaN で全順序が壊れる / 特例が再実行境界を破壊（退行）
ヒューリスティクスは単体では各々妥当でも、組み合わせで壊れる。 1つ直すと隣の組み合わせが露出する — これが「モグラ叩き」の力学だった。 残るバグ群（ポーリング3件・鮮度3件）はクライアント側の別問題で、§5 で扱う。

4. 読み手側の根本策② — 帰属を「タイムラインの分割」として定式化する

帰属系6件のバグはすべて「同じ実時間が二重に、または誤った持ち主に課金された」の変奏でした。 原因は実装形式にあります: 各区間が自分のカーソル（前回時刻）を持ち、イベントごとに増分加算する方式では、 二重計上が「規律で防ぐもの」になってしまう — そして6回破られた。

Before: カーソル増分方式（規律で防ぐ）

区間A の視点（自分のカーソルで加算）
A: 1分
A にも課金されうる領域（6分）
区間B の視点（自分のカーソルで加算）
B: 6分
0分7分

Σ = 最大 11分 > 実時間 7分 — 各区間が独立に加算するため、重複が表現できてしまう（R9 で実際に発生）

After: タイムライン分割方式（構造で防ぐ）

隣接イベント間を「スライス」とし、各スライスを10分で頭打ちした上で高々1つの持ち主に割り当てる。

イベント列: t0=STARTED A → t1=STARTED B → t2=ARTIFACT(B) → t3=COMPLETED B → now
[t0,t1)
→ A
[t1,t2) → B（直近開始）
[t2,t3) → B（Stage名指し）
[t3,now)
→ 持ち主なし
t0t1t2now

Σ activeMs ≤ 実時間 が構造的に保証 — 各スライスは1回しか配られないので、二重計上はそもそも表現できない

過去の帰属バグ6件（ループ内二重計上・末尾の全区間課金・着手前イベント・末尾所有者…）は、 この形式ではすべて「スライスXの持ち主は誰か」という1つの純関数の判断に還元される。 そこだけ網羅テストすれば済み、新しい変奏が出ても壊れ方が「配り先の間違い」に限定される （時間が消えたり増えたりはしない）。attribution.ts の内部改修で収まる。

6. やらなくてよいこと（同じくらい重要）

やらないこと理由
増分計算・キャッシュ層フルパースは実測 90ms。毎回全再計算が最も単純で正しい。キャッシュは無効化・移行・掃除という3つの状態管理を連れてくる
独自の記録層（globalStorage 等）最初の判断は正しかった — 監査ログは既に git 管理の永続記録で、導入初日に過去の実績が遡って埋まる。痛みの原因は「導出方式」ではなく「ログの相関性欠如」だった
見積りの高度化（レンジ・分布・学習…）中央値 + フォールバック階段 + 信頼度フラグで用は足りている。精度の律速は見積り手法ではなく activeMs 自体の誤差（10分頭打ち）
ステージ内粒度（サブエージェント単位）の計測監査ログに開始イベントが存在せず、自前計測は「拡張が起動していた区間しか埋まらない」まだら履歴になる

8. まとめ — 一般化できる教訓

  1. 他システムのログを読むときは、まず「そのログに何が欠けているか」を書き出す。 相関・帰属・順序のどれが欠けているかが、そのまま実装の困難地図になる。今回それを事前にやっていれば、単一区間モデルは最初から選ばなかった。
  2. 「規律で守る不変条件」は、いつか破られる。 Σ activeMs ≤ 実時間 は6回破られた。不変条件は表現の構造（分割・型・単方向データフロー）に埋め込むのが根本策。
  3. 敵対的レビューは機械化できる。 生成器 + 不変条件 = プロパティベーステスト。外部レビュアーに15ラウンドかけて教わったことを、テストスイートに常駐させられる。
  4. 最適化は、それが守る状態機械のバグ代金込みで評価する。 「開区間があるときだけポーリング」は 90ms/30秒 を節約するために3つのバグを買った。
