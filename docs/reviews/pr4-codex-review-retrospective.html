フェーズ2: 転換点 — モデルそのものが誤っていた（R5）

「バグ」から「設計の誤り」へ

R5 で Codex はフレームワーク自身のプロトコル文書 （.claude/aidlc-common/protocols/stage-protocol.md）を根拠に3件を提示。 検証するとプロトコルに明記されており、Claude が設計時に読み込めていなかった正式挙動でした。

指摘プロトコルの記述壊れていたもの
unit-major では複数の設計ステージが同時に開く「ステージのユニット別設計作業は Current Stage がより前のステージを指したまま走りうる」「ゲートは設計ブロック末尾でカスケード発火」「開いた区間は常に1つ」というモデル自体。後のステージが始まるたびに前の区間を放棄し、設計ブロックの大半の実測値を喪失
STAGE_SKIPPED は終端イベント「STAGE_SKIPPED を1件出し…STAGE_COMPLETED は出さない」スキップされたステージの区間が永久に閉じない
backward ジャンプは完了ステージを pending に戻すエンジンのソース（aidlc-jump.ts）で確認差し戻されたステージの過去の閉区間を「現在の試行」と誤認 → 必要な再実行が見積りから消える
ここで「単一区間モデル」→「ステージ別の並行区間モデル」へ書き換えた。 正しい方向の修正だったが、並行モデルは帰属（どの区間に時間を課金するか）という新しい問題系を持ち込み、 これがフェーズ3のモグラ叩きの主因になる。

フェーズ4: 凍結宣言 — patch をやめる（R14〜R15）

「正しい指摘を、あえて直さない」判断

R14 の指摘（末尾の所有者が新規開始で移らず、沈黙生成中の B が 0m、待機中の A が 12m になる）は 検証すると正しかった — が、時間の帰属に関する6件目でした。ここで Claude は方針を切り替えます:

  • 指摘は正しいと検証した上で、修正しないことをスレッドに明記（「自動応答ですが、修正の報告ではありません」）
  • derive.ts に変更凍結を宣言（以降のラウンドの修正指示にも「derive.ts は触るな」を明記）
  • 再現手順ごと issue #5 に記録し、「ペアリングと帰属を2つの純粋パスに分割する」案を提出
  • 自動で解決済みになったスレッドを手で未解決に戻した — 実際に未解決だから
根拠はデータ: 指摘の大半が derive.ts 1ファイルに集中し、そのすべてが 「時間の帰属」と「無秩序下でのペアリング」という2つの関心事の変奏だった。 単一ループに2つの関心事が絡み合っている限り、次の変奏が出続ける — というのが凍結の論理。
時間の帰属 6件
ペアリング 4件
ポーリング生存性 3件
鮮度の照合 3件
その他 (docs/UI/テスト)

主な指摘の関心事別分布（概算）。左2つ = derive.ts の2大関心事で全体の半分を占める。

R15 でも2件（完了ワークフローが Current Stage: none という文字列センチネルを実在ステージと誤認し 「残り12.5分」と主張する / 現在ステージ行の信頼度がハードコード）が届いたが、 修正ディスパッチの途中でユーザーが PR #4 をマージし、「#5 に取り組んで」と指示。フェーズ5へ。

4. 対応の内訳 — 全部を「修正」したわけではない

約20件の指摘に対する対応は4種類に分かれます。この使い分け自体が今回の記録の核心です。

対応件数例
修正（検証 → RED→GREEN テスト付き）大多数フェーズ1〜3・5の各修正
部分対応（提案とは違う形で解決）2件「timings.length >= 21 を削除せよ」→ 削除すると空配列でも通るため > 0 に緩和。理由を返信し、レビュアーも受け入れた
意図的見送り（正しいが直さない）1件R14。issue #5 に記録し、スレッドは未解決のまま残した（後に PR #6 で解消）
スキップ（nitpick 等）数件ポーリング間隔の定数共有（型専用パッケージの規約と衝突するため見送り、理由を返信）

また CodeRabbit の MD040 指摘（コードフェンスの言語未指定）は、対象ファイルが誤コミットされた内部作業レポートだと判明し、 「整形」ではなく「リポジトリから除外 + gitignore」で対応 — 指摘の字面ではなく意図に応えた例。

5. 教訓

  1. 外部レビュアーは一次資料で殴ってくる。 Codex の最強の指摘（R5・R10）はフレームワークのプロトコル文書とエンジンのソースを引用していた。設計時にそれを読み込めていなかったことが、後の8ラウンドの遠因になった。
  2. 同じ場所への patch の繰り返しは収束しない。 「時間の帰属」だけで6回。修正のたびに新しい変奏が出るのは、修正が悪いのではなく構造が2つの関心事を絡めているサイン。閾値を決めて（今回は「同じ関心事の再来」）、patch をやめて構造に手を入れる判断が必要だった。
  3. 「正しい指摘を直さない」には記録が要る。 R14 の見送りは、検証結果・理由・再現手順を issue に残し、スレッドを未解決のまま保つことで初めて成立した。黙って放置とは別物。
  4. 検証してから直す。 全指摘を再現してから修正に入ったため、誤指摘に振り回されることがなく、逆に自分の判断の誤り（Header・awaiting-approval・比較関数特例）を発見できた。
  5. 分割は縫い目に新しいバグを作るが、影響範囲も縫い目に閉じる。 PR #6 の退行は分割の失敗ではなく、分割が機能している証拠だった。
