## 設計と検証の不足

バージョン定数とGUIの状態は共通化したが、実行手順は `workflows-install.ts` と `workflows-native-update.ts` に分かれていた。さらに更新側では、マシン既定版の最終復元を `workflows-update.ts` が担当する。どの層がどの状態を守るかを横断して確認せず、一方に入れた保護を他方に適用し忘れた。

扱う状態の寿命も異なる。マシン既定版は複数フォルダで共有され、固定版とツール設定はプロジェクトに属する。パネルを閉じれば前進する処理は止める必要があるが、開いていて信頼されているフォルダへの復元は続ける必要がある。この区別と、ツール設定の書き込み開始後は固定版だけを戻せないという境界を、初期実装の検証条件にしていなかった。

テストは各コメントの再現に寄っていた。最終診断だけの中断テストでは、前半のインストール・切り替え・固定コマンドに通知が届かない問題を検出できない。設定関数を成功するモックに置き換えたテストでは、実際の実行中ワークフロー検査が「本体変更後」に走るという順序も隠れる。全体のテスト数やカバレッジが高くても、この組み合わせの検証にはならなかった。

## 今回の修正と確認条件

| 守る条件                                                     | 修正・回帰テスト                                                                                                                                                                                                 |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 実行中のワークフローがあれば、本体・固定版を変更しない       | 更新サービスは修復マーカーを付ける前に検査。更新処理も最初の変更前に検査し、インストール・修復・本体切り替え・固定の直前に再検査する。実際の `aidlc-state.md` を一時フォルダに置き、開始時と処理途中の両方を検証 |
| コマンドの失敗や中断は「まだ書き込んでいない」と同義ではない | インストールは固定コマンドの前に復元処理を登録。更新も通常エラー時に固定版を復元。書き込み後に中断・エラーが起きるテストで確認                                                                                   |
| ツール設定の書き込み前なら、元の固定版または固定なしに戻す   | 古い固定版と固定なしの両方について、固定中断・固定エラー・設定事前検査の中断・エラーを検証                                                                                                                       |
| ツール設定の書き込みが始まったら、固定版だけを戻さない       | インストールにも `onApplyStart` を接続。書き込み途中の中断と、複数ツールの部分成功で対象版を維持することを検証                                                                                                   |
| パネル破棄と復元可能性を分ける                               | インストールGUIにも `canRestore` を渡す。パネルだけを閉じた場合は復元でき、フォルダ削除時は復元しないことを検証                                                                                                  |
| 復元の失敗を隠さず、操作ロックは解放する                     | インストールは復元失敗を結果に含める。失敗後に次の操作を開始できることも検証                                                                                                                                     |
| 対象版、全ツールの最終診断、異なるフォルダ間の排他を維持する | 既存の管理・更新・GUI入口のテストと全体検査で確認                                                                                                                                                                |

固定版の復元には公式の `config --pin` / `--unpin` を使い、中断済みのシグナルを渡さない。固定ファイルだけを直接戻すと、公式CLIが管理する登録情報とずれるためである。上流のタグ `v2.8.1` にある `core/tools/aidlc-lifecycle.ts` を `git show` で確認した。旧版が手元になければ復元コマンドが取得を必要とする場合があり、その失敗は復元失敗として報告する。

検証はCLI境界を差し替えた自動テストと、一時フォルダ内の状態ファイル・固定ファイルの確認による。実機のVS Codeでインストーラーを中断するE2E試験ではない。また、現在の排他は同じ拡張ホスト内の操作が対象で、別ウィンドウや外部CLIとのプロセス間ロックではない。実行中ワークフローの再検査も外部プロセスとの原子的な排他を保証するものではない。
