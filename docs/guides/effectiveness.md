# 効果測定で案件を比較する

Dashboard のヘッダーから「効果測定」を開きます。現在の space にある案件を一覧にし、scope と depth で絞り込めます。VS Code / Cursor の拡張と、ブラウザ版 Dashboard で利用できます。

画面を開いたときに記録を読み取り、表示中の変更通知に合わせて再取得します。別の案件や別の端末から更新した記録を確認する場合は「更新」を押してください。ワークフローを実行したり、案件を選択したりしなくても一覧を確認できます。

## 表示する指標

| 指標               | 読み方                                                                                                                           |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| 完了までの時間     | ワークフローの開始から完了までの経過時間。休止や承認待ちも含みます。未完了案件の経過時間とは区別して表示します。                 |
| 承認待ち           | 承認待ち開始から承認・差し戻しまでの時間。終了した待ち時間と、現在待っている時間を分けます。並行する待ち時間は重複計上しません。 |
| 差し戻し           | 記録されたゲート却下の回数。修正の記録とは別に数えます。                                                                         |
| レビュー初回合格率 | 初回のレビュー依頼と結果を対応付けられたもののうち、READY だった割合。対象件数も表示します。                                     |
| 品質チェック       | 検証できた成功、失敗、省略、未完了を分けます。ツール未導入や実行エラーを成功に数えません。                                       |
| AI利用量           | 記録がある場合に入出力・キャッシュのトークン数と料金換算額を表示します。料金は設定された単価による推定で、請求額ではありません。 |

「未記録」はゼロとは異なります。古い案件やフックが動いていなかった期間は、集計に必要な記録が揃わない場合があります。結果を対応付けられないレビューや、復旧時に補った承認待ち開始も、正確な計測には利用しません。部分的に読み取れた案件は、その注意点を表示します。

監査イベントが10万件、監査ファイルが128個を超える場合や、監査ファイルの一部を読み取れない・解析できない場合は、その案件の監査ログに基づく指標を「未記録」にします。途中の記録だけで期間や回数を確定せず、理由を「記録の内訳」に表示します。独立して正常に読み取れた利用量台帳は引き続き使用できます。

別端末の監査ファイルに同時刻の記録があり、その中に再開始・ジャンプ・承認などの境界が含まれる場合も、ファイル名から前後関係を推測せず監査指標を非表示にします。初回レビューの対応付けがない案件は、初回合格率の「記録あり」の件数に含めません。

この画面の時間は人の実作業時間ではありません。ホーム画面にある監査イベント間隔からの活動時間の推定とも別の指標です。

承認待ちの区間をすべて集計から除外した場合は、待ち時間を「未記録」とし、記録がある案件の件数にも含めません。除外区間数は「記録の内訳」に残します。終了した待機と待機中の時間は別々に扱い、開始と終了を対応付けられた0秒だけを確定した「0分」と表示します。

人の入力回数は、実行先のワークフローが明示された記録のみを数えます。現行の aidlc-workflows 2.8.0 の標準フックは `HUMAN_TURN` に実行先を記録しないため、通常実行と単独ステージ実行を区別できません。この形式の記録しかない場合、入力回数は「判別不可（実行先未記録）」となります。時刻やセッションの一致だけでは補完しません。正確な回数の収集には、エンジン側で呼び出し・質問への返答の実行先を記録する対応が必要です。

品質チェックは、その案件の監査ログに記録された検査の合計です。通常実行と単独ステージ実行の両方を含みます。現行の書き込み時センサーにも実行先情報がないため、主ワークフローだけの検査回数には分離しません。実行先タグの有無で集計対象を変えず、APIでは `sensors.scope = "intent-record"` として対象範囲を示します。

## AI利用量の取得条件

aidlc-workflows 2.8.0 の利用量収集処理は Claude Code の記録に対応しています。Cursor で利用量の記録が作られていなければ、拡張から料金を推定することはありません。

`AIDLC_DISABLE_USAGE_TRACKING` による停止中は、利用量台帳を読み取らず、過去の監査ログに残っているトークン数・費用も表示しません。拡張やブラウザ版サーバーの環境変数を最優先し、未設定の場合はマシン設定、プロジェクトの `aidlc.settings.json`、`aidlc.settings.local.json` の順に `flags.bypasses` を解決します。後の設定に配列がある場合は、空配列を含めて前の配列を置き換えます。環境変数は `1` の場合に停止し、`0` や空文字を明示した場合は設定ファイルより優先されます。設定を読み取れない場合も、利用量と費用を非表示にして注意を表示します。

利用量は案件に紐付いたローカルの台帳と、監査ログに残った集計を読み取ります。完了時の監査記録に台帳より多いトークンが残っていれば監査記録を採用し、内訳の大小が食い違う場合は部分的な集計として扱います。同じ工程の完了時に記録される利用量は累計なので、繰り返し完了した値を足し合わせません。単価が分からないモデルを含む場合も、料金が一部のみであることを表示します。

チーム実行の作業ツリーは利用量台帳を別々に持ちます。監査ログの利用量をクローン単位で整理し、同じクローンの工程別累計と完了時累計を重複させずに、複数クローンの記録を合算します。この場合のAPI出典は `audit-clones` です。担当者全員の記録が揃った保証はないため、一部の記録として表示します。監査ログを集計できずローカル台帳だけを使う場合も、他のクローンの利用量が含まれない可能性を明示します。

親の監査ファイルに作業ログが統合されている場合は、`AUDIT_FORKED` と `AUDIT_MERGED` の対応関係と取り込み件数から実行元を識別します。元の作業ログも残っていても同じ利用量を二重加算しません。統合記録を対応付けできない場合は監査ログの利用量を非表示にし、ローカル台帳があれば部分的な値として表示します。

既知のモデルの判定には標準料金表と `AIDLC_MODEL_RATES` の上書きファイルも使用します。有効な0円の料金設定は「単価不明」と区別します。保存済みの費用を新しい料金で再計算する処理は行いません。

ローカル台帳は Git の共有対象ではありません。別の端末で取得できる数値は、同期された監査ログや、その端末に残っている台帳によって異なります。

## 比較するときの条件

scope、depth、案件の規模や難易度が近いものを比較してください。初回合格率や品質チェックの成功率だけで品質全体を判断せず、対象件数、省略された検証、リリース後の不具合も確認します。

AI-DLC の導入による短縮率を出すには、不使用時や導入前の比較データが必要です。この画面は既存の実行記録を集計するもので、削減時間や改善率を自動的に推定するものではありません。

## 読み取り範囲

集計はローカルで行い、案件の状態・監査ログと、取得可能な利用量台帳を読み取ります。状態や監査ログを書き換えず、会話本文や回答内容を集計APIへ返しません。クラウドサービスやデータベースは追加しません。

拡張とブラウザは共通の `GET /api/effectiveness` を使用します。初期のワークフロー表示とは独立して取得するため、案件横断の集計がホーム画面の初回表示を待たせません。
