# ルールと学習ループ

ルールは、あなたのチームがすべてのワークフローへ持ち込む常設の決定です — それが無ければ実行のたびに説明し直すことになる「いつもこうする」です。ハーネスエンジニアとして、ルールの作成方法は 2 つあります。ルールファイルを直接編集するか、**学習ループ**にワークフロー中の訂正を永続的なルールへ昇格させてもらうかです。この章は、ユーザーガイドの [ルールと学習ループ](../guide/09-rules-and-the-learning-loop.md) の章に対する、作成側の相棒です。あちらはループを概念として扱い、ANZ 銀行の例を最初から最後まで辿ります。ここでの焦点は運用面です。何のためにどのファイルを編集するのか、ルールを重ねたとき厳密加算モデルはどう振る舞うのか、そして一度きりの修正が常設のルールになるようループをどう回すのか。

ルールは制御ループのフィードフォワード側です — エージェントが作業する*前に*読む散文です。[センサー](06-sensors.md) はフィードバック側 — 書き込みの*後に*発火する決定論的な検査です。ルールは自分の相棒としてセンサーを名指しできます。この 2 つの半分は、対になるよう設計されています。

---

## 5 つの層と、編集するファイル

ルールは `core/memory/`（スペースメモリ層に対する、作成されるソース）配下の Markdown ファイルとして、スコープごとに 1 ファイル存在します。`scope:` というフロントマターのフィールドはありません — この実装はスコープをファイル名から導出するため、あなたが選ぶファイル*こそ*が、作成対象のスコープです。

| こういう範囲に適用したいルール… | 編集するファイル | スコープ |
|---|---|---|
| 組織のすべてのプロジェクト | `org.md` | org（フレームワーク既定） |
| チームが動かすすべてのプロジェクト | `team.md` | team |
| このプロジェクトだけ | `project.md` | project |
| 1 つのフェーズのすべてのステージ | `phases/<phase>.md` | phase |

4 つのフェーズファイルは `phases/ideation.md`、`phases/inception.md`、`phases/construction.md`、`phases/operation.md` です（initialization はブートストラップ専用で、ルールファイルを出荷しません）。5 つ目の層 — ステージごとのルール（`aidlc-stage-<slug>.md`）— は将来のリリースのために予約されており、まだ作成できません。

どのファイルへ手を伸ばすかは、2 つの判断で決まります。

- **`org.md` はフレームワークが出荷するものです。** すべてのプロジェクトが継承する既定 — trunk ベース開発、ウォーキングスケルトンの方針、スコープごとのテスト姿勢 — を担います。上流のものとして扱ってください。ほとんどのハーネスエンジニアはこれに手を触れず、team か project で作成します。
- **project スコープは永続的な逸脱のためのものであって、何でも置く場所ではありません。** `project.md` へ手を伸ばすのは、*このプロジェクト*がチーム全体の実践から安定して外れるときだけにしてください — チームが squash するところをリベースする monorepo、テスト下限を飛ばすレガシープロジェクトなど。そのルールがチームの動かすすべてのプロジェクトで役に立つなら、それは `team.md` に属します。

各ファイルは、話題ごとの見出し — `## Way of Working`、`## Testing Posture`、`## Deployment`、`## Code Style` など — の下に置かれた素の散文です。ルールを追加するには、それが属する見出しの下に箇条書きを 1 つ足します。ファイル名からスコープへの完全な対応表と解決器の仕組みが規範となる契約です: [ルールシステム § ファイル名から導出するスコープ](../reference/08-rule-system.md#filename-derived-scope) と [§ 配置](../reference/08-rule-system.md#layout)。

## 厳密加算: 層は積み上がり、どれも黙って上書きしない

チェーンは、すべてのワークフローの開始時に 5 つの層を通して解決されます。

```
org → team → project → phase → stage
```

モデルは**厳密加算**です。適用されるすべてのルールが、エージェントの文脈に一度に現れます — 実行時に落とされたり抑制されたりするものはありません。org の既定、team の実践、project の特殊化が連結され、対応するフェーズのルールは、ステージが既にフロントマターで `phase:` を宣言しているために付随します（ステージが他のあらゆるものをインポートするのと同じ、プル型の作成方向です）。解決されたチェーンは、ワークフロー開始時に各ステージノードへ一度だけ焼き込まれます — ランタイムがそれを歩き直すことは決してありません。[ルールシステム § 厳密加算の実行時モデル](../reference/08-rule-system.md#strict-additive-runtime-model) と [§ 5 層の継承](../reference/08-rule-system.md#five-layer-inheritance) を参照してください。

作成者としてのあなたにとって、これが意味するのは次のことです。`overrides:` ブロックも、設定すべき `enforcement:` キーワードもありません。狭い層が広い層に対して静かに勝つことはありません。代わりに、あなたが書いたすべての層が、エージェントの視界に同時に存在します。これは作成の仕方を変えます — ルールは、適用されるべきスコープで肯定的に述べ、上位の層を抑制するスイッチへ手を伸ばすのではなく、それらと積み上がることを信頼します。

### 競合は、学習の書き込み前に検査されるのであって、実行時に解決されるのではない

実行時に何も上書きしないため、より広いスコープのルールと*矛盾する*ルールは、解決器がほどけない問題になってしまいます。学習ループのプロトコルは、選択が決定論的なライターへ到達する前に、オーケストレーターへセクション単位の LLM 検査を実行させることでこれに対処します。ある `## 見出し` の下に team または project スコープの学習が追加されようとしているとき、オーケストレーターは提案されたテキストを `org.md` の同じ見出しと比較します。矛盾を見つけると、org の文を提示し、3 つの選択肢 — **修正**、**スキップ**、org ルールの所有者への**エスカレーション** — を示します。競合が無いか、ユーザーがエスカレーションした選択だけが先へ進みます。project 層の書き込みは org に対してのみ検査します。team と project の差は正当なプロジェクト特殊化であって、方針違反ではないからです。

決定論的な `aidlc-learnings.ts persist` ライターは `org.md` を読みませんし、この比較を独自に強制することもありません。受け取った選択をそのまま受け入れます。この検査は監査上の補助であって、強制の境界ではありません。もう 1 つの受け入れゲートは practices-discovery ですが、そちらは org 競合の検査を実行しません。その昇格は、ユーザーの確認によって正当化される、決定論的なセクション置換だからです。事後の状態は、読み取り専用の `/aidlc --doctor` の 2 行が可視化します。**rule-drift** の行は、team または project の内容が、内容のある org の見出しと重なる箇所を（人間が確認すべき矛盾候補として）示し、ライフサイクル上 stale なファイルは stale-suppressed として別途報告されます。**paired-coverage** の行は、実際に解決されるセンサーを名指ししているルールの数を報告します。どちらも助言であり、終了コードを変えることはありません。[ルールシステム § ルールドリフト検出](../reference/08-rule-system.md#rule-drift-detection) を参照してください。

## 学習ループを回す

ルールが作成されるもう 1 つの道では、あなたはファイルを一度も開きません — ワークフロー中にエージェントを訂正し、ゲートでその訂正を確認すると、フレームワークが代わりに書いてくれます。それが学習ループです。ほとんどのステージ実行は何も追加しませんが、それが健全です。ループは、そのステージ中に取っておく価値のあることが起きたときにだけ発火します。

仕組みは [ユーザーガイドの章](../guide/09-rules-and-the-learning-loop.md) で扱っています。ハーネスエンジニアの視点では、ループが何を生み、それがどこへ着地するかが要点です。

1. **ステージ中、日誌が記録する。** コンダクター（有効なステージを実行している、生きた `/aidlc` セッション）は、`<record>/<phase>/<stage>/memory.md`（インテントの記録ディレクトリ `aidlc/spaces/<space>/intents/<YYMMDD>-<label>/` の下）に観察ログを保ち、Interpretations、Deviations、Tradeoffs、Open questions の 4 見出しの下にエントリを置きます。これは自動で作成・維持されるものであり、手で編集してはいけません。日誌を書くのは言語モデルで、その後の受け入れ比較はオーケストレーターが行います。候補の抽出と最終的な書き込みは決定論的なツールが担い、選択と競合の処理はゲートにおけるあなたの明示的な選択です。
2. **ゲートが候補を提示する。** 承認ゲートの前に、学習ゲートが `memory.md` を読み、空でない日誌の各行を逐語のまま候補として表示します。加えて「次回のために追加することはありますか？」という自由文のチャネルがあり、そこへ観察を入力して、4 つの見出しのどれに属するかを選べます。
3. **何を残すかを確認すると、書き込まれる。** 確認された学びは日付付きのエントリとして着地します — あなたがファイルパスを選ぶことはありません。見出しが行き先を決めます。

### 残した学びの着地先

確認された学びは実践*そのもの*です。practices-discovery が確認するのと同じスペースメモリのファイル（`aidlc/spaces/<active-space>/memory/team.md` / `memory/project.md`）に着地します — 別途 `*-learnings.md` という面があるわけではありません。ゲートが話題の見出しでそれを振り分けます。

| ゲートでの見出し | 着地先 | 監査イベント |
|---|---|---|
| Interpretation / Deviation / Tradeoff | `aidlc/spaces/<active-space>/memory/project.md`（既定） | `RULE_LEARNED` |
| 同上、ワンクリックで昇格 | `aidlc/spaces/<active-space>/memory/team.md` | `RULE_LEARNED` |
| Open question | 何も書かれません — 調査項目は昇格しません | — |

既定のスコープは、もっとも狭い **project** です。ワンクリックの「チームへ昇格」の仕掛けが、その学びがこのプロジェクトを越えて当てはまるときに `memory/team.md` へ広げます。org へ広げる道はありません — org の実践はフレームワークが出荷するか、別のプロセスで組織が作成するものであり、ループが org スコープへ書くことは決してありません。既定を狭く保つことで、1 つのプロジェクトでの驚きが、うっかり組織全体のルールになるのを防ぎます。学習ループと practices-discovery は、2 つの異なるライフサイクルでこれら同じファイルへ書き込みます。ループは日付付きのエントリを 1 件ずつ追記し、practices-discovery はセクションまるごとを確認します。解決器は、org → team → project → phase というきれいな整数のチェーン上でファイルを並べます。

### 学びがルールではなく検査であるとき（`SENSOR_PROPOSED`）

取っておく価値があるものが、*繰り返し行っている手作業の検査*であることもあります — あるステージの出力について、同じ抜けをずっと目視で確かめている、というような場合です。ゲートでその種の学びを確認すると、フレームワークはそれをルールではなくセンサーのバインディングとして扱います。2 つの書き込みをアトミックにインストールします。`.claude/sensors/` の下にセンサーマニフェストの雛形を作り、発端となったステージの `sensors:` インポート一覧へ新しいセンサーの ID を追記し、`SENSOR_PROPOSED` の監査行を残します。これが、フレームワークのリリース以外でステージファイルに対して認められている唯一の編集です — 増えるのはインポート一覧だけで、ステージ本文には決して触れません。そこから先は、[センサー](06-sensors.md) を使って手でマニフェストを肉付けします — ループはバインディングの雛形を作り、検査はあなたが作成します。

### 学びは、進行中のワークフローではなく次のワークフローに効く

ゲートで捕まえた学びが、現在の実行の残りに対してルールを変えることは**ありません**。このワークフローについては、あなたは既に会話の中でエージェントを訂正しています。ルールは次回のためのものです。新しい行はディスク上にありますが、進行中のワークフローは開始時のコンパイル済みの視界を保ちます。*次に*実行する `/aidlc` が再コンパイルし、ディレクトリ走査が新しいファイルを拾い、ルールはステージ 1 から適用されます。

これは手で作成する場合にも当てはまります。ワークフローの途中で `team.md` を編集しても、進行中の実行に遡って効くことはありません。ルールが効くのは、次のコンパイル境界です。変更をすぐ効かせたいなら、ワークフローを完了するか再開して、コンパイルにあなたの編集を読み直させてください。
