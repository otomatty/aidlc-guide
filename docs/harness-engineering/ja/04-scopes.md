# スコープ

スコープは、ある種類の作業に対してフレームワークの 33 ステージのうち*どれ*を実行し、どれを見送るかを決めるダイヤルです。バグ修正に市場調査や環境プロビジョニングは不要ですが、デプロイパイプラインと実行のステージは走らせます。規制のあるエンタープライズの機能開発なら、ライフサイクル全体が必要です。毎回ユーザーにステージを手で選ばせるのではなく、AI-DLC は名前の付いた 11 のスコープを出荷しています。それぞれが、全ステージ集合に対する厳選された EXECUTE／SKIP の判定であり、深さ・テスト戦略・任意のレビュー上限といったワークフローの既定値と対になっています。スコープを選べば、残りは連鎖して決まります。

ハーネスエンジニアにとって、スコープは純粋なデータであり、他のあらゆるプリミティブと同じくファイルとして作成します。半分ずつの 2 つから成ります。1 つは `core/scopes/aidlc-<name>.md` ファイル（アイデンティティ、経路選択のメタデータ、ワークフローの既定値）、もう 1 つはステージごとのメンバーシップタグ（各ステージのフロントマターの `scopes:` 一覧が、そのステージが動くスコープを名指しする）です。スコープの追加や調整に TypeScript は不要です。この章はその作業の流れを辿ります。スコープは何でできているか、チームのスコープをどう追加するか、既存のものをどう調整するか、そしてツールが何を検査してくれて何をあなたに委ねるか。

利用事例とユーザーが読む経路選択の表を含む 11 スコープの完全なカタログは、ユーザーガイドの [スコープ・深さ・テスト戦略](../guide/05-scopes-and-depth.md) を参照してください。この章は、その同じデータの作成側です。

## スコープは何でできているか

スコープは 2 か所で作成され、その分割こそが眼目です。スコープの*アイデンティティ*は自分のファイルに住み、その*メンバーシップ*（どのステージがその下で動くか）は、転置されてステージ側に住みます。

**1. スコープファイル — `core/scopes/aidlc-<name>.md`。** `core/sensors/` と同じく、スコープごとに 1 ファイルです。`feature` スコープのフロントマターはこうなります。

```yaml
---
name: feature
depth: Standard
keywords: []
description: Full lifecycle for new features, practical depth
skeleton: on
---

# feature scope

Prose intent: why these stages, why skip those.
```

スコープのフロントマターのフィールドは次のとおりです。

| フィールド | 必須 | 何をするか |
|-------|----------|--------------|
| `name` | はい | スコープ名。コアのファイルは `aidlc-<name>.md`、プラグインのスコープファイルは `name` と等しい語幹を使います。 |
| `depth` | はい | 既定の詳細度 — `Minimal`、`Standard`、`Comprehensive`。 |
| `testStrategy` | いいえ | 深さとは独立にテスト量を上書きします。既定では `depth` に一致します。 |
| `review_cap` | いいえ | このスコープでのレビュークラスの上限: `adversarial`、`advisory`、`none`。無い場合、スコープレベルでの引き下げはありません。上限はステージの `review_class` を下げられますが、上げることは決してできません。自律スウォームのレビューは、ステージが宣言したクラスを保ちます。 |
| `keywords` | いいえ | `/aidlc <自由文>` の自動検出のための自然言語トリガー。フラットな文字列リストはブロック形式（`- item`）でもフロー形式（`[item, item]`）でも構いません。空リストはオプトアウトです。 |
| `description` | いいえ | `/aidlc --help` に表示される 1 行説明。（SKILL.md のコンパイル済みスコープ表は Scope / Depth / TestStrategy / EXECUTE / Total のみを表示し、説明は含みません。） |
| `skeleton` | いいえ | 実践がスコープ依存のとき、`on` はこのスコープをウォーキングスケルトンの儀式に参加させます。`off` または省略はオプトアウトです。 |
| `runner` | いいえ | `true` にすると、既定で生成されるスコープランナー集合にこのスコープが含まれます。 |
| `freeform_default` | いいえ | `true` にすると、優先されるコア既定（`classic`）が有効でない場合の、選択状態を考慮したフォールバックとしてこのスコープを指名します。 |

ローダーは、ファイルをまたいでスコープ `name` が重複することを拒否し、エラーで両方のファイルを名指しします。

### 自由文の既定

`freeform_default: true` により、プラグイン選択の結果として内部既定の `classic` が利用できない場合に使うスコープを、インストール側が指名できます。この指名は「有効なプラグインが 1 つだけ」のフォールバックより先に確認されるため、複数のスコープを持つプラグインは、アルファベット順で最初のスコープを受け入れる代わりに、自分の軽量な既定を選べます。

`freeform_default: true` を宣言できる**有効な**スコープは、多くとも 1 つです。選択されたコア／プラグイン集合に 2 つ以上含まれる場合、グラフのコンパイルは失敗し、主張しているすべてを名指しします。無効なプラグイン上の主張は、それらのプラグインが同時に有効化されるまで衝突しません。このフィールドが明示的な打ち間違いを直すことはありません。未知の `AWS_AIDLC_DEFAULT_SCOPE` の値は、引き続き検証で失敗します。

### ウォーキングスケルトンの既定

任意の `skeleton:` フィールドは、スコープ依存のウォーキングスケルトンの姿勢を制御します。`skeleton: on` は、チームの `## Walking Skeleton` の実践が `scope-dependent` に解決される場合、このスコープでは Construction がウォーキングスケルトンの儀式で始まることを意味します。`skeleton: off` は、最初の Bolt が通常の Bolt として実行されることを意味します。省略時は off が既定なので、合成された／実行時に承認されたスコープやプラグインのスコープが、明示的にオプトインしない限りスケルトンの Bolt を生み出すことはありません。

**2. メンバーシップのタグ — 各ステージの `scopes:` フロントマター。** ステージは、`core/aidlc-common/stages/<phase>/<slug>.md` にある自分自身のフロントマターで、自分が動くスコープを名指しします。

```yaml
scopes:
  - enterprise
  - feature
  - mvp
```

あるスコープを名指ししているステージは、そのスコープでは `EXECUTE` です。名指ししていなければ `SKIP` です。ビルドの手順 `bun .claude/tools/aidlc-graph.ts compile` は、すべてのステージの `scopes:` 一覧を*転置*して、`.claude/tools/data/scope-grid.json` のコンパイル済み EXECUTE／SKIP グリッドにします — 純粋な転置であり、`stage-graph.json` とまったく同じく `compile --check` の乖離ガードが付いています。ランタイムが読むのはこのグリッドであり、手で編集することはありません。3 つの初期化ステージはすべてのスコープを名指しします（常に実行されるため）。

理解しておく価値のある唯一の判断は、`depth` と `testStrategy` の関係です。深さは各ステージの成果物がどれだけ詳細を持つかを制御し、テスト戦略は生成されるテストの数を制御します。この 2 つが独立なのは意図的です。出荷されるほとんどのスコープは `testStrategy` を省いて `depth` から継承します — `classic` は Standard/Standard、`express` は Minimal/Minimal です。`workshop` は Standard の深さと Minimal のテストで、この明示的な分離を示しています。あなたのスコープで分離したいなら、両方を宣言してください。各レベルの意味は、ユーザーガイドの [3 段階の深さ](../guide/05-scopes-and-depth.md#the-3-depth-levels) と [3 段階のテスト戦略](../guide/05-scopes-and-depth.md#the-3-test-strategy-levels) を参照してください。

フィールドごとの網羅的な契約 — `keywords` がどう語境界で一致するか、曖昧な自由文の呼び出しをアルファベット順のスコープのタイブレークがどう解決するかを含む — は、開発者リファレンスの [貢献 § スコープを追加する](../reference/11-contributing.md#adding-a-scope) にあります。この章は判断をまとめたもので、規範となる仕様はそちらです。

## スコープとステージの関係

スコープとステージは反対側の端から互いを指しており、両方向を視野に入れておくと理解しやすくなります。

**ステージ**は自分自身のアイデンティティ — フェーズ、リードエージェント、消費・生成する成果物、そして今では自分が動くスコープ（`scopes:` 一覧）— を宣言します。**スコープ**は自分の `.md` ファイルで、アイデンティティ・経路選択のメタデータ・ワークフローの既定値を宣言し、その中にステージごとのメンバーシップは持ちません。メンバーシップはステージ側に住みます。両者を結ぶのはスコープ名です。新しいステージを追加するとき（[ステージを追加する](02-adding-a-stage.md) を参照）、スコープのメンバーシップは*そのステージ側*に置きます — その `scopes:` 一覧が、そのステージを実行すべきすべてのスコープを名指しします。どのスコープも名指ししないステージは、どこでも `SKIP` です。コンパイル時の転置がステージごとの一覧をグリッドに変えるため、メンバーシップはステージ上で一度だけ書けばよく、11 個のスコープブロックで宣言し直す必要はありません。

この分離は、本ガイドの他の部分が依って立つのと同じ、データかコードかの線です（[ハーネスエンジニアガイド](00-overview.md) を参照）。スコープファイルは*アイデンティティ*についてのデータ、ステージの `scopes:` 一覧は*メンバーシップ*についてのデータ、コンパイル済みグリッドはその 2 つの転置です。

## チームのスコープを追加する

チームが `hotfix` スコープを欲しがっているとしましょう。`bugfix` より軽量で、緊急の本番パッチ向けに、回帰テストとデプロイだけを行い、それ以外は何もしないものです。変更は、新しいスコープファイル、実行すべき各ステージへの `scopes:` タグ、そして再コンパイルです。以下の規律をなぞってください。検証手順とコマンドラインの全体は [貢献 § スコープを追加する](../reference/11-contributing.md#adding-a-scope) にあります。

### 手順

1. **`core/scopes/aidlc-hotfix.md` を置く。** `aidlc-bugfix.md`（既存でもっとも近いスコープ）をコピーし、フロントマターを編集します。`name: hotfix` を設定し、`depth` を選び、自由文の自動検出が欲しければ `keywords`（`[hotfix, urgent]`）を追加し、ヘルプ用の `description` を書き、スコープ依存の Construction 儀式の既定として `skeleton: on|off` を設定し、選択されたインストールにおける唯一のフォールバック指名である場合にだけ `freeform_default: true` を、`depth` と食い違わせる場合にだけ `testStrategy` を、ステージのレビューを下げる場合にだけ `review_cap` を設定します。意図を説明する短い散文の本文を書いてください。

2. **`hotfix` の下で実行すべきステージにタグを付ける。** `EXECUTE` にしたい各ステージ（`core/aidlc-common/stages/<phase>/` 配下）で、フロントマターの `scopes:` 一覧に `hotfix` を追加します。タグを付けなかったステージは、そのスコープでは `SKIP` です。3 つの初期化ステージは必ず含めてください（常に実行されます）。

3. **再コンパイルする。** `bun .claude/tools/aidlc-graph.ts compile` を実行してタグを `scope-grid.json` へ転置し、続いて `bun .claude/tools/aidlc-utility.ts scope-table` で SKILL.md のコンパイル済みスコープ表を更新します。`bun .claude/tools/aidlc-graph.ts compile --check` と `bun .claude/tools/aidlc-utility.ts scope-table --check` を実行して、乖離が無いこと（終了コード 0）を確認します。

4. **スコープが解決され、受け付けられることを確認する。** `/aidlc --doctor` を実行します。続いて、新しいスコープでの初期化が正しい `Scope:` 行を持つ状態ファイルを生成すること、そして環境既定として、またワークフロー途中の `--scope` 変更として受け付けられることを確認します。

5. **キーワード推論を確認する**（`keywords` を書いた場合のみ）。トリガーの 1 つを含む自由文が、`feature` へ落ちるのではなく新しいスコープを検出することを確認します。

6. **スコープを意識したドキュメントを更新し、経路選択のテストを追加する。** いくつかのドキュメントはスコープを手で列挙しています — ユーザーガイドのスコープリファレンスと経路選択の表、カスタマイズ章の有効値一覧、オーケストレーターリファレンスのスコープ→ステージ対応です。同じ変更の中で更新してください。あなたのスコープが、既存のどのスコープとも異なるパターンでステージをスキップする場合は、既存のスコープ別テストにならったワークフローテストを追加します。

7. **（任意）入力可能なランナーを生成する。** スコープはファイルが着地した時点で `/aidlc --scope <name>` から完全に使えます — ランナーは不要です。1 語のコマンド（`/aidlc-hotfix`）が欲しければ、スコープのフロントマターに `runner: true` を追加して `bun .claude/tools/aidlc-runner-gen.ts scopes` を実行します。`bun .claude/tools/aidlc-runner-gen.ts scopes --all` は、そのフラグにかかわらず、すべてのスコープファイルについて `skills/aidlc-<scope>/SKILL.md` を出力します。各ランナーは、スコープを埋め込んだうえで `aidlc-orchestrate next --scope <name>` を `done` まで駆動する薄いシェルであり、加えて「無関係な新しい作業を始めますか？」の節を持ちます。そこには `/aidlc` オーケストレーターと同じ、認識・提示（`AskUserQuestion`。自動作成は決してしない）・`next --new-intent --scope <name>` の案内が入ります。ランナーは、すでに実行可能なスコープをパッケージしたものであり、スコープファイルがその定義です。ランナーは `hooks:` ブロックを持ちません。決定論的なスパイン（監査、センサー、rebuild-stage-graph、状態検証）はプロジェクト全体の `settings.json` に登録されているため、どのランナーもそれを無償で継承します。スコープファイルを追加・改名したら、そのつどジェネレーター（または `scopes --check`）を実行し直してください。

### 自動で検証されること

この実装は、有効なスコープの一覧を実行時に `validScopes()` を通じて `.claude/scopes/*.md` の存在から導出します。そのため、ファイルが着地した瞬間に多くのことが整います。

- スコープは一度にすべての場所で有効になります — `init`、`--scope` の変更、環境既定の解決、`doctor` はすべて同じヘルパーを参照するため、どれもコードの編集を必要としません。
- エラーメッセージは、変更なしにあなたのスコープをアルファベット順で列挙します。
- `keywords` を与えていれば、フロントマターの一覧が埋まった時点で自由文の `/aidlc <text>` がそれを自動検出します — SKILL.md の散文編集は不要で、表の再生成だけです。
- 転置の乖離ガード（`compile --check`）は、ステージの `scopes:` タグを編集してグリッドを再コンパイルしていない場合にビルドを失敗させます。

### 自動では検証されないこと

- **スコープ名を打ち間違えた `scopes:` タグも、そのままパースされます。** `hotfix` ではなく `hotfx` を名指ししたステージのフロントマターは、きれいにコンパイルされます — 誰も求めていないグリッドの列を作るだけです。厄介なのは、`validScopes()` が `.md` ファイルから導出されるため、ファイルの無いスコープは呼び出し時に拒否される一方、ステージ上の打ち間違えたタグは、そのステージを本物のスコープから静かに脱落させる点です。`/aidlc --doctor` とスコープ別テストがガードレールです。
- **コンパイル済みスコープ表は乖離しえます。** ステージの `scopes:` を編集して手順 3 の再コンパイルと表の再生成を飛ばすと、エンジンは古いグリッドを読み続けます。`--check` フラグ（テストスイートが実行します）がこれを捕まえますが、それはあなたが実行した場合だけです。
- **スコープ別のフェーズ順カバレッジ。** 出荷されているフェーズ順のテストは、既知のスコープ名をハードコードした一覧を反復します。その一覧を伸ばすまで、新しいスコープはそこで動かされません。同じ変更の中で追加してください。
- **手で保守されているドキュメント。** ドキュメントを代わりに grep してくれるものはありません。スコープリファレンス、経路選択の表、カスタマイズの有効値一覧は散文です。スコープファイルとの歩調は自分で合わせてください。

## 既存のスコープを調整する

調整はもっと小さな編集ですが、着地するのはスコープではなくステージです。よくあるのは 2 つです。

- **ステージを出し入れする。** ステージの `scopes:` 一覧からスコープ名を追加・削除します。たとえば、あなたのチームが最初の版でも常に監視を配線するので `observability-setup` の `scopes:` に `mvp` を加える、といった変更がこれにあたります。タグを 1 つ、そして再コンパイル（`compile` + スコープ表）と `--doctor` の実行です。
- **既定の深さ・テスト戦略・レビュー上限を変える。** スコープの `core/scopes/aidlc-<name>.md` のフロントマターで `depth` を調整し、`testStrategy` を追加／削除し、`review_cap` を追加／削除します。前の 2 つは成果物とテストの量を再較正し、`review_cap` はステージのレビュークラスを `adversarial`・`advisory`・`none` へ下げます（上げることは決してありません）。各スコープが自分の既定値を持つため、変更はそのスコープを選ぶすべてのワークフローに適用されます。実行ごとの `--depth`、`--test-strategy`、`--review` は、対応する振る舞いをさらに下げられます。

いずれにせよ、上の手順 3 の「再コンパイルと doctor」の対が当てはまります。編集は小さく、検証は同じです。

階層についての注記です。出荷済みスコープの調整は、フレームワークが出荷したファイル — ステージの `scopes:` タグや、出荷済みの `core/scopes/aidlc-*.md` — を直接編集します。異なる既定値を望むフォークではそれで構いませんが、`aidlc-` の系譜を持つファイルを変えているのであり、フレームワークのアップグレード時にそれらを突き合わせる必要が生じうる点は意識しておいてください。他の皆が頼っている既定値に触れずにチーム固有の振る舞いが欲しいときは、出荷済みの 11 個と並べて新しいスコープファイルを追加するほうがきれいな道です。
