# Opus 5.5 向けワークフロープラグイン：設計案

状態: 設計案（2026-10-08）。未実装。プラグイン名 `focus` とスコープ名 `focus-flow` は仮の名前。

## 結論

標準の 33 ステージ・14 エージェントの代わりに、4 ステージ（うち 1 つは条件付き）・3 エージェントと専用スコープ `focus-flow` を、aidlc-workflows のプラグインとして定義する。

- 人が承認するのは「何を作るか」「どう作るか」「出してよいか」の 3 回にする。過去 6 件のワークフローでは 1 件あたり 14〜28 回の承認があり、そのうち約半数（131 回中 70 回）は 2 分以内に承認されていた。
- 成果物は判断ごとに 1 つの文書にまとめる。ID のずれや、同じステージ内の文書間の食い違いをなくし、Opus 5.5 の 1M トークンの文脈と長時間の自律作業を活かす。
- 検証はステップを重ねて行わず、テストと品質ゲートの実行結果と、新しい文脈で読む独立レビューで行う。Opus 5.5 は自分で検証するため、検証の指示を重ねると過剰になる。
- 公式のプラグイン機構だけを使い、標準のステージ・エージェント・スコープは変更しない。スコープを選ぶだけで従来の流れと切り替えられる。

## 1. 根拠

### 過去 6 件のワークフローの実績

対象は `aidlc/spaces/default/intents/` の 6 件（prd・i18n・locale・deeplink・bridge・ask-chat）。監査ログのイベント間隔から算出し、20 分を超える間隔は作業時間に含めていない（`docs/guides/stage-timing.md` と同じ規則）。

| 指標                       | 結果                                                                                                                         |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 経過時間と作業時間         | 合計約 280 時間のうち、作業は約 38 時間（14%）。承認待ち約 50 時間、一時停止約 56 時間                                       |
| 承認ゲート                 | 1 件あたり 14〜28 回。131 回中 70 回が 2 分以内に承認され、待ち時間の中央値は 1.0〜5.4 分                                    |
| 質問                       | 回答 265 件。推奨回答をそのまま採用 85 件、要約の確認 27 件、学習の質問への「追加なし」約 100 件                             |
| 作業時間の内訳             | code-generation 35%、inception 28%、construction の設計 15%、ideation 14%、operation 3%                                      |
| 手戻り                     | prd の設計とコードレビューで NOT-READY 28 回。ask-chat は書式検査の失敗で code-generation を丸ごとやり直した                 |
| ほぼ価値のなかったステージ | market-research と contract-design は 6 件中 0 件で実行。operation の 7 ステージはローカル専用のため各 1〜3 分で「該当なし」 |
| 文脈の途切れ               | Bolt を別ワークフローに分けた結果、ideation の文書を毎回書き直した。要件改訂後もストーリーが古い要件 ID を参照していた       |
| レビュー                   | レビュアーの読取範囲外で止まった回数が 77 回。ask-chat では指摘がすべて「受容」で、2 回目のレビューも同じ指摘を繰り返した    |
| センサー                   | 失敗 705 回。そのうち約 20% は成果物ではないファイル（記録用 JSON や `memory.md`）に対するもの                               |
| ワークフロー後の手戻り     | PR #4 はレビュー 15 往復、PR #96 は 7 版。指摘箇所だけを直し、同じ挙動を持つ別経路（導入と更新など）を確認していなかった     |

### Opus 5.5 の特性

出典は Anthropic の移行ガイド（Claude Opus 5.5 の節と、Claude Opus 5 の挙動の節）。

- 1M トークンの文脈、最大出力 128K。思考は常に有効で、推論の深さは推論強度（`low`〜`max`）で決まる。既定は `medium`。
- 開発作業では、`medium` で Claude Opus 5 の `high` と同等以上の結果を、少ない手順と約半分のトークンで出した。コードレビューでは見つけるバグが増え、誤検知は減った。
- 自分で作業を検証する。「見直して」「検証用のサブエージェントを使って」といった指示や、別の検証ステップを足すと過剰な検証になる。
- サブエージェントを多用しがちで、そのたびに文脈の再構築とコストがかかる。サブエージェントは、独立した大きな作業を並行させるときに使う。
- 手順を細かく並べた指示より、目的と制約を伝えた指示のほうが結果がよい。範囲を勝手に広げることがあるため、範囲は明示する。

### エンジンの制約（2.10.0）

- 専用スコープに自作ステージだけを入れれば、標準ステージはスキップされる。初期化の 3 ステージは常に実行される。
- モデルと推論強度はエージェントにしか設定できない。その設定が効くのは作業をエージェントに渡したとき（`subagent`・レビュアー等）だけで、`inline` のステージはセッションのモデルと推論強度で動く。
- 初期化以外のすべてのステージに承認ゲートが付く。ゲートの数はステージの数で決まる。
- Unit ごとの繰り返しと並列ビルドは、標準 `units-generation` の成果物を前提にしている。プラグインはこの成果物を作れない。
- 自作ステージの成果物名とステージ名は、プラグイン名で始める。既存ステージへの加算はできるが、担当エージェントの変更や記述の削除はできない。

## 2. 設計方針

1. **承認は人が決めるべき判断にだけ置く。** 「何を作るか」「どう作るか」「出してよいか」の 3 回。
2. **判断ごとに 1 文書。** 要件・ストーリー・受け入れ条件は 1 つの仕様書に、設計・NFR・テスト計画・作業順は 1 つの設計書にまとめる。
3. **質問は作業が実質的に変わるものだけ。** 推奨回答で済むものは「前提」として書き、承認時にまとめて確認してもらう。
4. **検証は実行で示す。** テストを先に書き、品質ゲート（このリポジトリでは `bun run check`）の実行結果を証拠として残す。否定側（止まるべきものが止まること）を先に確かめる。
5. **独立レビューは要所に 1 人。** 新しい文脈で読むレビュアーを、仕様・設計・実装の 3 か所に置く。ほかのステージ単位のレビューは設けない。
6. **エージェントは役割ではなく、文脈と権限の境界で分ける。** 対話で進めるステージはセッション自身が担い、実装とレビューだけを別エージェントに渡す。
7. **指示は目的・契約・完了条件・境界で書く。** 手順の列挙は、エンジンが要求する最小限の `### Step` に留める。

## 3. ステージ構成

| ステージ        | フェーズ     | 決めること・作るもの                               | 担当と方式                      | レビュー                 | 成果物                 |
| --------------- | ------------ | -------------------------------------------------- | ------------------------------- | ------------------------ | ---------------------- |
| `focus-frame`   | inception    | 何を作るか。課題・範囲・受け入れ条件               | `focus-lead-agent`・inline      | 1 回（advisory）         | `focus-spec`           |
| `focus-design`  | inception    | どう作るか。設計判断・影響範囲・テスト計画・作業順 | `focus-lead-agent`・inline      | 最大 2 回（adversarial） | `focus-design`         |
| `focus-build`   | construction | テスト先行で実装し、品質ゲートで検証する           | `focus-builder-agent`・subagent | 最大 2 回（adversarial） | `focus-build-report`   |
| `focus-release` | operation    | デプロイと本番確認（条件付き）                     | `focus-lead-agent`・inline      | なし                     | `focus-release-report` |

`focus-release` は、マージより先の配備があるプロジェクトでだけ実行する（`execution: CONDITIONAL`）。このリポジトリはローカル専用のため実行しない。承認は通常 3 回になる。最初の construction ステージでは、Walking Skeleton の要否を決める分類の確認が別に入る可能性がある（S5）。

## 4. 各ステージの定義

ステージ本文はエンジンの要件どおり `## Steps` と `### Step N` を持つが、各ステップは目的と完了条件だけを書く。本文は英語で書き、成果物は会話言語の規則に従って書かれる。

### focus-frame（何を作るか）

- **目的:** 依頼を、承認できる仕様にする。
- **入力:** 依頼文、開発ルール（`memory/`）、既存の codekb（あれば）、リポジトリ。
- **成果物 `focus-spec`:** 課題と利用者、範囲と範囲外、機能要件（`FR-n`）と Given/When/Then の受け入れ条件、数値つきの非機能要件、適用する開発ルール、`## Assumptions & Open Questions`、`## Sources`。
- **質問:** 答えによって作るものが変わる質問だけを、1 回にまとめて聞く。推奨回答で済むものは前提として書く。
- **しないこと:** 実装方式は決めない。依頼にない機能を加えない。

### focus-design（どう作るか）

- **目的:** 承認された仕様を、実装できる計画にする。
- **成果物 `focus-design`:**
  - 設計判断。各判断に背景・決定・結果・退けた案（2 つ以上）を書く。
  - 影響範囲。同じ挙動を持つ全経路（例: 導入と更新）と、変更が波及する呼び出し元を列挙する。
  - 契約。所有者の表と、変更するインターフェース。
  - 「要件 ID → 実現機構」の表。機構はモジュール・関数・設定キーまで書く。
  - テスト計画。先に失敗させるテストと、否定側の確認を含める。
  - 作業順、リスクと戻し方。画面の変更があれば画面の流れと状態も書く。
- **しないこと:** コードを書かない。仕様にない要件を足さない。足す必要がある場合は仕様の改訂として提示する。

### focus-build（作って確かめる）

- **目的:** 設計どおりに実装し、仕様の受け入れ条件を満たすことを実行結果で示す。
- **進め方:** 作業順に沿って、テストを先に書いてから実装する。プロジェクトの品質ゲートを通す。設計と違う実装が必要になったら、設計書を改訂して逸脱として報告する。
- **成果物 `focus-build-report`:** 結果の要約、受け入れ条件 → テスト → 結果の表、実行した検証コマンドと出力、設計からの逸脱、残るリスク。
- **センサー:** `linter`・`type-check`。

frontmatter の例（`stages/construction/focus-build.md`）:

```yaml
---
slug: focus-build
name: Build and verify
phase: construction
plugin: focus
execution: ALWAYS
condition: Always executes once the design is approved.
lead_agent: focus-builder-agent
support_agents: []
mode: subagent
reviewer: focus-reviewer-agent
review_artifact: focus-build-report
reviewer_max_iterations: 2
review_class: adversarial
workspace_requires: true
produces:
  - focus-build-report
consumes:
  - artifact: focus-spec
    required: true
  - artifact: focus-design
    required: true
requires_stage:
  - focus-design
sensors:
  - linter
  - type-check
scopes:
  - focus-flow
inputs: focus-spec, focus-design, the repository
outputs: application code and tests + focus-build-report.md (engine-resolved)
---
```

### focus-release（条件付き）

配備があるプロジェクトでだけ実行し、配備・本番での確認・戻し方を `focus-release-report` に残す。ローカル専用のプロジェクトでは、実行時にスキップする。

## 5. エージェント

| エージェント           | 使う場所                        | 方式     | モデル     | 推論強度   | 道具                                            |
| ---------------------- | ------------------------------- | -------- | ---------- | ---------- | ----------------------------------------------- |
| `focus-lead-agent`     | frame・design・release          | inline   | セッション | セッション | セッションと同じ                                |
| `focus-builder-agent`  | build                           | subagent | Opus 5.5   | `medium`   | 編集・実行あり、`Task` なし                     |
| `focus-reviewer-agent` | frame・design・build のレビュー | reviewer | Opus 5.5   | `high`     | 読取・実行・レビュー記録の書き込み、`Task` なし |

- 標準のレビュアーは `model: sonnet`・`effort: medium` で動いている。本設計ではレビュアーを Opus 5.5 にし、コードレビューの強さを活かす。
- 実装を別エージェントに渡す理由は二つ。モデルと推論強度を固定できること、承認済みの仕様と設計だけを入力とする新しい文脈で作業できること。
- builder は `medium` から始める。品質の不足が測定で分かった場合だけ `high` に上げる。

各エージェントの本文に入れるもの:

- 依頼された範囲を守り、範囲を変える場合は一文で伝えて元の依頼どおり進めること。
- 結果を先に書き、読み手が文脈を知らない前提で書くこと。
- 進捗や完了の報告は、そのセッションのツール実行結果で裏付けられるものだけにすること。
- レビュアーは判断を変える指摘だけを重要度つきで挙げ、指摘の根拠となる箇所を示すこと。

入れないもの: 「念のため見直す」「検証用にサブエージェントを使う」といった自己検証の指示。Opus 5.5 では過剰な検証の原因になる。

## 6. 専用スコープ

`scopes/focus-flow.md`:

```yaml
---
name: focus-flow
plugin: focus
depth: Standard
testStrategy: Standard
description: Three decisions - what, how, ship - tuned for Claude Opus 5.5
keywords:
  - focus
skeleton: off
runner: true
sensors: on
learnings: on
summary_confirmation: on
---
```

- 既定スコープは `classic` のままにし、`/aidlc --scope focus-flow` か専用の起動コマンドで選ぶ。
- 学習の確認は有効のままにする。承認が 3 回になるため、確認の回数も 3 回になる。
- ガードの設定はスコープで指定しない。利用者の設定に従う。

## 7. 大きな作業の扱い

初版では Unit を使わず、`focus-design` の作業順に沿って 1 回のビルドで進める。過去 6 件の Unit 数は 9・6・2・1・1・1 で、複数の Bolt に分けた計画は別ワークフローに分かれ、ideation の文書を書き直す結果になった。

Unit ごとの繰り返しと並列ビルドが必要な規模の作業には、次の版で別スコープを用意する。標準 `units-generation` を加算で専用スコープに入れ、`focus-design` を入力として読ませ、`focus-build` を Unit ごとの実行に対応させる。

## 8. Guide への影響

- プラグインのステージはステージグラフに含まれ、ダッシュボードに表示される。公式ドキュメントへの対応表がないため、ステージファイルの説明を表示する必要がある。
- Unit を使わないため、Unit × ステージの表は空になる。時間計測は 4 ステージ単位で動く想定。
- 表示と時間計測が崩れないことを、試作の段階で確認する（S7）。

## 9. 作り方と検証

- ソースはこのリポジトリの `plugins/focus/` に置く。公式のプラグイン作成の慣例どおりの置き場で、Guide のカスタマイズ画面からも読める。
- 公式の `aidlc-plugin-create.ts` で骨組みを作り、`aidlc plugin validate` と `aidlc-plugin-test.ts` で、取りこぼしなく合成でき、2 回目の合成がバイト一致することを確かめる。
- 検証と合成テストを `bun run check` に配線する。
- このリポジトリの AI-DLC にビルドして組み込み、実際の小さな機能 1 件で試行する。比較対象は、同じ規模の deeplink（Unit 1、作業 2 時間 56 分、承認 25 回、回答 51 件）と ask-chat（作業 8 時間 39 分、承認 14 回、code-generation の再実行あり）。

試行で測る指標:

| 指標                   | 狙い                                     |
| ---------------------- | ---------------------------------------- |
| 承認の回数と待ち時間   | 3 回（配備がある場合 4 回）              |
| 作業時間               | 同規模の過去例より短い                   |
| 質問数と推奨採用の割合 | 推奨をそのまま採用する質問が出ない       |
| レビューの指摘と採用数 | 指摘が採用されるか、根拠つきで退けられる |
| やり直し               | ステージの差し戻しと全面再実行がない     |
| マージ後の手戻り       | PR のレビュー往復が過去例より少ない      |
| センサーの失敗         | 成果物以外への誤検知がない               |

## 11. 実装順

1. 公式の骨組みで最小のプラグインを作り、S1〜S6 を確かめて、結果をこの文書に追記する。
2. 4 ステージ・3 エージェント・スコープを書き、検証と合成テストを `bun run check` に通す。
3. このリポジトリで小さな機能 1 件を試行し、9. の指標を記録する。推論強度と質問の量を調整する。
4. 試行結果を見て、Unit 対応の版と、Cursor など他のツールへの展開を決める。

## 12. 未決事項

1. プラグイン名とスコープ名。仮に `focus` と `focus-flow`。
