# 版ゲートの設計（案）

プロジェクトまたはエンジンの aidlc-workflows の版が Guide の対応版と一致しない場合、Guide は更新画面を表示し、更新が終わるまで主要機能を使えなくする。読み取り処理は対応版の形式だけを前提にでき、複数の版の解釈を抱えずに済む。2026-10-09 時点の案で、未実装。

## 決定事項（2026-10-09）

| 項目 | 決定 |
|---|---|
| 基準の版 | Guide の対応版 `WORKFLOWS_TARGET_VERSION`。公式の最新リリースは見ない（起動時の通信も不要） |
| 対応版より古い | 更新画面を表示してブロックする |
| 対応版より新しい | 拡張の更新（または対応待ち）を案内してブロックする。Guide はダウングレードしない |
| ブロック中も使えるもの | 更新・セットアップ画面、同梱の公式ドキュメントの閲覧、Doctor の診断と修復・再試行 |
| ブロックするもの | ダッシュボードのワークフロー表示、カスタマイズ、回答の書き込み、ドキュメントの質問（チャット）、MCP の文書参照・状態参照、ステータスバーの現在地表示 |
| 回避手段 | 設けない。Doctor と修復だけを使える |

## 判定

新しい純関数 `inspectVersionGate(root)` を共有パッケージに置き、拡張・ブラウザ版・MCP の3経路が同じ判定を使う。いまの判定は拡張の `inspectWorkflowsManagement`（プロジェクト側）と `inspectCliManagement`（エンジン側）に分かれ、Doctor の `workflowsVersionCheck` は docs manifest の版と比べて新しい版を正常とみなすなど、基準がばらばらになっている。これを1つにまとめる。

- **プロジェクトの版:** 各ハーネスの `tools/data/aidlc-stamp.json` の `frameworkVersion` と `tools/aidlc-version.ts`、および `.aidlc-version`（pin）。すべてが対応版と一致したら一致とする。
- **エンジンの版:** native 導入のプロジェクトでは、pin を解決した実行ファイルの版。copy 版ではハーネスの版がそのままエンジンの版になる。
- **結果:** `ok`、`older`、`newer`、`unknown`（読めない・衝突）、`not-installed`。`ok` 以外はブロックする。`not-installed` は従来のセットアップ画面へ誘導する。
- **費用:** 判定は同期の fs 読み取りだけで行う。実行ファイル全体の sha256 は判定に含めず、更新・修復のときだけ計算する。ダッシュボードを開くたび、またファイル変更の監視時に再判定する。

## 強制する場所

| 経路 | 強制の方法 |
|---|---|
| 拡張のコマンド（開く・ようこそ・更新情報） | `openDashboard` の前に判定し、`ok` 以外は更新画面を開く。セットアップ完了済みでも素通りさせない |
| ダッシュボード webview | 起動時の `/api/workflow` より前に、ホストから `version-gate` を送る。ブロック中はナビを差し替え、`docs` / `guides` のルートだけ表示する。ドキュメント画面の質問欄は出さない |
| api-core（拡張内・ブラウザ版の共通） | `routeRead` / `routePost` の入口で判定し、許可リスト（`official-docs/*`、`guides*`、`docs-settings` など閲覧系）以外を「更新が必要」のエラーで拒否する。画面の分岐が漏れても、ここで止まる |
| ブラウザ版 `dashboard-server` | api-core の入口判定で同じく止まる。起動時にも判定を表示する |
| MCP サーバー | 全ツールの呼び出しごとに判定し、`ok` 以外は更新が必要な旨と手順を返す。共有の `.mcp.json` / `SKILL.md` の登録は書き換えない |
| ステータスバー | 現在地の代わりに「更新が必要」を表示し、クリックで更新画面を開く |
| 起動時の通知 | 「後で」（snooze）は廃止する。ブロック中は毎回更新画面へ誘導する |

## 更新画面

既存の更新パネル（`aidlcGuide.updateWorkflows`）を拡張して使う。

- 現在の各ハーネスの版・pin・エンジンの版と、対応版を並べて表示する。
- `older`: 全ツールを対応版に更新する。作業中でも実行でき（2.11 の決定事項1）、管理者権限の扱いは上流に合わせる（決定事項2）。更新で `.aidlc-version` などの共有ファイルが変わるので、コミットが必要なことを明記する。
- `newer`: 拡張の更新確認（`checkUpdate`）を出す。対応する Guide がまだない場合は、その旨を表示する。
- `unknown`: Doctor と修復を案内する。
- 同梱の公式ドキュメントへのリンクを置く。

## 既知の制約

- **チームで共有するリポジトリ:** 1人が拡張を更新すると、その人はリポジトリの版を上げるまで使えない。拡張は main へのマージごとに配布されるため、対応版を上げる Guide のリリースは、全利用者にプロジェクトの更新を求めることになる。リリースハイライトと更新画面で事前に知らせる。
- **信頼されていないワークスペース:** 更新できないので、ドキュメント閲覧以外は使えない。
- **フォルダーを開いていない:** 判定対象がないため、ドキュメント閲覧だけを許可する（現状はダッシュボード自体が開けない。別途検討）。
- **マルチルート:** 判定は root ごとに行う。

## 2.11 対応との関係

- reader は対応版の形式だけを読めばよくなる。2.11 で解釈が変わった規則（STAGE_JUMPED の範囲、記録 JSON がない場合の Verdict、memory の relaxed / off、run floor）は、版を切り替えずに 2.11 の規則へ置き換える。
- 2.11 調査の「4. reader の互換修正を先に出すか」は不要になる。版ゲートと 2.11 対応を同じリリースで出す。版ゲートを先に main へ入れる場合は `release:skip` を付け、対応版 2.10.0 のまま配布しない（2.11 に上げた利用者が拡張の更新待ちでブロックされるのを避ける）。
