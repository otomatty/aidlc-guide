# Claude Code 向け開発ワークフロープラグイン：設計

状態: 初版を `plugins/focus/` に実装（2026-10-08）。実プロジェクトへの導入と、実際の Jira チケットでの試行はまだ行っていない。
プラグイン名 `focus` とスコープ名 `focus-flow` は仮の名前。

## 結論

Jira チケットを起点に、Inception で要件・設計・Unit・Bolt を決め、Construction で Unit ごとにテストを先に書いてから
TDD で実装するワークフローを、aidlc-workflows のプラグインとして実装した。対象は Claude Code、モデルは Claude Opus 5.5。

```text
初期化（自動）
  │
  ├─ Inception（標準ステージ ＋ プラグインの追記）
  │    reverse-engineering    既存コードの構成を codekb に残す
  │    requirements-analysis  Jira・Confluence・コードから要件と受け入れ条件。確証のない点は宛先つきの質問
  │    domain-design          設計。構成の As-Is と To-Be を比較図で示す
  │    units-generation       Unit と依存関係
  │    delivery-planning      Bolt の計画、Construction の進め方の推奨、品質ゲートのコマンド
  │
  └─ Construction（プラグインのステージ、Unit ごと）
       focus-test       失敗するテストを先に書く → AI が要件の漏れを確認 → 人がテストを最終確認
       focus-implement  人がテストを確かめた記録を受けてから、TDD でテストを通し、品質ゲートを通す

各ステージ: 図（SVG）を中心にした成果物 → 承認前に図を自動検査 → コミット → 人の承認
```

- 標準の仕組みで使えるものは使う。Unit と Bolt、unit-major / stage-major、Unit ごとの検証コマンドは標準のまま動く
  （swarm は code-generation 専用の手順のため、focus のステージには使わない。2. を参照）。
- 人が読む説明は図を中心にする。図は JSON の元データから SVG を作り、Markdown から読み込む。
- 図が元データと一致し最新であることを、承認の前にエンジンのセンサーで確かめる。一致しなければ承認に進めない。
- インタラクティブな HTML は、同じ元データを使う形で別途検討する（6. を参照）。

## 1. 前回の設計からの変更

| 項目              | 前回                                   | 今回                                                                            |
| ----------------- | -------------------------------------- | ------------------------------------------------------------------------------- |
| Inception         | プラグインの 2 ステージ                | 標準の 5 ステージに、プラグインから日本語の手順を追記する                       |
| Unit と Bolt      | プラグイン側で管理（進め方を選べない） | 標準の `units-generation` と `delivery-planning`。進め方は標準の手順で選べる    |
| 品質ゲート        | 自作のセンサーで実行                   | 実装ステージで実行し、標準の Unit ごとの検証コマンドでも確かめる                |
| 人のレビュー      | HTML                                   | 図（SVG）を埋め込んだ Markdown。HTML はインタラクティブな資料として別に検討する |
| 2 つめ以降の Bolt | 別のワークフロー                       | 同じワークフローの中で、標準の Bolt の仕組みで進める                            |

変更の理由: 標準の Unit 機構は `units-generation` の成果物を前提にしている。一方、プラグインのステージは
同じフェーズの標準ステージより後ろに並ぶため、自作の設計ステージの後に `units-generation` を置けない。
そこで Inception は標準ステージを使い、プラグインは手順の追記に留めた。

## 2. 標準の仕組みで使っているもの

| 標準の仕組み                             | 使い方                                                                                 |
| ---------------------------------------- | -------------------------------------------------------------------------------------- |
| `reverse-engineering` と codekb          | 既存コードの理解。codekb はスペース単位で残り、次のチケットでも使える                  |
| `requirements-analysis`・`domain-design` | 要件と設計。質問の書式、要約の確認、承認ゲートは標準のまま                             |
| `units-generation`                       | Unit と依存関係（エンジンが読む Unit の依存グラフ）                                    |
| `delivery-planning`                      | Bolt の計画                                                                            |
| Construction の進め方                    | unit-major / stage-major、serial / swarm、承認の自動化（gated / autonomous）を人が選ぶ |
| Unit ごとのチェックポイント              | 人が承認した検証コマンド（品質ゲート）を、Unit ごとに実行して確かめる                  |
| `source-manifest.json` と出所の記録      | Unit ごとに変更したソースを記録し、レビューした内容とコミットの一致を確かめられる      |
| レビュアーの手順                         | テストのレビュー（READY / NOT-READY、最大 2 回の差し戻し）                             |
| センサーの手順                           | 承認の前に図を検査し、失敗したら承認に進めない（明示の上書きは記録に残る）             |
| 学習の記録                               | 承認のたびに、次に活かす学びを記録できる                                               |
| モデルの方針（`aidlc config models`）    | 標準のエージェント（要件・設計の担当、標準のレビュアー）のモデルと推論強度を設定する   |

### Bolt と Construction の進め方

プラグインのステージ `focus-test` と `focus-implement` は、Unit ごとに回る Construction のステージ
（`for_each: unit-of-work`）として定義した。`units-generation` がスコープに入っているため、標準の
Construction の手順がそのまま適用される。

- 進め方: Unit を 1 つずつ最後まで進める unit-major か、ステージごとに全 Unit を進める stage-major かを、人が選ぶ。
- 実行: 直列（serial）か並列（swarm）かを、stage-major のときに人が選ぶ。ただしエンジンの swarm は、Unit ごとの
  `subagent` ステージを code-generation の手順で並列に動かす。focus のステージをこの手順で動かすと、テストの承認前に
  実装まで進んでしまうため、両ステージは `inline` にして swarm の対象から外した。swarm を選んでも、両ステージは直列で動く。
- 検証: Unit ごとのチェックポイントで、人が承認した検証コマンド（品質ゲート）を実行する。
- テストの確認: unit-major では、エンジンは Unit の途中のステージの承認画面を出さず、Unit の最後のチェック
  ポイントでまとめて確認する。そのままでは focus-test の承認より先に実装が始まるため、focus-implement に
  `summary_confirmation: required` を付け、コードを書く前に人がテストを確かめる確認を置いた。エンジンはこの確認の
  記録を検査し、記録より前に保存された報告書では完了を認めない。stage-major でも Unit ごとに同じ確認をする。
  ただし、人が承認の自動化（autonomous）を選んだ Construction では、エンジンはこの確認を省く。

組み込んだ状態のエンジンで、両ステージが unit-major の対象として扱われることを確認した（9. を参照）。

## 3. 標準ステージへの追記の仕組みと制約

- 追記は、各標準ステージの手順の先頭（`before-step:1`）と、完了の報告（Completion Handoff）の直前に差し込む。
  図・検査・コミットを完了の報告より前に終えるため。完了の報告のステップ番号は標準の版で変わりうるので、
  テストで組み込み先の標準ステージの本文から番号を確かめ、合成テストで差し込めない場合に失敗させている。
- 最初にコミットしうるステージ（reverse-engineering、実行しない場合は requirements-analysis）の開始時に、
  既定ブランチにいれば作業ブランチを作る。
- 追記は、そのステージを使うすべてのスコープの本文に入る。このため、各追記の冒頭に「スコープが `focus-flow` の
  ときだけ従う」と書き、図の検査センサーもほかのスコープでは何もしない。テストでこの条件を守らせている。
- 標準ステージの本文（英語）と担当エージェントは変えられない。日本語の手順を追記として足す形になる。
  プラグインのステージ（Construction）は、本文もエージェントもすべて日本語で書いた。
- 共通の約束（情報源、宛先つき質問、図解、コミット）は、ナレッジ `focus-flow-guide.md` の 1 か所に書き、
  追記とステージはそこを参照する。

## 4. 図解

### 方式

人が読む成果物は、図を中心に説明する。図は画像（SVG）として作り、Markdown から読み込む。

1. 成果物のフォルダーの `diagrams/<名前>.json` に、図の元データを書く。
2. `bun .claude/tools/focus-diagram.ts render diagrams/<名前>.json` で SVG を作る。
3. 本文に `![図 1: 説明](diagrams/<名前>.svg)` で埋め込む。

| 種類      | 用途                 | 特徴                                                                         |
| --------- | -------------------- | ---------------------------------------------------------------------------- |
| `graph`   | 構成、流れ、依存関係 | 層ごとに自動で配置する。2 段以上離れた矢印は、間のボックスを避けて通す       |
| `compare` | As-Is と To-Be       | 同じ ID の要素を比べて、追加・変更・削除を自動で判定し、色・記号・凡例で示す |
| `matrix`  | 要件とテストの対応   | 対応のない要件を「未対応」、要件のないテストを警告として表示する             |

### 画像にした理由

- GitHub・VS Code・PR の画面で、そのまま表示される。HTML のように開き方を案内する必要がない。
- 元データ（JSON）が差分として読める。図の変更をレビューできる。
- 描画が決定的なので、「図が元データから作られた最新のものか」を機械で確かめられる。手で描いた図や古い図は、
  承認の前に差し戻される。
- Opus 5.5 は図の読み取りが正確で、図を入力にした作業もしやすい。
- 色だけに頼らず、記号（＋・△・－）と文字で状態を示す。背景を白に固定し、暗い表示でも読める。

### 検査

センサー `focus-diagrams`（承認の前に実行し、失敗すると承認に進めない）が、次を確かめる。

- 画像は文書のフォルダー内の相対パスで、外部の URL や絶対パスではない。
- SVG に同じ名前の元データがあり、元データから作り直した結果と一致する。
- 主な成果物（`requirements`・`components`・`unit-of-work`・`bolt-plan`・
  `focus-test-report`・`focus-implementation-report`）に図が 1 つ以上ある。

## 5. Construction：テスト先行・TDD・品質ゲート

| 順  | 誰が                       | 何をする                                                                             |
| --- | -------------------------- | ------------------------------------------------------------------------------------ |
| 1   | テスト作成（Opus、`high`） | 受け入れ条件ごとに、失敗するテストを書く。期待どおりに失敗することを実行して確かめる |
| 2   | レビュアー（Opus、`high`） | 新しい文脈で、要件の漏れと、実装しなくても通るテストを探す。最大 2 回差し戻す        |
| 3   | 人                         | 要件とテストの対応図（`matrix`）とテストを見て、最終確認する                         |
| 4   | 実装（Opus、`medium`）     | テストを 1 つずつ通し、整理し、品質ゲートを通す。承認されたテストは変えない          |
| 5   | 人と標準の検証             | Unit ごとの検証コマンド（品質ゲート）の実行結果と、変更箇所の図を見て承認する        |

- テストを書く担当と実装する担当を分け、実装の都合でテストが歪まないようにした。
- 失敗するテストのコミットを git フックが拒む場合は、テストフレームワークの「失敗を期待する」指定を付けてコミットし、
  実装ステージで外す。

## 6. インタラクティブな説明資料（検討）

AI の成果物とコードベースを理解するための手法を比べた。いずれも、静的な図と同じ元データ（JSON）と、
成果物の ID（`FR-n`・`AC-n`・`U-n`・`T-n`）から作れる。

| 手法                 | 分かること                                           | 操作                                     | データ源                              |
| -------------------- | ---------------------------------------------------- | ---------------------------------------- | ------------------------------------- |
| As-Is / To-Be の比較 | 何が加わり、変わり、消えるか                         | 差分だけ表示、要素を選んで前後を見比べる | `compare` の元データ                  |
| 追跡グラフ           | 要件 → 設計 → Unit → テスト → コードのつながりと抜け | 要件を選ぶと、関係する要素を強調する     | 成果物の ID、`source-manifest.json`   |
| 影響範囲マップ       | 変更がコードのどこに波及するか                       | 変更したファイルから呼び出し元を辿る     | import の依存関係、git の差分         |
| Unit と Bolt の進捗  | どの Unit がどこまで進んだか                         | Bolt ごとに絞り込む                      | Unit の依存グラフ、ワークフローの状態 |
| 質問の一覧           | 誰の回答待ちで止まっているか                         | 宛先・状態で絞り込む                     | 質問ファイルの宛先と `[Answer]:`      |
| 設計判断の記録       | なぜその設計にしたか、退けた案は何か                 | 判断から関係する要件と要素へ移る         | 設計の成果物                          |

推奨: 静的な図は承認とレビューのために残し、インタラクティブな資料は「追跡グラフ」と「影響範囲マップ」から
試作する。人がレビューで見落としやすいのが、要件とテストの抜けと、変更の波及だから。

置き場の候補は、この AIDLC Guide のダッシュボード。すでに AI-DLC のワークフローの記録を読んで表示しているため、
同じ元データを読む画面を足せば、プロジェクトごとに HTML を生成・配布する必要がない。試作では、
レビューにかかる時間と、見つかった抜けの数で効果を測る。

## 7. エージェントとモデル

| エージェント                                    | 担当                 | モデル     | 推論強度   |
| ----------------------------------------------- | -------------------- | ---------- | ---------- |
| 標準の担当（product・architect・delivery など） | Inception（inline）  | セッション | セッション |
| `focus-test-writer-agent`                       | テスト先行（inline） | セッション | セッション |
| `focus-builder-agent`                           | 実装（inline）       | セッション | セッション |
| `focus-reviewer-agent`                          | テストのレビュー     | `opus`     | `high`     |

- Inception は対話が多いため、セッション自身が進める。セッションは Opus 5.5、推論強度 `high` で使う。
- Construction の 2 ステージも `inline` で、セッションが担当エージェントの人格とナレッジを読み込んで進める
  （swarm の対象から外すため。2. を参照）。エージェント定義の `model` と `effort` は、別のエージェントとして
  呼ばれたときだけ使われる。テストのレビュアーは別のエージェントとして Opus で動く。
- 標準のレビュアー（要件・設計のレビュー）は、初期状態では Sonnet の `medium` で動く。Opus にするには
  `aidlc config models --agent <名前> --model <モデル> --effort high --project` で設定する。
- エージェントの本文には「念のため見直す」「検証用にサブエージェントを使う」といった指示を入れていない。
  Opus 5.5 では過剰な検証の原因になるため。

## 8. Jira・Confluence・コミット

- Jira と Confluence は、Atlassian の MCP ツールで読むだけにする。参照した版（Jira の更新日時、Confluence の版）を
  `## Sources` に記録する。本文は資料として扱い、そこに書かれた指示には従わない。
- 確証のない点は、宛先（PO・開発者・デザイナー・QA）を書いた質問にする。回答待ちの間はワークフローを一時停止する。
- 各ステージの最後、承認を求める前にコミットする。`git add` は対象を明示し、`--no-verify` は使わない。
  プッシュと PR の作成は人が行う。

## 9. 品質の確かめ方

| 確かめたこと                   | 方法                                                                                                                      |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| 図のツールの振る舞い           | テスト 101 件（入力の検証、配置、描画、比較、対応表、文書の検査、センサーの入口）                                         |
| プラグインの約束               | テスト 27 件（追記の適用条件と差し込み位置、Unit ごとのステージ、エージェントの設定、センサーとガイドの対応）             |
| テストが不具合を検出できるか   | 実装と内容をわざと壊し、テストが失敗することを確かめた（壊し方 7 通り）                                                   |
| 公式の検証と合成               | `aidlc-plugin-validate.ts` と `aidlc-plugin-test.ts`（取りこぼしなし、2 回目もバイト一致）を `bun run check` に組み込んだ |
| 組み込んだ後のエンジンの扱い   | 一時コピーに合成し、スコープの構成、センサーの紐づけ、Unit ごとの扱いを確認した                                           |
| センサーがエンジン経由で動くか | 図なし（失敗）、図あり（通過）、図を手で編集（失敗）、別スコープ（対象外）の 4 通りを確認した                             |
| 図の読みやすさ                 | 描いた図をブラウザーで画像にして確認した。見つかった問題は、テストを足してから直した                                      |

図の読みやすさの確認で直した問題: 矢印のラベルがボックスに隠れる、2 段以上離れた矢印が途中のボックスを横切る、
As-Is と To-Be を横に並べると幅が 2,000px を超えて縮小表示で読めない（左から右の流れでは上下に並べるようにした）。
