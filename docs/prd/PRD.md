## 1. 背景・課題

aidlc-workflows v2 は 5 フェーズ・32 ステージで構成され、Construction フェーズではユニット × ステージの組み合わせで成果物 Markdown が増殖する（参考: tb-lxp の 1 インテントで約 593 ファイル）。この構造は監査可能性・再現性のためには正しいが、人間側に次の 3 つの問題を生んでいる。

| # | 課題 | 具体像 |
|---|------|--------|
| P-1 | 現在地がわからない | 経験の浅いエンジニアは「今どのフェーズ・ステージにいて、次に何が来るのか」を `aidlc-state.md` の生テキストから読み解けない |
| P-2 | 成果物が多すぎて把握できない | ユニット × ステージで同名ファイルが複製され、フォルダを眺めても全体像・欠落・薄い箇所が見えない |
| P-3 | 調べ物が本線セッションを汚す | ワークフロー実行中に技術質問・用語質問・実装状況調査をすると、本線の Claude Code セッションの文脈が濁る |

加えてチーム運用上の要望として、**同期的に aidlc-workflows を回すとき（mob elaboration 等）に、ドライバーのブランチ状態を参加者全員がリアルタイムに確認したい**（P-4）。

## 2. 目的とゴール / 非ゴール

### 目的

aidlc-workflows の経験が浅いエンジニアでも、**現在の状況と今後のステージを迷わず理解でき**、成果物を**読みやすい形で閲覧・共有できる**ローカル開発者ツールを提供する。

### ゴール

- G-1: ワークフローの現在地（フェーズ / ステージ / ユニット / ゲート状態）が 1 画面で把握できる
- G-2: 各ステージの「目的・入出力・担当エージェント・次に人間へ求められること」が初学者向けの平易な解説付きで読める（公式ドキュメントへ deep-link）
- G-3: 成果物 Markdown を WYSIWYG ビューアで閲覧できる
- G-4: 本線セッションに影響を与えないサイドセッションから、aidlc の状態・技術質問・実装状況調査ができる
- G-5: モブセッション中、ドライバーのワークフロー状態と成果物を参加者全員がリアルタイム閲覧できる

### 非ゴール

- aidlc-workflows 本体（エンジン・ステージ定義・監査ログ）の変更・置き換え
- 成果物の汎用編集ツール化（監査対象ファイルの手編集は規約違反。編集は質問ファイルの `[Answer]:` 記入のみ）
- クラウドサービス化・アカウント管理（ローカルツールに徹する）
- 複数インテント横断の分析・レポーティング（将来検討）

## 3. 対象ユーザー

| ペルソナ | 状況 | 主なニーズ |
|---------|------|-----------|
| **初学者エンジニア** | aidlc-workflows 経験が浅い。モブに参加する | 現在地・次のステージ・用語を気軽に知りたい（G-1, G-2, G-4） |
| **ドライバー** | 本線の Claude Code セッションでワークフローを進める | 本線を汚さず調べ物をしたい。状態を参加者に見せたい（G-4, G-5） |
| **モブ参加者** | ドライバーの画面を見ながら議論・質問回答する | ブランチの中身と AI とのやりとりをライブで追いたい（G-3, G-5） |

## 4. 全体アーキテクチャ方針

**「1 ライブラリ・3 サーフェス」+ 既製品の活用。**

- 状態の読み取りロジックを 1 つのライブラリ（aidlc-reader）に集約し、Dashboard・MCP サーバー・Mob モードの 3 面から同じモデルを参照する
- ツールは **読み取り専用** を原則とする（aidlc の成果物はエンジンと監査ログが所有）
- リアルタイム共有は自作せず **VS Code Live Share** を軸に据え、本ツールは aidlc 固有の構造化ビューを重ねるレイヤーに徹する
- サイドセッションは Claude Code 標準のセッション分岐機構（独立起動 / `/branch` / `--fork-session`）の薄いラッパーとする

## 5. 機能要件

### F-01: aidlc-reader（状態モデルライブラリ）

- FR-1.1: `aidlc-state.md` をパースし、フェーズ / ステージ進捗（EXECUTE・SKIP・完了・進行中・ゲート待ち）・スコープ設定・ユニット情報を型付きモデルとして提供する
- FR-1.2: インテントの成果物ツリー（`aidlc/spaces/<space>/intents/<record>/`）を走査し、ユニット × ステージ × 成果物種別のマトリクスを構築する
- FR-1.3: 監査シャード（`<record>/audit/`）から直近のイベント履歴（ステージ開始 / 完了 / ゲート / レビュー verdict）を抽出する
- FR-1.4: アクティブインテントの解決（`active-intent` カーソル）と複数インテントの列挙に対応する
- FR-1.5: ファイル監視（state・construction 配下）により、生成中もモデルが追従する

### F-02: MCP サーバー

`.mcp.json` に登録し、本線・サイドセッションのどちらの Claude Code からも利用できる。

- FR-2.1: `aidlc_status` — 現在のフェーズ / ステージ / ユニット / ゲート状態 / 完了数を返す
- FR-2.2: `aidlc_explain_stage(slug)` — ステージの目的・入出力・担当エージェントを公式 docs から要約して返す
- FR-2.3: `aidlc_next_steps` — 次に来るステージと、そこで人間に求められること（ゲート / 質問）を返す
- FR-2.4: `aidlc_read_artifact(path)` — インテント配下の成果物本文を返す
- FR-2.5: `aidlc_glossary(term)` — Bolt / gate / unit などの用語を docs から引いて返す

### F-03: サイドセッション支援（`btw` ラッパー）

- FR-3.1: `btw` コマンド 1 つで、読み取り専用（`--permission-mode plan`）の独立 Claude Code セッションを新ターミナルに起動する
- FR-3.2: `btw --fork` で本線セッションの文脈を引き継いだ分岐セッションを起動する（最新セッション ID の解決を隠蔽）
- FR-3.3: `btw -p "<質問>"` でヘッドレスのワンショット質問に対応する
- FR-3.4: fork の既知の制約（JSONL は最終フラッシュ時点であり、本線実行中の直近会話が含まれない場合がある）をヘルプ・ドキュメントに明記し、文脈が必要な場合は本線内 `/branch` を案内する

### F-04: Dashboard（ローカル Web）

- FR-4.1: **Now strip** — フェーズ / 現在ステージ / ユニット / Depth / 完了数（例: 15/22）を常時表示する
- FR-4.2: **Stage rail** — 実行対象ステージを一列に表示し、完了 / 進行中 / ゲート待ち / SKIP を色分けする。クリックでそのステージの成果物・解説・docs へ遷移する
- FR-4.3: **Unit × Stage マトリクス** — 行 = ユニット、列 = Construction ステージ。セルは成果物の有無・件数・レビュー verdict（READY / NOT-READY）を表示する
- FR-4.4: 各ステージカードに初学者向け解説（目的・入出力・担当エージェント・ゲートで求められること）を表示する
- FR-4.5: SKIP ステージは折りたたみ、SKIP 理由（スコープ由来）を表示する

### F-05: Docs Bridge（ドキュメント直結）

- FR-5.1: ステージ slug → 公式ドキュメント該当節（guide / reference）への静的対応表を持ち、Dashboard と MCP（FR-2.2, FR-2.5）の両方が同じ対応表を参照する
- FR-5.2: docs リポジトリの場所は設定ファイルで指定する（ローカル clone のパス）
- FR-5.3: プロジェクト固有ドキュメント（PRD / ADR / team practices）へのリンク欄を設定で追加できる

### F-06: WYSIWYG Markdown ビューア

- FR-6.1: 成果物 Markdown を WYSIWYG 表示する（第一候補: Milkdown / Crepe）
- FR-6.2: 既定は読み取り専用。編集は `*-questions.md` の `[Answer]:` 記入のみ許可する（許可対象はファイル名パターンで制御）
- FR-6.3: Mermaid 図はレンダリングして表示する（成果物に多用されるため）

### F-07: Mob モード（リアルタイム共有）

- FR-7.1: Dashboard を `--host` で LAN 公開でき、参加者はブラウザで閲覧できる
- FR-7.2: ファイル監視 → WebSocket push により、ドライバー側の状態変化（ステージ遷移・成果物生成）が参加者ビューに即時反映される
- FR-7.3: 参加者ビューは read-only 固定（編集 UI・FR-6.2 の編集も無効）
- FR-7.4: リモート参加向けのトンネル公開（cloudflared / Tailscale 等）は手順ドキュメントとして提供する（ツール本体には組み込まない）

### F-08: 運用ガイド（自作コード外の成果物）

- FR-8.1: **Live Share 運用ガイド** — ドライバーがワークスペース共有 + Claude Code ターミナルの read-only 共有を行う手順・設定（`liveshare.autoShareTerminals` 等）・注意点をまとめる
- FR-8.2: **非同期共有規約** — ゲート通過時に自動 `git push` するフックの導入手順と、参加者側の checkout 不要閲覧（`git fetch` + `git show origin/<branch>:<path>`）の手順をまとめる

## 6. 非機能要件

- NFR-1 **読み取り専用原則**: FR-6.2 の質問ファイル編集を除き、ツールは aidlc 配下・リポジトリに書き込まない
- NFR-2 **起動速度**: Dashboard 起動から初回表示まで 3 秒以内（593 ファイル規模のインテントで）
- NFR-3 **追従性**: ファイル変更からビュー反映まで 2 秒以内（ローカル）
- NFR-4 **クロスプラットフォーム**: Windows（Git Bash 環境含む）と macOS で動作する
- NFR-5 **依存最小**: ランタイムは bun のみ。DB 不要（ファイルシステムが唯一の真実のソース）
- NFR-6 **堅牢性**: パース不能な state / 成果物があっても全体は落とさず、該当箇所を「解析不可」として表示する
- NFR-7 **セキュリティ**: Mob モードの listen は既定で localhost。LAN 公開は明示フラグ。トンネル公開時の認証は運用ガイドで注意喚起する

## 7. 技術方針

| 領域 | 選定 | 理由 |
|------|------|------|
| ランタイム / ビルド | bun + TypeScript | aidlc-workflows のツール群と同一。チーム標準 |
| Dashboard | Vite + React | チームの既存スタック（tb-lxp と同じ）で学習コストゼロ |
| WYSIWYG | Milkdown (Crepe) | Markdown ネイティブで往復変換の劣化が最小 |
| MCP サーバー | MCP TypeScript SDK (stdio) | Claude Code 標準の統合方法 |
| ファイル監視 | chokidar | クロスプラットフォームの実績 |
| リアルタイム共有 | VS Code Live Share（既製品）+ 自作 WebSocket push | 要件の大半を既製品が満たす。自作は構造化ビューの配信のみ |

## 8. スコープ外（明示）

- aidlc の状態・成果物への書き込み（質問ファイルの `[Answer]:` を除く）
- AI による成果物の自動要約・自動レビュー
- 全文検索エンジン（まず slug → docs 対応表で足りる想定。効かなければ将来追加）
- 複数インテント・複数スペースの横断ビュー
- 認証付きの社外公開ホスティング

## 9. リリース計画

| マイルストーン | 内容 | 完了条件 |
|--------------|------|---------|
| **M1** | aidlc-reader + MCP サーバー（F-01, F-02） | サイドセッションから `aidlc_status` / `aidlc_explain_stage` が実データで答える |
| **M2** | `btw` ラッパー + Dashboard 骨格（F-03, F-04, F-05） | 初学者が Now strip + Stage rail + マトリクスで現在地を説明できる |
| **M3** | WYSIWYG ビューア（F-06） | 成果物と Mermaid が読める。質問ファイルの回答記入ができる |
| **M4** | Mob モード + 運用ガイド（F-07, F-08） | モブセッション 1 回を Live Share + Dashboard 併用で完走する |

各マイルストーンで tb-lxp の実インテント（260719-tb-lxp-mvp、約 593 ファイル）を読み取りテストのフィクスチャとして使用する。

## 10. 成功指標

- S-1: 初学者が「現在のステージ・次のステージ・そこで求められること」をツールだけで 1 分以内に説明できる
- S-2: モブ参加者がドライバーへの口頭確認なしにブランチ状態を把握できる（モブ後アンケート）
- S-3: 本線セッションの `/clear` や文脈汚染を理由とするやり直しが減る（定性）
- S-4: ステージに関する「これ何？」系の質問が MCP / Dashboard で自己解決される割合

## 11. リスクと対応

| リスク | 影響 | 対応 |
|--------|------|------|
| aidlc-workflows のバージョンアップで state / ディレクトリ構造が変わる | reader が壊れる | パーサを 1 モジュールに隔離し、スキーマ version（State Version）で分岐。解析不可時は NFR-6 のフォールバック |
| `--fork-session` の JSONL フラッシュ問題 | 分岐セッションに直近文脈が乗らない | FR-3.4 の通り制約を明記し、本線内 `/branch` を第一に案内 |
| Live Share が組織ポリシーで使えない | G-5 が弱まる | 代替として tmux 共有 / Dashboard 単独運用を運用ガイドに記載 |
| Milkdown が aidlc 成果物の記法（テーブル・Mermaid 混在）を崩す | G-3 が弱まる | M3 冒頭に実成果物での表示検証を置き、不適なら候補交代（BlockNote / plain preview） |
