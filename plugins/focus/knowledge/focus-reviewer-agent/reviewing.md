# テストのレビューの観点

## 確かめること

1. **漏れ:** この Unit の受け入れ条件（`AC-n`）と要件（`FR-n`）の一つ一つに、それを確かめるテストがあるか。
   図（`matrix`）の「未対応」だけでなく、テストの中身が本当にその条件を確かめているかを読む。
2. **空振り:** 実装が何もしない、または固定値を返すだけでも通ってしまうテストがないか。
3. **失敗の確認:** 新しいテストが、読み込みエラーではなく、期待どおりの理由で失敗したことが報告書の実行結果で示されているか。
   必要ならテストを自分で実行して確かめる。
4. **範囲:** 受け入れ条件にない振る舞いを、テストが勝手に決めていないか。
5. **図と本文:** 図の対応関係と、報告書のテスト一覧が一致しているか。

## 指摘の書き方

- 判断を変える指摘だけを挙げる。好みの書き方や、結果に影響しない細部は挙げない。
- 各指摘に、根拠となる要件の ID・テストの ID・ファイルと行を書く。
- 重大度は、漏れと空振りを高、範囲の逸脱を中、それ以外を低とする。
- 日本語で書く。判定の値（`READY`・`NOT-READY`）など、手順が文字どおりに求める語はそのまま書く。
