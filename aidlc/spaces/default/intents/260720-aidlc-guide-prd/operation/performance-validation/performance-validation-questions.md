## Q1: 負荷試験の形

本ツールは**単一ユーザーのローカルプロセス**であり、同時接続はモブ参加者の数（数名〜十数名）に限られる。一般的な負荷試験（RPS を上げてスループット限界を探る）は目的に合わない。

- A. 同時接続数を上げるスループット試験
- B. **実データ規模に対する応答時間の実測**（tb-lxp 687ファイル。cold/warm を分けて記録）
- C. 両方

[Answer]: B

**根拠**: NFR-2 / NFR-3 は「起動→初回表示3秒」「変更→反映2秒」という**体感の応答時間**であってスループットではない。スケール軸は「同時接続数」ではなく「ワークスペースのファイル数」であり、そこを実測するのが要件に対する検証になる。同時接続の上限は SC-MM の想定内（数名〜十数名）で、全クライアントに同一 broadcast を送る設計上、参加者ごとの追加処理が無い。

## Q2: フィクスチャの扱い

tb-lxp（`/c/work/tb-lxp`、687ファイル、State Version 7、commit `dbf87e7`）を計測対象とする。team.md は「tb-lxp は read-only フィクスチャとして扱い、書き換えない」と定めている。しかし P-AV-4（保存操作）の計測には**書き込みが必要**である。

- A. tb-lxp に直接書き込んで計測する
- B. tb-lxp を別ディレクトリに複製し、複製側で書き込み計測を行う
- C. P-AV-4 の計測を諦める

[Answer]: B

**根拠**: A は明示された規約に反し、しかも「決定的であるようピン留めする」という前提を壊す。C は測れるものを測らない選択で、要件が残ったまま検証が消える。B は規約を守りつつ実測できる唯一の選択肢である。**実施結果**: 687ファイルをスクラッチへ複製し、そこでのみ `POST /api/answer` を発行した。計測後に tb-lxp が汚れていないことを `git status` と mtime で確認している。

## Q3: ブラウザ側の描画をどう測るか

NFR-2 の終点は「Now strip が読める時点」（FR-4.1 の受入基準）であり、サーバ応答時間だけでは足りない。

- A. サーバ応答時間のみを測り、描画は「速いはず」と推定する
- B. 実ブラウザで Navigation Timing / Resource Timing を取得して測る

[Answer]: B

**根拠**: A は推定を実測と偽ることになる。B を採り、実ブラウザで `navigationStart` からの相対時刻を取得した。あわせて **MA-6（FR-6.1 チェック項目2 — mermaid が図として描画されること）** も同じブラウザで確認できるため、build-and-test から持ち越した手動受入項目をこの機会に閉じる。

## Q4: 未計測のまま残す項目をどう扱うか

別端末が必要な項目（MA-1 / MA-2 / MA-3 / MA-4 の参加者側計測）は、本ステージの環境では実施できない。

- A. ローカルの数値で代用したことにする
- B. 未実施として明示し、`nfr-validation-matrix.md` に「未検証」と記録する

[Answer]: B

**根拠**: A は検証の偽装である。参加者側の反映時間（MA-4）については、**同一 broadcast を使う設計上サーバ側の push レイテンシがそのまま参加者側にも適用される**ことを根拠として示せるが、それは「測った」ことではないので推論として明記する。
