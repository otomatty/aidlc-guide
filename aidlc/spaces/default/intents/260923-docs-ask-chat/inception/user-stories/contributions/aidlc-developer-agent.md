## Contribution (implementability and story sizing)

既存 docs-qa（ask / job / cancel / evidence、`DocsQaResult`、サーバ側の直近 8 件履歴、ホストモード拒否、同時 1 件）を踏まえ、各物語が「そのサイズのまま実装できるか」だけを見る。

**US1.1** — 実装可能。ホームからカード列を外し、送信後にチャット画面へ移す変更に閉じる。既存の質問送信経路を入口の遷移先へ付け替える形で足りる。サイズは入口一本として妥当。ただし AC の 2000 字は入口送信にしか無い。

**US2.1** — 実装可能で、既存の待ち・キャンセル・単一ジョブ・ホスト拒否をそのまま載せる話としてサイズも妥当。直近 8 件の受け渡しと回答の非切り詰め（6000 字カット撤去）も既存契約の調整に収まる。一方、FR6 の「チャット画面から 2000 字超は送れない」がこの物語の AC に無い。続き質問の入力上限がここに無いと、実装・テストの受け入れが US1.1 の入口だけに偏る。

**US3.1** — 観測条件としては実装可能。現状はプロセス内メモリで再起動後に消える前提なので、ローカル永続だけが増える。置き場は要件どおり未決のままでよく、物語が機構を決め込んでいない点は実装しやすい。サイズは「残る／表示は切らない／ローカルのみ」に閉じており妥当。US2.1 の履歴件数と表示件数を分けたのも実装境界として正しい。

**US4.1** — 実装可能。既存の記事画面への遷移に、チャットへの戻りと会話・下書きの保持を足す話に閉じる。分割表示をしない前提ならルーティングと画面状態の保持で足りる。永続（US3.1）に依存させていないのも、セッション内往復としては実装しやすい。サイズ妥当。

まとめ: 四本の分け方と Must の粒度は既存フローに対して実装しやすい。唯一の欠けは、2000 字上限が US1.1 に寄り、US2.1 の続き送信 AC に無いこと。
