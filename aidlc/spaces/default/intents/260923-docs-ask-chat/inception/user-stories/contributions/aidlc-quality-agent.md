## Contribution (testability of the acceptance criteria)

四本の物語分け（入口 → 続き → 保存 → 引用往復）と質問者ひとりの主人公は、受け入れの単位として操作ごとに閉じている。UI で見える成否（入口の有無、遷移、送信可否、キャンセル、記事往復、再表示）は観測可能で、NFR1 の UI / 契約テストに落としやすい。

問題は、画面だけでは合否が決まらない条項が AC に混ざっている点である。

- **AC1.1.1〜AC1.1.3**: 入口の有無・カード非表示・遷移・2000 字超過時の送信拒否は、いずれも画面状態として検証できる。
- **AC2.1.2 / AC2.1.3（キャンセル） / AC2.1.5 / AC4.1.* / AC3.1.1 の「閉じたあと残る」**: 操作後の画面・API 拒否で判定できる。
- **AC2.1.1 の後半（直近 8 件が渡る／文字数で切らない）と AC3.1.2 の後半（渡す履歴だけ 8 件）**: 利用者の画面には現れない。リクエスト本文または契約テストでの観測点を AC に書かないと、UI 合格と輸送合格が混線する。
- **AC2.1.4（同時処理 1 件）**: 「同時」の観測手段（進行中ジョブ数など）が AC に無いと、受け入れが主観になる。
- **AC2.1.3 の「新しい質問で切り替わらない」**: AC2.1.2 で応答中送信が既に不可なら、独立した失敗パスを起こしにくい。拒否時に進行中ジョブが変わらないことを明示しないと冗長で検証しづらい。
- **AC3.1.1 の「スクロール分を含む」**: 仮想化・遅延描画がある場合、何を「出していた」と数えるかが曖昧。永続化されたターン集合＝再表示集合、と観測対象を固定したい。
- **AC3.1.3（ローカルにだけ）**: 否定形の排他は、保存先と「クラウドへ送らない」の観測手順（ローカルストア確認＋永続化向け送信が無いこと）を書かないと反証しにくい。

要件側の FR / NFR と対照すると、検証すべき振る舞いは揃っている。欠けているのは主に「どこを見て合否とするか」の明示である。

## Positions

AGREE: 物語四本・質問者ひとり・Must Have 一括は、受け入れの単位として操作ごとに閉じており妥当である。
AGREE: AC1.1.1 / AC1.1.2 / AC1.1.3 は入口・遷移・送信拒否として画面観測可能でテスト可能である。
AGREE: AC2.1.2（応答完了まで送信不可・待ち行列なし）は送信コントロールと試行結果で検証可能である。
AGREE: AC2.1.3 のキャンセル操作そのものは、現行と同じ操作での停止として観測・テスト可能である。
AGREE: AC2.1.5（ホストモード拒否）は送信・取得・キャンセル・根拠の拒否応答として契約／UI 双方で検証可能である。
AGREE: AC4.1.1 / AC4.1.2 / AC4.1.3 は記事遷移・復帰・会話と書きかけ保持として画面状態で検証可能である。
AGREE: AC3.1.1 の再起動後に会話が残る、という核は永続化＋再開の統合テストで検証可能である。
OBJECT: AC2.1.1 は「次を送れる」（UI）と「直近 8 件が渡る／文字数で切らない」（輸送）を一つの AC に混ぜており、後者の観測点（リクエストまたは契約）が無いと合否が曖昧である。
OBJECT: AC3.1.2 後半の「渡す履歴だけが直近 8 件」も同様に、表示と輸送の観測点が分離されていない。
OBJECT: AC2.1.4「同時に処理される質問は 1 件」は、進行中件数など観測可能な合図が AC に無く、受け入れ判定が主観になりうる。
OBJECT: AC2.1.3 の「新しい質問で進行中の応答は切り替わらない」は、AC2.1.2 下では独立トリガーが弱く、拒否時にジョブが不変であることの明示が無いと冗長・検証困難である。
OBJECT: AC3.1.1 の「スクロール分を含む」は、仮想化時に何を残存集合と数えるかが不明で、永続化集合＝再表示集合といった観測定義が要る。
OBJECT: AC3.1.3「ローカルにだけ」は否定の排他であり、保存先と非クラウドの観測手順が無いと反証しにくい。
